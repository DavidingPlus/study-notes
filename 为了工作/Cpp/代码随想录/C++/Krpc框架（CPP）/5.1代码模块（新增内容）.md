# krpcprovider修改：

在 `Krpc6` 中，为了解决旧版中的**内存泄漏问题**和**服务集群注册漏洞**，对 `KrpcProvider` 类做出了非常核心的架构优化与代码修改。

具体而言，`KrpcProvider` 的修改体现在以下三个维度：

***

## 1. 彻底解决 Request/Response 的内存泄漏

在 Protobuf 中，`service->GetRequestPrototype(method).New()` 和 `GetResponsePrototype(method).New()` 都是在堆上动态分配内存的（通过 `new`）。

### 旧版（`Krpc`）的代码：

旧版中，`SendRpcResponse` 的签名只有两个参数，未接收 `request` 指针，且整个流程中**完全没有释放** `request` 和 `response` 的堆内存：

```cpp
// 旧版签名：无 request 参数，且内部未进行 delete
void SendRpcResponse(const muduo::net::TcpConnectionPtr& conn, google::protobuf::Message* response);
```

* **后果**：在高并发吞吐下，随着处理的请求越来越多，服务器的内存会迅速耗尽，直接导致 OOM 崩溃。

### 新版（`Krpc6`）的修复：

新版将 `request` 传入了 `SendRpcResponse`，并在数据序列化发送完毕后，**主动释放**了这两个对象：

```cpp
// 新版签名
void SendRpcResponse(const muduo::net::TcpConnectionPtr& conn, google::protobuf::Message* response, google::protobuf::Message* request);

// 新版实现
void KrpcProvider::SendRpcResponse(const muduo::net::TcpConnectionPtr &conn, google::protobuf::Message *response, google::protobuf::Message *request)
{
    std::string response_str;
    if (response->SerializeToString(&response_str)) {
        // ... 发送逻辑 ...
    }
    // 发送完成后，显式释放堆内存，彻底杜绝内存泄漏
    delete response;
    delete request;
}
```

***

## 2. 闭包（Closure）实现机制的改变

### 旧版（`Krpc`）：

旧版使用 Protobuf 官方的模板函数 `google::protobuf::NewCallback` 自动生成闭包：

```cpp
google::protobuf::Closure *done = google::protobuf::NewCallback<KrpcProvider,
                                                                const muduo::net::TcpConnectionPtr &,
                                                                google::protobuf::Message *>(this,
                                                                                             &KrpcProvider::SendRpcResponse,
                                                                                             conn, response);
```

* **缺点**：这个官方模板函数很难方便地绑定和管理多个自定义的堆对象（比如我们需要把 `request` 也传进去一起销毁）。

### 新版（`Krpc6`）：

新版废弃了 `NewCallback`，改用自定义的 `KrpcClosure`，通过 C++11 的 **Lambda 表达式**进行值捕获，在回调时同时将 `conn`、`response` 和 `request` 一并传入，实现安全销毁：

```cpp
google::protobuf::Closure *done = new KrpcClosure(
    [this, conn, response, request]()
    {
        this->SendRpcResponse(conn, response, request);
    });
```

***

## 3. ZooKeeper 注册路径重新设计（支持集群与多实例）

这是分布式架构上的一个重大修改。

### 旧版（`Krpc`）的注册逻辑：

旧版将服务节点具体的方法作为 ZK 节点：

* 注册结构：`"/服务名/方法名"` -> 节点数据写入 `"IP:Port"`

```cpp
std::string service_path = "/" + sp.first; // /UserServiceRpc
zkclient.Create(service_path.c_str(), nullptr, 0);
for (auto &mp : sp.second.method_map) {
    std::string method_path = service_path + "/" + mp.first; // /UserServiceRpc/Login
    // 写入 IP:Port
    zkclient.Create(method_path.c_str(), method_path_data, strlen(method_path_data), ZOO_EPHEMERAL);
}
```

* **缺陷**：如果有多台服务器部署了同一个服务（即集群），第二台服务器启动时，会因为 `/UserServiceRpc/Login` 节点已经存在而注册失败，或者覆盖掉第一台服务器的数据。**旧版实际上不支持同一个服务的集群多实例部署**。

### 新版（`Krpc6`）的注册逻辑：

新版将注册细化到了**服务实例级别**：

* 注册结构：`"/服务名/实例IP:Port"` -> 节点名称和数据都为 `"IP:Port"`

```cpp
for (auto &sp : service_map)
{
    std::string service_path = "/" + sp.first; // 父节点：/UserServiceRpc
    zkclient.Create(service_path.c_str(), nullptr, 0);

    std::string ip_port = ip + ":" + std::to_string(port);
    std::string instance_path = service_path + "/" + ip_port; // 子节点：/UserServiceRpc/127.0.0.1:8000

    // 注册为临时节点（ZOO_EPHEMERAL）
    zkclient.Create(instance_path.c_str(), ip_port.c_str(), ip_port.length(), ZOO_EPHEMERAL);
}
```

* **优化效果**：
  * 支持了**多实例共存**。例如 `/UserServiceRpc` 目录下可以同时存在 `192.168.1.10:8000` 和 `192.168.1.11:8000` 两个临时子节点。
  * 配合新增的 `ServiceDiscovery` 模块，客户端获取 `/UserServiceRpc` 下的所有子节点，导入一致性哈希环，真正实现了动态集群负载均衡。

## <font style="color:rgb(51, 51, 51);">ServiceDiscovery类实现</font>

* **<font style="color:rgb(51, 51, 51);">新增目的</font>**<font style="color:rgb(51, 51, 51);">：在旧版中，客户端每次发起调用都需要通过 zookeeperutil 实时、同步地向 ZooKeeper 查询子节点并解析，这会带来严重的网络与性能开销。新版引入了 ServiceDiscovery 作为单例，负责集中管理服务发现。它通过 ZooKeeper 的 Watcher 机制异步监听节点变化，并在本地缓存节点信息和一致性哈希环，避免了重复查询。</font>
* <font style="color:rgb(51, 51, 51);">ServiceDiscovery 采用单例模式。其核心逻辑是在首次获取某服务时，向 ZooKeeper 注册一个子节点变更监听器（Watcher）。一旦某服务的提供者上线或下线，ZooKeeper 会回调 WatcherCallback，进而更新本地的一致性哈希环，使客户端总是能拿到最新的可用节点。</font>

```cpp
#ifndef SERVICE_DISCOVERY_H
#define SERVICE_DISCOVERY_H

#include "zookeeperutil.h"
#include "ConsistentHash.h"
#include <string>
#include <vector>
#include <unordered_map>
#include <unordered_set>
#include <shared_mutex>
#include <mutex>

class ServiceDiscovery
{
public:
// 获取单例对象的引用（全局唯一）
static ServiceDiscovery &GetInstance();

// 初始化 ZooKeeper 客户端并建立连接
void Init();

// 输入服务名（如 UserServiceRpc）和路由 Key（请求 ID 转换的字符串），返回经一致性哈希选择后的 "IP:Port" 节点
std::string GetTargetNode(const std::string &service_name, const std::string &key);

private:
// 构造与析构私有化，防止外部创建或销毁，符合单例模式
ServiceDiscovery() = default;
~ServiceDiscovery() = default;
ServiceDiscovery(const ServiceDiscovery &) = delete;
ServiceDiscovery &operator=(const ServiceDiscovery &) = delete;

// 内部持有的封装版 ZooKeeper 客户端，用于与 ZK 服务端交互
ZkClient m_zkClient;

// 映射表：Key 为服务名，Value 为该服务独立对应的一致性哈希环（使用智能指针管理寿命）
std::unordered_map<std::string, std::unique_ptr<ConsistentHash>> m_chash_map;

// 本地缓存：Key 为服务名，Value 为当前已知的可用 "IP:Port" 节点列表
std::unordered_map<std::string, std::vector<std::string>> m_nodes_cache;

// 互斥锁，用于保护上面两个 map 的线程安全
std::mutex m_mtx;

// 静态回调函数：符合 ZooKeeper 的 C API 规范。当监听的 ZK 节点发生变更时，ZK 异步线程会调用此函数
static void WatcherCallback(zhandle_t *zh, int type, int state, const char *path, void *watcherCtx);

// 内部辅助函数：用于增量更新本地缓存和哈希环（仅在 Watcher 触发时被内部调用，需在加锁状态下执行）
void UpdateCacheLocked(const std::string &service_name, const std::string &path);
};

#endif
```

```cpp
#include "ServiceDiscovery.h"
#include "KrpcLogger.h"

// 实现单例模式，使用 C++11 标准保证的局部静态变量线程安全初始化
ServiceDiscovery &ServiceDiscovery::GetInstance()
{
    static ServiceDiscovery instance;
    return instance;
}

// 启动并连接 ZooKeeper
void ServiceDiscovery::Init()
{
    m_zkClient.Start();
}

// 客户端获取可用节点的核心入口
std::string ServiceDiscovery::GetTargetNode(const std::string &service_name, const std::string &key)
{
    std::lock_guard<std::mutex> lock(m_mtx); // 加锁，保护临界资源

    // 如果是第一次调用该服务，本地还没有初始化它的一致性哈希环
    if (m_chash_map.find(service_name) == m_chash_map.end())
    {
        // 创建该服务对应的一致性哈希环实例
        m_chash_map[service_name] = std::unique_ptr<ConsistentHash>(new ConsistentHash());

        // 拼接 ZooKeeper 中的服务路径，例如 "/UserServiceRpc"
        std::string path = "/" + service_name;

        // 从 ZooKeeper 中获取该节点的所有子节点（服务提供者的 IP:Port）
        // 传入 WatcherCallback 和 this 指针。一旦子节点变更，就会触发回调
        std::vector<std::string> new_nodes = m_zkClient.GetChildren(path.c_str(), WatcherCallback, this);

        // 更新一致性哈希环的节点配置
        m_chash_map[service_name]->UpdateNodes(new_nodes);

        // 同步更新本地节点缓存
        m_nodes_cache[service_name] = new_nodes;
    }

    // 从对应的一致性哈希环中，根据 Key 路由，返回最终选中的服务提供方地址 "IP:Port"
    return m_chash_map[service_name]->GetTargetNode(key);
}

// 监听回调函数：当 ZooKeeper 检测到子节点变化（如某服务器宕机或新服务器上线）时异步触发
void ServiceDiscovery::WatcherCallback(zhandle_t *zh, int type, int state, const char *path, void *watcherCtx)
{
    // 判断是否是子节点变更事件
    if (type == ZOO_CHILD_EVENT)
    { 
        // 强转上下文指针，获取 ServiceDiscovery 的单例对象实例
        ServiceDiscovery *sd = static_cast<ServiceDiscovery *>(watcherCtx);
        std::string path_str = path;            // 事件发生的 ZK 路径，例如 "/UserServiceRpc"
        std::string service_name = path_str.substr(1); // 去掉斜杠，提取出服务名 "UserServiceRpc"

        std::lock_guard<std::mutex> lock(sd->m_mtx); // 加锁更新数据

        // 重新获取最新的子节点，并继续注册下一次变更的监听器（实现持续监听）
        std::vector<std::string> new_nodes = sd->m_zkClient.GetChildren(path_str.c_str(), WatcherCallback, sd);

        // 如果哈希环已经存在，全量更新该服务的哈希环节点列表
        if (sd->m_chash_map.find(service_name) != sd->m_chash_map.end()) {
            sd->m_chash_map[service_name]->UpdateNodes(new_nodes);
        }

        // 刷新本地缓存
        sd->m_nodes_cache[service_name] = new_nodes;
    }
}

// 增量更新逻辑（代码中保留了此设计，但在回调中为了保证哈希环一致性，直接使用了 UpdateNodes 全量更新）
void ServiceDiscovery::UpdateCacheLocked(const std::string &service_name, const std::string &path)
{
    // 重新获取最新的节点
    std::vector<std::string> new_nodes = m_zkClient.GetChildren(path.c_str(), WatcherCallback, this);

    // 获取引用
    auto &old_nodes = m_nodes_cache[service_name];
    auto &chash = m_chash_map[service_name];

    // 将旧节点与新节点放入集合中，用于求差集，以此判断哪些是新上线的，哪些是下线的
    std::unordered_set<std::string> old_set(old_nodes.begin(), old_nodes.end());
    std::unordered_set<std::string> new_set(new_nodes.begin(), new_nodes.end());

    std::vector<std::string> added, removed;

    // 找出新增的节点：在新节点列表中，但旧集合中没有
    for (const auto &n : new_nodes)
    {
        if (old_set.find(n) == old_set.end())
            added.push_back(n);
    }
    
    // 找出被移除的节点：在旧节点列表中，但新集合中没有
    for (const auto &n : old_nodes)
    {
        if (new_set.find(n) == new_set.end())
            removed.push_back(n);
    }

    // 精准调用 ConsistentHash 的 AddNodes（只增加新节点）
    if (!added.empty())
    {
        chash->AddNodes(added);
        LOG(INFO) << "[ServiceDiscovery] " << service_name << " 新增了 " << added.size() << " 个节点";
    }
    
    // 精准调用 ConsistentHash 的 RemoveNode（逐个移除下线节点）
    for (const auto &r : removed)
    {
        chash->RemoveNode(r);
        LOG(INFO) << "[ServiceDiscovery] " << service_name << " 移除了 1 个节点: " << r;
    }

    // 更新本地缓存
    m_nodes_cache[service_name] = new_nodes;
}
```

## <font style="color:rgb(51, 51, 51);">负载均衡：一致性哈希类</font>

* **<font style="color:rgb(51, 51, 51);">核心作用</font>**<font style="color:rgb(51, 51, 51);">：在分布式 RPC 中，服务往往部署在多台服务器上。一致性哈希用于决定客户端的请求应该路由到哪一台服务器。它通过引入“虚拟节点”解决数据倾斜问题，并带有一个独立的后台线程（均衡器），自动监控各节点的负载。若发现某些节点负载过高，会自动调整其虚拟节点数量（权重），实现自适应负载均衡。</font>
* **<font style="color:rgb(51, 51, 51);">引入读写锁（std::shared\_timed\_mutex）</font>**<font style="color:rgb(51, 51, 51);">：旧版使用普通互斥锁，导致多线程路由时全部卡在 GetTargetNode。新版使用读写锁，允许多个线程同时读取哈希环（共享锁），仅在节点更新时加写锁（独占锁）。</font>
* **<font style="color:rgb(51, 51, 51);">引入原子计数器与 thread\_local 批处理</font>**<font style="color:rgb(51, 51, 51);">：旧版多线程累加节点请求数会导致严重的 CPU 缓存行冲突。新版将计数器改为 std::atomic，并采用 thread\_local 计数器，每满 100 次请求才同步一次全局原子变量，减少了总线锁争抢。</font>

```cpp
    std::unordered_map<std::string, std::shared_ptr<std::atomic<long long>>> m_node_counts;

    // 核心修改：读写锁。读操作（GetTargetNode）加共享锁，写操作（Update/Add/Remove）加独占锁
    mutable std::shared_timed_mutex m_rw_mtx;
```

```cpp
// 核心路由算法
std::string ConsistentHash::GetTargetNode(const std::string &key)
{
    std::string node;
    std::shared_ptr<std::atomic<long long>> counter_ptr;

    {
        // 1. 加共享锁（读锁），允许多个线程同时并发读取哈希环，不发生阻塞
        std::shared_lock<std::shared_timed_mutex> lock(m_rw_mtx);
        if (m_keys.empty())
            return "";

        // 2. 计算 Key 的哈希值并利用 std::lower_bound 进行二分查找
        uint32_t h = hash_func(key);
        auto it = std::lower_bound(m_keys.begin(), m_keys.end(), h);

        // 3. 如果到了环的尾部，则循环回头部
        if (it == m_keys.end())
            it = m_keys.begin();

        // 4. 获取对应的物理节点地址，并取出该节点请求数的原子计数器指针
        node = m_ring[*it];
        counter_ptr = m_node_counts[node]; 
    } // 自动释放读锁

    // 5. 极致并发性能优化：thread_local 批处理累加
    // 避免 100 个线程高频 fetch_add 同一个全局原子变量导致 CPU L1/L2 缓存行失效
    thread_local int sample_counter = 0;
    if (++sample_counter >= 100) {
        if (counter_ptr) {
            // 每满 100 次本地请求，才向全局物理节点计数器同步一次（松散内存序减小开销）
            counter_ptr->fetch_add(100, std::memory_order_relaxed);
        }
        m_total_requests.fetch_add(100, std::memory_order_relaxed);
        sample_counter = 0; // 重置本地计数器
    }

    return node;
}

// 物理节点全量更新接口（例如 ZK 监听到节点变化时调用）
void ConsistentHash::UpdateNodes(const std::vector<std::string>& nodes) {
    // 1. 加独占锁（写锁），此时任何读线程都必须等待更新完成，保证强一致性
    std::lock_guard<std::shared_timed_mutex> lock(m_rw_mtx); 

    // 2. 清空旧的数据结构
    m_keys.clear();
    m_ring.clear();
    m_node_replicas.clear();
    m_node_counts.clear();
    m_total_requests.store(0);

    // 3. 重新将新节点加入哈希环
    for (size_t i = 0; i < nodes.size(); ++i) {
        if (!nodes[i].empty()) {
            add_node_internal(nodes[i], m_config.replicas);
        }
    }

    // 4. 重新对虚拟节点哈希值进行升序排序，维持哈希环结构
    std::sort(m_keys.begin(), m_keys.end());
}
```

## <font style="color:rgb(51, 51, 51);">连接池类KrpcConnectPool</font>

* **<font style="color:rgb(51, 51, 51);">核心作用</font>**<font style="color:rgb(51, 51, 51);">：在高并发下，如果每次调用 RPC 都新建 TCP 连接，调用完就关闭，会导致大量的 </font>**<font style="color:rgb(51, 51, 51);">TIME\_WAIT</font>**<font style="color:rgb(51, 51, 51);"> 状态 socket，导致系统端口耗尽、延迟极高。连接池为每一个服务提供者节点维护一个套接字队列（ConnectionBucket）。客户端调用时从池中借出空闲的 socket，用完归还，实现 TCP 长连接复用。</font>

<font style="color:rgb(51, 51, 51);">.h</font>

```cpp
#ifndef KRPC_CONNECT_POOL_H
#define KRPC_CONNECT_POOL_H

#include <string>
#include <unordered_map>
#include <queue>
#include <shared_mutex>
#include <condition_variable>
#include <atomic>
#include <sys/socket.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <mutex>   

// 连接桶：每一个具体的 "IP:Port" 端点独占一个 bucket
struct ConnectionBucket
{
std::queue<int> free_fds;      // 存放该服务节点空闲的 socket fd 队列
std::mutex mtx;                // 保护当前桶内部 free_fds 队列的互斥锁
std::condition_variable cv;    // 条件变量，当连接达到上限、线程等待空闲连接时使用
std::atomic<int> active_count; // 已经为该节点创建的所有活动 TCP 连接总数

ConnectionBucket() : active_count(0) {}
};

class KrpcConnectPool
{
public:
// 获取连接池单例
static KrpcConnectPool &GetInstance();

// 借用连接：如果对应节点的 bucket 中有空闲连接则直接返回，否则新建；若达到上限则阻塞等待
int BorrowConnection(const std::string &ip, uint16_t port);

// 归还连接：使用完毕后必须归还。如果连接已损坏 (is_bad = true)，则直接关闭并扣减 active_count
void ReturnConnection(const std::string &ip, uint16_t port, int fd, bool is_bad = false);

private:
KrpcConnectPool();
~KrpcConnectPool();

int m_max_conn_per_node;                             // 每个服务节点允许的最大 TCP 连接上限
std::unordered_map<std::string, ConnectionBucket *> m_pools; // 映射： "IP:Port" -> 该节点的连接桶
std::mutex m_global_mtx;                             // 保护 m_pools 节点映射表创建时的全局互斥锁
};

#endif
```

<font style="color:rgb(51, 51, 51);">.cc</font>

```cpp
#include "KrpcConnectPool.h"
#include <chrono>
#include <netinet/tcp.h> // 引入 TCP_NODELAY 相关的系统宏定义

static int ConnectCount = 1024; // 每个服务节点的最大长连接数设定为 1024

KrpcConnectPool::KrpcConnectPool() : m_max_conn_per_node(ConnectCount) {}

// 借用连接
int KrpcConnectPool::BorrowConnection(const std::string &ip, uint16_t port)
{
    std::string key = ip + ":" + std::to_string(port);

    ConnectionBucket *bucket = nullptr;
    {
        // 1. 查询全局 map 找到对应的 bucket。只在查找和创建 bucket 时加全局锁，粒度极小
        std::lock_guard<std::mutex> lock(m_global_mtx);
        if (m_pools.find(key) == m_pools.end())
        {
            m_pools[key] = new ConnectionBucket();
        }
        bucket = m_pools[key];
    }

    // 2. 对当前节点的 bucket 加锁
    std::unique_lock<std::mutex> lock(bucket->mtx);

    // 情况 A：如果有现成空闲长连接，直接出队返回，性能最高
    if (!bucket->free_fds.empty())
    {
        int fd = bucket->free_fds.front();
        bucket->free_fds.pop();
        return fd;
    }

    // 情况 B：没有空闲连接，且当前创建的连接数还没达到 1024 上限，允许新建连接
    if (bucket->active_count < m_max_conn_per_node)
    {
        bucket->active_count++; // 预占位

        lock.unlock(); // 【关键设计】：在进行耗时的 connect 系统调用前必须解锁，避免阻塞其他线程
        int fd = socket(AF_INET, SOCK_STREAM, 0);

        // 【核心优化】：禁用 TCP Nagle 算法。小数据包不等待，直接发出，延迟大幅度降低
        int opt = 1;
        setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));

        struct sockaddr_in addr;
        addr.sin_family = AF_INET;
        addr.sin_port = htons(port);
        addr.sin_addr.s_addr = inet_addr(ip.c_str());

        // 发起同步阻塞 TCP 连接
        if (connect(fd, (struct sockaddr *)&addr, sizeof(addr)) == 0)
        {
            return fd; // 连接成功
        }
        else
        {
            close(fd); // 连接失败
            lock.lock();
            bucket->active_count--; // 回滚计数
            bucket->cv.notify_one(); 
            return -1;
        }
    }

    // 情况 C：连接已达上限（1024），线程阻塞挂起，等待其他线程 ReturnConnection 释放连接
    if (bucket->cv.wait_for(lock, std::chrono::milliseconds(1000), [&]
    { return !bucket->free_fds.empty(); }))
    {
        int fd = bucket->free_fds.front();
        bucket->free_fds.pop();
        return fd; // 在 1000 毫秒内等到了可用连接
    }
    return -1; // 等待超时，降级报错
}

// 归还连接
void KrpcConnectPool::ReturnConnection(const std::string &ip, uint16_t port, int fd, bool is_bad)
{
    std::string key = ip + ":" + std::to_string(port);

    ConnectionBucket *bucket = nullptr;
    {
        std::lock_guard<std::mutex> lock(m_global_mtx);
        auto it = m_pools.find(key);
        if (it != m_pools.end()) bucket = it->second;
    }

    if (!bucket)
    {
        close(fd);
        return;
    }

    std::lock_guard<std::mutex> lock(bucket->mtx);
    // 如果通信过程中发生过网络断开、对端关闭等异常 (is_bad = true)
    if (is_bad)
    {
        close(fd);              // 彻底关闭不可用的 socket 资源
        bucket->active_count--; // 活动连接数扣减，允许后续重新建立新连接
    }
    else
    {
        bucket->free_fds.push(fd); // 依旧健康的长连接，放回桶队列中备用
    }
    bucket->cv.notify_one(); // 唤醒可能正在等待连接的 Borrow 线程
}
```

# <font style="color:rgb(51, 51, 51);">KrpcClosure辅助类</font>

<font style="color:rgb(51, 51, 51);">KrpcClosure 定义于 src/Krpcprovider.cc 头部。在 Protobuf 的 RPC 架构中，当服务提供者（Callee）执行完本地业务后，需要调用 done->Run() 来将结果发送回客户端。</font>

## <font style="color:rgb(51, 51, 51);">Krpcprovider.cc 内 KrpcClosure内容：</font>

```cpp
// 继承自 google::protobuf::Closure 抽象基类
class KrpcClosure : public google::protobuf::Closure
{
public:
// 构造函数：接收一个 std::function 类型的回调函数（一般是 Lambda 表达式）并移动赋值给成员变量
explicit KrpcClosure(std::function<void()> cb) : cb_(std::move(cb)) {}

// 重写基类的纯虚函数 Run()。当调用 done->Run() 时，会执行此函数
void Run() override
{
    cb_();       // 执行我们传入的 Lambda 表达式，内部会调用 SendRpcResponse 并清理连接
    delete this; // 关键：根据 Protobuf Closure 的生命周期规范，执行完毕后必须自我销毁，防止内存泄漏
}

private:
std::function<void()> cb_; // 存储回调逻辑
};
```

```cpp
});
```
