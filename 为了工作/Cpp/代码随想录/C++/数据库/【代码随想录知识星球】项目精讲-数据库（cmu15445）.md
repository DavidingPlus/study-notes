## 项目难点
1. 并发的B+树如何检查器是否正确?
    1. 记录`log`和表征`B+树`结构的符合, 从日志中尽显比对
2. `B+树`的锁是否会造成性能影响? 尤其是根节点, 所有的增删改查都会获取根节点的锁?
    1. 改用悲观锁和乐观锁的实现方案, 假设不会有锁冲突, 发现冲突时采用悲观锁的方案重新执行
3. `B+树`中如何避免死锁?
    1. 严格采用`螃蟹锁`的枷锁方案, 从上到下依次获取锁, 当方向固定时就避免了循环等待造成的死锁
4. 如何对大量的连表查询进行优化
    1. 本项目的优化较为简单, 就是不断地将查询条件下推, 尽量保证连表的记录数量少
5. `Join`的速度慢, 如何优化?
    1. `Lab3`中的`Join`只要求实现`NestedLoopJoin`, 但可以自己实现一个哈希查询`HashJoin`, 伪代码实现如下:

```latex
- Hash Join 实现:

函数 HashJoin(T1, T2, col):
// 创建一个哈希表
HashTable = {}

// 构建阶段: 遍历较小或者能够放入内存的表T1
对于 每个记录r1 in T1:
   // 使用公共列col作为键插入到哈希表
   如果 r1.col 不在 HashTable 中:
      HashTable[r1.col] = []
   HashTable[r1.col].append(r1)

// 探索阶段: 遍历另一个表T2
结果集 Result = []
对于 每个记录r2 in T2:
   // 查找匹配项
   如果 r2.col 在 HashTable 中:
      对于 每个记录r1 in HashTable[r2.col]:
            // 将匹配的记录组合成一个新的结果记录
            新记录 = CombineRecords(r1, r2)
            Result.append(新记录)

返回 Result

函数 CombineRecords(r1, r2):
// 创建一个新的记录，包含r1和r2中所有非重复的列
新记录 = {}
新记录.update(r1) // 添加来自r1的所有列
新记录.update(r2) // 添加来自r2的所有列，覆盖任何重复的列
返回 新记录
```

## 相关面试问题
1. 介绍一下项目
    1. 参照简历写法即可
2. ⭐ lruK 怎么实现？和lru比有什么区别？好在哪里？
    - `LRU-K` 实现上需要维护一个访问历史记录，通常是一个固定长度的队列或位向量，以记录最近`K`次访问的情况。相比`LRU`，它在淘汰时不仅考虑最后一次访问的时间，还会考虑最近一段时间内的访问频次。这样可以更好地适应非均匀访问模式。
    - `LRU-K` 的好处在于它更加灵活，能够适应更多类型的访问模式。
3. ⭐ 讲讲可扩展哈希？
    - 可扩展哈希是一种动态哈希方法，它允许随着数据的增长而动态扩展哈希表，同时尽量减少重新哈希的成本。它通过分级哈希目录来支持数据的增加和删除，从而实现高效的哈希表扩展。
4. ⭐ 操作系统已经有 page cache 为什么还要自己做缓存池。
    - 操作系统的`page cache`主要用于缓存文件系统的读写操作，而数据库自建缓存池是为了优化特定数据访问模式，提供更细粒度的缓存管理，降低延迟。
5. ⭐ 数据库为什么要用 buffer pool，不用 mmap 管理内存（注意和2区分）。
    - `buffer pool` 是数据库系统中用于缓存数据页的内存区域，它提供了高级别的抽象，如事务隔离、脏页管理等。`mmap` 则是操作系统提供的内存映射文件功能，直接映射文件到内存，不提供数据库所需的高级特性。
6. ⭐ 为什么要用 B+ 树？ B+ 树和 B 树区别在哪？ 哪个层级更高？
    - `B+树` 主要用于外部存储索引，所
7. ⭐ B+ 树并发管理如何做？悲观怎么做？乐观呢？有什么区别？适用什么场景  
   有数据都存储在叶子节点，便于范围查询；而 `B 树` 的数据存储在所有节点中。`B+树` 更适合数据库索引，因为它优化了范围查询和扫描性能。
    - `B+树` 的并发管理可以通过加锁机制实现，悲观锁会在操作前锁定节点，确保一致性；乐观锁则尝试操作后检查冲突。悲观锁适用于写操作频繁的场景，乐观锁适用于读多写少的场景。
8. 火山模型是什么？为什么要用火山模型或者说它的优缺点？
    - 火山模型是一种数据库查询执行模型，它支持流式输出结果，并且可以方便地实现迭代操作。优点是易于实现并行处理，缺点是可能需要额外的内存开销。
9. 除了火山模型还了解什么？有什么区别？
    - 除了火山模型，还有传统的管道-过滤器模型。火山模型更侧重于迭代和流式处理，而传统模型更侧重于批处理。
10. 用火山模型一次一次吐出多个 tuple 和向量化模型有什么区别？
    - 向量化模型强调一次处理多个元组，以利用现代CPU的SIMD指令集提高性能。火山模型则是逐个元组处理。
11. nested loop join 具体怎么做。与hash join 的区别。什么时候用 hash join 什么时候 用 nested loop join ?
    - `nested loop join` 适用于小表和索引扫描，直接在一个表上遍历另一个表；`hash join` 则适用于大表，先构建哈希表再查找。`hash join` 在处理大规模数据时通常更高效。
12. 讲一讲优化器?
    - 查询优化器负责选择最佳的查询执行计划，包括访问路径、连接顺序等，以最小化资源消耗。
13. 规则优化如何避免 overhead? （就是优化本身比执行开销大）
    - 优化器通过成本模型估算不同执行路径的开销，避免过于复杂的优化规则导致的性能损失。
14. 优化器如何避免不必要的路径
    - 优化器通过成本估算和统计信息来排除那些成本过高的执行计划。
15. 怎么实现基于代价优化？为什么交换表的顺序就能达到优化效果。
    - 基于代价优化通过评估各种执行计划的成本，同时会利用数据库表的统计信息, 选择最优方案。交换表顺序可以减少扫描量或利用索引。
16. 事务并发控制如何做？锁的类型有哪几种？不同隔离级别如何实现？
    - 事务并发控制通过锁机制保证数据的一致性和隔离性。锁类型包括共享锁、排他锁等。不同隔离级别通过锁的粒度和持续时间来实现。
17. 两阶段锁流程
    - 两阶段锁分为获取锁阶段和释放锁阶段，确保事务的原子性和一致性。
18. 加锁解锁流程
    - 加锁流程涉及请求锁、等待锁、获得锁；解锁流程则是在事务提交或回滚后释放所有持有的锁。
19. 怎么检测死锁，死锁依赖关系怎么建立的
    - 死锁检测通过分析锁等待图来发现循环等待的情况。一旦发现死锁，通常通过牺牲某个事务来解决。

### raft 相关
1. Raft 选举流程  
   Raft 的选举流程主要包括以下几个步骤：
    1. **超时触发**：如果一个 Follower 在超时时间内没有收到任何消息（心跳或日志条目），它将转变为 Candidate 状态。
    2. **投票请求**：Candidate 发送投票请求（RequestVote RPC）给集群中的所有节点，其中包括自己的任期号 Term。
    3. **投票响应**：如果接收者当前任期小于候选者的任期，并且它还没有投票给其他人，它会投票给候选者并发送投票确认（VoteGranted）。
    4. **胜出条件**：如果候选者获得多数票（N/2 + 1），它将变成 Leader 并发送心跳消息给所有节点。
    5. **任期更新**：如果候选者没有赢得选举，它会回到 Follower 状态，并等待下一个超时周期。
2. Raft 如何保证安全性，即只有一个 Leader  
Raft 通过要求候选者获得大多数节点的投票来确保任何时候最多只有一个 Leader。这是因为如果有两个候选者同时成为 Leader，它们都不能获得多数票，因此无法胜出。
3. Follower 投票后宕机了，起来后还会再投票吗？  
如果一个 Follower 在投票后宕机并在新的任期开始前恢复，它会忽略之前的投票，并在没有收到任何消息时再次转变为 Candidate 并发起新的选举。如果它在新的任期内收到了合法的心跳或投票请求，它会根据当前的任期号决定是否投票。
4. Raft 有哪些状态要持久化？为什么？  
Raft 需要持久化以下状态：

持久化这些状态的原因是为了在系统崩溃后能够正确恢复，并保持一致性。

    - 当前任期号（CurrentTerm）：用于识别任期内的投票。
    - 投票给谁（VotedFor）：记录在当前任期内投票给了哪个候选者。
    - 日志（Log）：存储所有的日志条目，包括客户端请求和任何其他元数据。
5. Raft Term ID 有什么用  
Term ID 用于标识一个任期，并帮助节点确定消息的有效性。每个任期都有一个唯一的 ID，并且任期号随时间递增。Term ID 有助于解决日志冲突、投票有效性等问题。
6. Raft 日志复制流程  
Leader 收到客户端请求后，将请求追加到自己的日志中，并广播给所有 Follower。Follower 验证日志条目的正确性，并回复给 Leader。Leader 等待大多数 Follower 确认后，将日志条目应用到状态机中。
7. Follower 收到日志冲突了怎么办  
如果 Follower 收到的日志与自己的日志存在冲突，Follower 会拒绝该日志条目，并告知 Leader 冲突的位置。Leader 会尝试通过截断自己的日志来解决冲突，并重新发送日志条目。
8. Leader 和 Follower 的日志 有一个 index 上的 日志 term 相同，那么之前的日志也是相同的吗？  
如果 Leader 和 Follower 的日志在某个 index 上的 term 相同，则之前的日志也是相同的。这是因为在 Raft 中，相同的 term 表示相同的操作。
9. 基于 Raft 的 KV 存储如何实现线性一致性  
线性一致性指的是任意两个操作之间的顺序关系，即使在系统故障期间也是如此。基于 Raft 的 KV 存储通过确保所有操作都在 Leader 上有序地执行，并且所有 Follower 保持一致的日志来实现线性一致性。
10. Raft 如何读  
      在 Raft 中，读取操作通常通过 Leader 进行。Leader 处理读请求，并从其本地状态机获取结果。
11. Raft 读优化  
      Raft 可以通过读取复制（Read Replication）来优化读性能，允许从 Follower 节点读取数据。此外，可以使用快照来减少日志的大小，提高读取速度。
12. Raft no-op 作用  
      no-op（No Operation）是 Raft 中的一个特殊日志条目，用于在没有客户端请求时保持 Leader 的活跃状态。它可以确保 Leader 定期发送心跳消息，维持集群的正常运作。
13. Raft 少数分区 Follower 不断发起选举自增 term，分区恢复后干扰 集群 怎么优化  
      为了避免少数分区的 Follower 影响整个集群，可以采取以下措施：
    - 增加选举超时时间的随机性，减少同时发起选举的概率。
    - 使用分区感知算法，如 Raft 分区恢复机制（如 Raft 的自动修复功能）。
14. 如何基于 Raft 实现一个分布式锁  
      基于 Raft 实现分布式锁的关键在于确保锁的分配和释放操作在集群中是一致的。可以设计一个简单的锁服务，该服务通过 Raft 协议在 Leader 上执行锁的获取和释放操作，并将这些操作的结果同步到其他节点。例如，客户端请求获取锁时，Leader 在日志中记录获取锁的请求，并广播给 Follower。只有当大多数节点确认后，客户端才能认为锁已被成功获取。释放锁的过程类似。这样可以确保锁的一致性和安全性。

### 数据库相关
1. ACID  
   ACID 是数据库事务处理的基本原则，它代表四个特性：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。
    - **原子性**：事务作为一个整体被执行，要么全部完成，要么全部不完成。如果事务的一部分失败，则整个事务都将回滚，确保数据的一致性。
    - **一致性**：事务开始前和结束后，数据库都必须处于一致的状态。这意味着事务只能从一个一致性的状态转换到另一个一致性的状态。
    - **隔离性**：每个事务独立运行，就好像没有其他事务在并发运行一样。不同的事务不会看到彼此未提交的变化。
    - **持久性**：一旦事务提交，它对数据库所做的更改就是永久的，即使系统崩溃也不会丢失这些更改。
2. 事务持久化  
   事务持久性通常是通过日志记录（Logging）来实现的。具体来说，数据库管理系统会在事务提交之前，将事务的所有更改写入到日志文件中。这种日志被称为重做日志（Redo Log）或事务日志（Transaction Log）。当事务提交时，日志会被标记为已提交，并且日志条目会立即写入到持久存储中。这样做的目的是为了确保在系统崩溃之后，可以通过重做日志恢复未写入主存储的数据，从而保证事务的持久性。常见的持久化机制还包括：
    - **检查点（Checkpoint）**：定期将缓冲池中的脏页（即已经被修改但尚未写入磁盘的页面）强制写入磁盘。
    - **恢复管理**：在系统故障后，通过分析日志文件来确定哪些事务已经成功提交（通过重做日志）以及哪些事务未能完成（通过撤销日志或undo log）。
3. 脏读、幻读、不可重复读

这些现象都是由于事务的隔离性不足导致的。不同的隔离级别（Read Uncommitted、Read Committed、Repeatable Read、Serializable）提供了不同程度的保护措施来防止这些问题的发生。较高的隔离级别可以更好地防止脏读、不可重复读和幻读，但也可能导致更高的锁竞争和资源消耗。

    - **脏读**（Dirty Read）：一个事务读取了另一个事务未提交的数据。如果第二个事务最终回滚，则第一个事务读取的数据是无效的，这种情况称为脏读。
    - **不可重复读**（Non-repeatable Read）：一个事务多次读取同一数据，在两次读取之间，另一个事务修改了该数据。因此，第一次读取和第二次读取的结果不同。
    - **幻读**（Phantom Read）：一个事务在两次相同的查询之间，另一个事务插入了一些新的行。因此，第一次查询和第二次查询的结果集不一样，产生了“幻影”行。

## 拓展&&可以深挖的点
### 为什么现在更多的`KV`数据库采用`LSM Tree`而抛弃了`B+树`?
尽管 `B+树` 在许多方面表现良好，特别是在范围查询和随机读取方面，但在写密集型的工作负载下，尤其是对于大规模数据存储而言，`LSM Tree`（Log-Structured Merge Tree）提供了一些关键的优势，使其更适合某些应用场景。以下是一些原因：

1. **写放大问题**：
    - **B+树**：每次写入操作都需要修改或重建树的内部节点，这会导致较高的磁盘写入放大，尤其是在固态硬盘（SSD）上，频繁的写入操作会加速设备的磨损。
    - **LSM Tree**：写入操作只需要追加到内存中的内存表（MemTable）中，然后再批量写入磁盘上的SSTable（Sorted String Table）。这种方式减少了写放大，延长了存储设备的寿命。
2. **写入性能**：
    - **B+树**：每次写入都需要对磁盘进行随机写入，这在高写入负载下会导致性能下降。
    - **LSM Tree**：由于采用了追加写的方式，写入操作主要表现为顺序写入，这在SSD和HDD上都能获得更好的性能。
3. **合并和压缩**：
    - **B+树**：没有合并或压缩的概念，树的高度随着数据量的增长而增长。
    - **LSM Tree**：通过后台的合并（Compaction）过程，可以将多个SSTable合并成一个更大的文件，从而减少文件的数量，优化读取性能，并清理掉已经被删除的数据。
4. **读取性能**：
    - **B+树**：适合范围查询，因为所有的数据都连续存储在磁盘上。
    - **LSM Tree**：读取时需要查找内存中的MemTable以及多个磁盘上的SSTable，这可能会影响单个查询的性能。但是，通过缓存机制和索引优化，可以缓解这一问题。
5. **空间利用率**：
    - **B+树**：空间利用率较高，因为数据是紧密排列的。
    - **LSM Tree**：在合并过程中可能会出现一定的空间浪费，但通过合理的合并策略可以控制这种浪费。
6. **可扩展性**：
    - **B+树**：扩展性较差，特别是对于分布式系统，难以实现水平扩展。
    - **LSM Tree**：更容易实现水平扩展，因为可以将数据分片存储在不同的节点上，并且合并操作可以在后台并行进行。
7. **故障恢复**：
    - **B+树**：故障恢复可能需要重构整个树。
    - **LSM Tree**：由于数据是以追加的方式写入的，故障恢复相对简单，只需要重新加载内存表和磁盘上的SSTable即可。

因此, `LSM Tree` 在写密集型工作负载下的优势，特别是在大规模数据存储和处理场景中，使得许多 `KV` 数据库选择了 `LSM Tree` 而不是 `B+树`。
