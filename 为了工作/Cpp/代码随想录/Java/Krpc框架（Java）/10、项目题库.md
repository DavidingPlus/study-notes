## <font style="color:rgb(47, 48, 52);">1.netty传输位于网络结构模型中的哪一层？</font>
<font style="color:rgb(47, 48, 52);">传输层</font>

+ <font style="color:rgb(47, 48, 52);">Netty支持TCP和UDP等传输层协议，通过对这些协议的封装和抽象，Netty能够处理传输层的数据传输任务，如建立连接、数据传输和连接关闭等。</font>
+ <font style="color:rgb(47, 48, 52);">Netty的EventLoop和EventLoopGroup等组件基于Java NIO的多路复用器（Selector），实现了高效的IO事件处理机制，这在一定程度上与传输层的数据传输和事件处理机制相呼应。</font>

<font style="color:rgb(47, 48, 52);">应用层</font>

+ <font style="color:rgb(47, 48, 52);">Netty提供了丰富的协议支持，如HTTP、WebSocket、SSL、Protobuf等，这些协议主要工作在应用层。Netty通过编解码器等组件，能够方便地在应用层对数据进行编解码，从而实现与应用层协议的交互。</font>
+ <font style="color:rgb(47, 48, 52);">Netty的ChannelPipeline和ChannelHandler等组件构成了一个灵活的事件处理链，允许开发者在应用层自定义各种事件处理逻辑，如身份验证、消息加密、业务逻辑处理等。</font>

## <font style="color:rgb(47, 48, 52);">2.讲一讲netty在你项目中的作用和执行流程？</font>
**<font style="color:rgb(47, 48, 52);">作用</font>**<font style="color:rgb(47, 48, 52);">：引用高性能网络框架netty，实现了高效的信息传输；抽象了Java NIO底层的复杂性，提供了简单易用的API，简化了网络编程；提供各种组件方便网络数据的处理</font>

**<font style="color:rgb(47, 48, 52);">执行流程：</font>**

<font style="color:rgb(47, 48, 52);">1. 客户端发起请求</font>

+ <font style="color:rgb(47, 48, 52);">客户端根据服务地址通过Netty客户端API创建一个客户端Channel，并连接到服务端的指定端口。</font>
+ <font style="color:rgb(47, 48, 52);">客户端将RPC调用信息（如方法名、参数等）封装成请求消息，并通过Netty的编码器（Encoder）将请求消息序列化成字节流。</font>
+ <font style="color:rgb(47, 48, 52);">客户端将序列化后的字节流通过网络发送给服务端。</font>

<font style="color:rgb(47, 48, 52);">2. 服务端接收请求并处理</font>

+ <font style="color:rgb(47, 48, 52);">服务端通过Netty服务端API监听指定端口，等待客户端的连接请求。</font>
+ <font style="color:rgb(47, 48, 52);">当接收到客户端的连接请求时，服务端通过Netty的解码器（Decoder）将接收到的字节流反序列化成请求消息。</font>
+ <font style="color:rgb(47, 48, 52);">服务端根据请求消息中的方法名和参数等信息，通过反射调用本地服务实现，并将执行结果封装成响应消息。</font>
+ <font style="color:rgb(47, 48, 52);">服务端通过Netty的编码器将响应消息序列化成字节流，并通过网络发送给客户端。</font>

<font style="color:rgb(47, 48, 52);">3. 客户端接收响应</font>

+ <font style="color:rgb(47, 48, 52);">客户端接收到服务端的响应字节流后，通过Netty的解码器将字节流反序列化成响应消息。</font>
+ <font style="color:rgb(47, 48, 52);">客户端根据响应消息中的结果信息，进行相应的业务处理。</font>

## <font style="color:rgb(47, 48, 52);">3.为什么会出现沾包问题？如何解决的？</font>
<font style="color:rgb(47, 48, 52);">	</font><font style="color:rgb(47, 48, 52);">netty默认底层通过TCP 进行传输，TCP</font>**<font style="color:rgb(47, 48, 52);">是面向流的协议</font>**<font style="color:rgb(47, 48, 52);">，接收方在接收到数据时无法直接得知一条消息的具体字节数，不知道数据的界限。由于TCP的流量控制机制，发生沾包或拆包，会导致接收的一个包可能会有多条消息或者不足一条消息，从而会出现接收方少读或者多读导致消息不能读完全的情况发生</font>

<font style="color:rgb(47, 48, 52);">	在发送消息时，先告诉接收方消息的长度，让接收方读取指定长度的字节，就能避免这个问题；项目中通过自定义的消息传输协议来实现对沾包问题的解决。</font>

<font style="color:rgb(47, 48, 52);">①服务注册与发现：注册中心实现了微服务架构中各个微服务的服务注册与发现，这是其最基础也是最重要的功能。通过注册中心，各个微服务可以将自己的地址信息（如IP地址、端口号等）注册到中心，同时也能够从中发现其他微服务的地址信息。</font>

<font style="color:rgb(47, 48, 52);">③增强微服务之间的去中心化在单体项目中，模块之间的依赖关系是通过内部的直接引用来实现的。而在微服务架构中，注册中心的存在使得微服务之间的依赖关系不再是直接的函数引用，而是通过注册中心来间接调用。这种方式增强了微服务之间的去中心化，提高了系统的灵活性和可扩展性。</font>

<font style="color:rgb(47, 48, 52);">④提升系统的可用性和容错性注册中心通常具有高可用性的设计，能够确保在部分节点故障时仍然能够正常工作。这使得整个微服务架构在面临故障时能够更加稳定地运行。</font>

## <font style="color:rgb(47, 48, 52);">1.三种负载均衡算法的比较？</font>
### <font style="color:rgb(47, 48, 52);">轮询法（Round Robin）</font>
**<font style="color:rgb(47, 48, 52);">原理</font>**<font style="color:rgb(47, 48, 52);">：轮询法将所有请求按顺序轮流分配给后端服务器，依次循环。</font>

**<font style="color:rgb(47, 48, 52);">优点</font>**

+ <font style="color:rgb(47, 48, 52);">简单易实现。</font>
+ <font style="color:rgb(47, 48, 52);">无状态，不保存任何信息，因此实现成本低。</font>

**<font style="color:rgb(47, 48, 52);">缺点</font>**

+ <font style="color:rgb(47, 48, 52);">当后端服务器性能差异大时，无法根据服务器的负载情况进行动态调整，可能导致某些服务器负载过大或过小。</font>

<font style="color:rgb(47, 48, 52);">如果服务器配置不一样，不适合使用轮询法。</font>

### <font style="color:rgb(47, 48, 52);">随机法（Random）</font>
**<font style="color:rgb(47, 48, 52);">原理</font>**<font style="color:rgb(47, 48, 52);">：随机法将请求随机分配到各个服务器。</font>

**<font style="color:rgb(47, 48, 52);">优点</font>**

+ <font style="color:rgb(47, 48, 52);">分配较为均匀，避免了轮询法可能出现的连续请求分配给同一台服务器的问题。</font>
+ <font style="color:rgb(47, 48, 52);">使用简单，不需要复杂的配置。</font>

**<font style="color:rgb(47, 48, 52);">缺点</font>**

+ <font style="color:rgb(47, 48, 52);">随机性可能导致某些服务器被频繁访问，而另一些服务器则相对较少，这取决于随机数的生成情况。</font>
+ <font style="color:rgb(47, 48, 52);">如果服务器配置不同，随机法可能导致负载不均衡，影响整体性能。</font>

### <font style="color:rgb(47, 48, 52);">一致性哈希法（Consistent Hashing）</font>
**<font style="color:rgb(47, 48, 52);">原理</font>**<font style="color:rgb(47, 48, 52);">：一致性哈希法将输入（如客户端IP地址）通过哈希函数映射到一个固定大小的环形空间（哈希环）上，每个服务器也映射到这个哈希环上。客户端的请求会根据哈希值在哈希环上顺时针查找，遇到的第一个服务器就是该请求的目标服务器。</font>

**<font style="color:rgb(47, 48, 52);">优点</font>**

+ <font style="color:rgb(47, 48, 52);">当服务器数量发生变化时，只有少数键需要被重新映射到新的服务器上，这大大减少了缓存失效的数量，提高了系统的可用性。</font>
+ <font style="color:rgb(47, 48, 52);">具有良好的可扩展性，可以动态地添加或删除服务器。</font>

**<font style="color:rgb(47, 48, 52);">缺点</font>**

+ <font style="color:rgb(47, 48, 52);">在哈希环偏斜的情况下，大部分的缓存对象很有可能会缓存到一台服务器上，导致缓存分布极度不均匀。</font>
+ <font style="color:rgb(47, 48, 52);">实现较为复杂，需要引入虚拟节点等技术来解决哈希偏斜问题。</font>

## <font style="color:rgb(47, 48, 52);">4.令牌桶算法如何实现的？</font>
**<font style="color:rgb(47, 48, 52);">令牌桶算法简介</font>**<font style="color:rgb(47, 48, 52);">：令牌桶是指一个限流容器，容器有最大容量，每秒或每100ms产生一个令牌（具体取决于机器每秒处理的请求数），当容量中令牌数量达到最大容量时，令牌数量也不会改变了，只有当有请求过来时，使得令牌数量减少（只有获取到令牌的请求才会执行业务逻辑），才会不断生成令牌</font>

**<font style="color:rgb(47, 48, 52);">令牌桶算法限流范围：</font>**<font style="color:rgb(47, 48, 52);">假设令牌桶最大容量为n，每秒产生r个令牌</font>

<font style="color:rgb(47, 48, 52);">平均速率：则随着时间推延，处理请求的平均速率越来越趋近于每秒处理r个请求，说明令牌桶算法可以控制平均速率</font>

<font style="color:rgb(47, 48, 52);">瞬时速率：如果在一瞬间有很多请求进来，此时来不及产生令牌，则在一瞬间最多只有n个请求能获取到令牌执行业务逻辑，所以令牌桶算法也可以控制瞬时速率</font>

## 5.LRU适合作为负载均衡的一个实现吗？
<font style="color:rgb(55, 65, 81);">不适合。</font>

<font style="color:rgb(55, 65, 81);">LRU的思想可以被借鉴用于负载均衡。例如可以设计一个基于请求历史的负载均衡算法，其中每个服务器都有一个“最近访问时间戳”，当新的请求到来时，可以选择“最久未被请求”的服务器进行处理。但这种做法通常不是最优的，因为它没有考虑到服务器的当前负载，并且还可能会出现 </font>**部分某个时间被大量访问的节点之后无法再访问到**<font style="color:rgb(55, 65, 81);">的问题。</font>

<font style="color:rgb(55, 65, 81);">但是我们可以在项目描述中加入LRU这个实现，因为LRU是</font>**热门**<font style="color:rgb(55, 65, 81);">的算法题之一，</font>

<font style="color:rgb(55, 65, 81);">写到其中，会</font>**引导**<font style="color:rgb(55, 65, 81);">面试官问你，LRU的实现 or 与其它算法的优缺点比较</font>

# <font style="color:rgb(51, 51, 51);">各种场景题</font>
<font style="color:rgb(47, 48, 52);">这方面一般是围绕着降级熔断重试 等等问题来回答，主要考察项目是否是自己做出来的，是否有对项目有过思考</font>

<font style="color:rgb(47, 48, 52);">举几个例子，比如：</font>

**<font style="color:rgb(47, 48, 52);">2.某个服务多个节点承压能力不一，怎么办？</font>**

**<font style="color:rgb(47, 48, 52);">3.每个服务都进行重试吗？</font>**

**<font style="color:rgb(47, 48, 52);">4.网络抖动导致某个节点被下线了，过一会网络好了，考虑过这个问题吗？</font>**

<font style="color:rgb(47, 48, 52);">这方面一般是围绕着降级熔断重试 等等问题来回答，主要考察项目是否是自己做出来的，是否有对项目有过思考</font>

## <font style="color:rgb(47, 48, 52);">1.本地缓存怎么做的？能保证缓存和服务的一致性吗？</font>
<font style="color:rgb(47, 48, 52);">在客户端设计一个缓存层，每次调用服务时从缓存层中获取地址，避免直接调用注册中心，优化速度和资源</font>

<font style="color:rgb(47, 48, 52);">可以。这里使用了zookeeper的监听机制，在服务节点上注册Watcher，当注册中心的服务地址发生改动时，Watcher会异步通知客户端的缓存层修改对应的地址，从而实现两者的一致性</font>

## <font style="color:rgb(47, 48, 52);">2.某个服务多个节点承压能力不一，怎么办？</font>
<font style="color:rgb(47, 48, 52);">前面学习过一致性哈希算法 就会知道，在一致性哈希算法中，使用虚拟节点对真实节点进行映射，并且能通过设置虚拟节点的个数 来控制该节点接收到请求的概率。</font>

<font style="color:rgb(47, 48, 52);">所以在服务器负载能力不一致的情况下，我们可以在服务端将服务器的负载能力写入到注册中心中，客户端在进行负载均衡时会在注册中心中获取各服务器的能力，并设置对应的虚拟节点的数量，来控制流量的分发。</font>

<font style="color:rgb(47, 48, 52);">这里可以拓展一下自适应负载均衡的实现</font>

## <font style="color:rgb(47, 48, 52);">3.网络抖动导致某个节点被下线了，过一会网络好了，考虑过这个问题吗？</font>
<font style="color:rgb(47, 48, 52);">当调用端发起的请求失败时，RPC 框架自身可以进行重试，再重新发送请求，通过这种方式保证系统的容错率；项目使用Google Guava这款性能强大且轻量的框架来实现失败重试的功能；</font>

## <font style="color:rgb(47, 48, 52);">4.每个服务都进行重试吗？</font>
<font style="color:rgb(47, 48, 52);">如果这个服务业务逻辑不是幂等的，比如插入数据操作，那触发重试的话会不会引发问题呢？</font>

<font style="color:rgb(47, 48, 52);">会的。</font>

<font style="color:rgb(47, 48, 52);">在使用 RPC 框架的时候，要确保被调用的服务的业务逻辑是幂等的，这样才能考虑根据事件情况开启 RPC 框架的异常重试功能</font>

<font style="color:rgb(47, 48, 52);">所以，我们可以</font>**<font style="color:rgb(47, 48, 52);">设置一个白名单</font>**<font style="color:rgb(47, 48, 52);">，服务端在注册节点时，将幂等性的服务注册在白名单中，客户端在请求服务前，先去白名单中查看该服务是否为幂等服务，如果是的话使用重试框架进行调用</font>

<font style="color:rgb(47, 48, 52);">白名单存放在zookeeper中（充当配置中心的角色）</font>

## <font style="color:rgb(47, 48, 52);">5.如果下游有一个服务的所有服务器都宕机了，该怎么做避免失败请求的大量堆积</font>
<font style="color:rgb(47, 48, 52);">项目在客户端调用的链路头部设置了熔断器，当检测到失败次数超过阈值时，熔断器会变为关闭状态，阻止后续的请求；在一定时间后，熔断器变为半开状态，并根据之后请求的成功情况来决定是否阻止或放行请求</font>
