# 协议

## 为什么需要协议呢？

在 RPC 调用中，协议的作用就是让数据的含义能被双方一致理解。例如，我们传输 “Hello, RPC”，如果没有协议定义，接收方可能会理解成 “He，lloRPC”，信息就产生了偏差。协议在这里就像文章中的标点符号，让通信中的信息保持一致且清晰。

## 如何设计协议

为了避免在协议升级过程中引发兼容性问题，特别是当向协议头添加新的字段时，必须设计一种支持可扩展的协议结构。假设你设计了一个88位的协议头，其中32位用于表示协议长度。如果你在升级时为了加入新功能，在协议头的最后增加了2位字段，那么可能会导致向后兼容性问题。具体来说，升级后的应用会使用新协议发送请求，但未升级的应用会继续按旧协议格式解析请求。这样，未升级的应用会错误地将协议头最后2个bit作为协议体数据的前2个bit读取，从而丢失原协议体的最后2个bit，导致数据错误。

你可能会想将新参数放入不定长的协议体中，这样可以避免修改协议头。但问题在于，协议体中的数据通常是经过序列化的，若需要获取新增的参数值，必须先反序列化整个协议体。然而，在某些场景下，这样做的代价较高。例如，如果服务提供方收到一个过期请求，表示请求的时间超过了调用方发送请求的时间和配置的超时时间。为了判断请求是否超时，服务提供方需要从协议中获取超时时间参数。如果之前的协议体没有这个字段，那么将超时时间加入协议体后，就需要反序列化整个协议体来获取超时时间，这会增加CPU的负担。

因此，为了平滑地支持协议的扩展，我们需要设计一种可扩展的协议结构。关键在于确保协议头的可扩展性，即在协议头中为新增字段留出空间，使协议能够灵活扩展。为此，协议头的长度不能是定长的。为了能够正确读取不定长的协议头，我们依然需要在协议中有一个固定部分，用来存储协议头的长度。这样，我们的协议结构就可以分为三部分：固定部分、协议头部分和协议体部分。前两部分可以统称为“协议头”，而协议体部分则包含实际的业务数据。

这种设计能够保证在协议升级时，不会导致老版本和新版本之间的兼容性问题，同时避免了过度依赖反序列化所带来的性能损耗，确保协议在扩展时的高效性和兼容性。

![1734438011166-5f546aab-2cd6-41c4-b6d9-b352eaf6b8ac.png](./img/VTld-KFQjuZz4IOY/1734438011166-5f546aab-2cd6-41c4-b6d9-b352eaf6b8ac-240515.png)

设计一个简单的RPC协议并不复杂，真正具有挑战性的部分在于如何设计一个**可升级**的协议。一个好的RPC协议不仅需要在扩展新特性时保持向下兼容，还要尽可能减少资源消耗。因此，我们的协议结构不仅要支持协议体的扩展，还必须确保协议头也具备扩展性。这样，在协议升级时，既能保证与旧版本的兼容性，又能避免引入不必要的性能损耗。

上述设计方法来源于我的经验，实践证明，**做好扩展性**是至关重要的。只有通过精心设计的协议结构，我们才能在不断变化的需求中保持灵活性和高效性，避免踩入一些常见的陷阱。希望这个协议模板能帮助你在设计RPC协议时少走弯路，提升系统的可维护性和可扩展性。

# 序列化

序列化指的是将对象转换成一种可传输或存储的格式（例如二进制或文本），通常用于数据的持久化（存储到磁盘）或网络传输。在序列化过程中，对象的属性、数据结构被转换为字节流，方便在不同系统之间传递。

反序列化指的是 将字节流转换回对象的过程。接收到数据后，通过反序列化将二进制数据还原为原始对象。

## 有哪些常见的序列化

任何序列化框架的核心思想，就是设计一种序列化协议，将对象的类型、属性类型和属性值按固定格式依次写入二进制字节流中，从而完成序列化。反序列化时，通过相同的格式依次读取对象的类型、属性类型和属性值，再根据这些信息重建出一个新的对象。

### JDK 原生序列化

如果你学过 Java 语言，那么你一定知道 JDK 的原生序列化。下面是 JDK 序列化的例子。

```java
import java.io.*;

class Person implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public String toString() {
        return "Person{name='" + name + "', age=" + age + "}";
    }
}

public class SerializationExample {
    public static void main(String[] args) {
        Person person = new Person("Alice", 25);

        // 序列化对象到文件
        try (FileOutputStream fileOut = new FileOutputStream("person.ser");
             ObjectOutputStream out = new ObjectOutputStream(fileOut)) {
            out.writeObject(person); // 序列化对象
            System.out.println("Serialized data is saved in person.ser");
        } catch (IOException e) {
            e.printStackTrace();
        }

        // 反序列化对象从文件
        try (FileInputStream fileIn = new FileInputStream("person.ser");
             ObjectInputStream in = new ObjectInputStream(fileIn)) {
            Person deserializedPerson = (Person) in.readObject(); // 反序列化对象
            System.out.println("Deserialized Person: " + deserializedPerson);
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

```

### JSON

最常见的序列化格式，<font style="color:rgb(59, 67, 81);">JSON是典型的Key-Value方式。 JSON 是一种轻量级的、基于文本的数据格式，结构简单且具有良好的可读性。下面是 JSON 序列化的例子。</font>

```java
import com.fasterxml.jackson.databind.ObjectMapper;
import java.io.Serializable;

public class JsonExample {

    // 定义 Person 类
    static class Person implements Serializable {
        private static final long serialVersionUID = 1L;
        
        private String name;
        private int age;

        public Person() {}  // 无参构造函数用于反序列化

        public Person(String name, int age) {
            this.name = name;
            this.age = age;
        }

        public String getName() { return name; }
        public void setName(String name) { this.name = name; }
        public int getAge() { return age; }
        public void setAge(int age) { this.age = age; }

        @Override
        public String toString() {
            return "Person{name='" + name + "', age=" + age + "}";
        }
    }

    public static void main(String[] args) {
        try {
            ObjectMapper objectMapper = new ObjectMapper();
            Person person = new Person("Alice", 25);

            // 序列化：对象转为 JSON 字符串
            String jsonString = objectMapper.writeValueAsString(person);
            System.out.println("Serialized JSON: " + jsonString);

            // 反序列化：JSON 字符串转为对象
            Person deserializedPerson = objectMapper.readValue(jsonString, Person.class);
            System.out.println("Deserialized Person: " + deserializedPerson);
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}

```

因此，在选择 JSON 作为 RPC 框架的序列化方式时，服务提供者和服务调用者之间传输的数据量应尽可能小，否则会对性能产生较大影响。

### <font style="color:rgb(59, 67, 81);">Hessian</font>

Hessian 是一种高效的二进制序列化协议，适用于 Java 等语言的分布式系统通信，尤其是在高性能 RPC 框架中广泛使用（如 Dubbo）。它由 Caucho Technology 开发，设计目标是跨语言的轻量、高效和简洁。Hessian 的优势在于序列化后的数据量小，传输速度快，因此非常适合微服务之间的高效通信。  下面是 Hessian 的例子。

```java
import com.caucho.hessian.io.HessianInput;
import com.caucho.hessian.io.HessianOutput;
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.Serializable;

public class HessianExample {

    // 定义可序列化的 Person 类
    static class Person implements Serializable {
        private String name;
        private int age;

        public Person() {}  // 无参构造函数用于反序列化

        public Person(String name, int age) {
            this.name = name;
            this.age = age;
        }

        public String getName() { return name; }
        public void setName(String name) { this.name = name; }
        public int getAge() { return age; }
        public void setAge(int age) { this.age = age; }

        @Override
        public String toString() {
            return "Person{name='" + name + "', age=" + age + "}";
        }
    }

    public static void main(String[] args) {
        Person person = new Person("Alice", 25);

        // 序列化：将对象转换为二进制数据
        byte[] serializedData = serialize(person);
        System.out.println("Serialized Data: " + serializedData);

        // 反序列化：将二进制数据转换为对象
        Person deserializedPerson = deserialize(serializedData);
        System.out.println("Deserialized Person: " + deserializedPerson);
    }

    // 序列化方法
    public static byte[] serialize(Person person) {
        try (ByteArrayOutputStream bos = new ByteArrayOutputStream();
             HessianOutput hessianOutput = new HessianOutput(bos)) {
            hessianOutput.writeObject(person);
            return bos.toByteArray();
        } catch (Exception e) {
            e.printStackTrace();
            return null;
        }
    }

    // 反序列化方法
    public static Person deserialize(byte[] data) {
        try (ByteArrayInputStream bis = new ByteArrayInputStream(data);
             HessianInput hessianInput = new HessianInput(bis)) {
            return (Person) hessianInput.readObject();
        } catch (Exception e) {
            e.printStackTrace();
            return null;
        }
    }
}

```

然而，Hessian 也存在一些问题：官方版本不支持 Java 中某些常见类型，例如 `LinkedHashMap` 和 `LinkedHashSet` 等 `Linked` 系列集合。同时，在反序列化 `Byte` 或 `Short` 类型时，数据会自动转换为 `Integer` 类型。

### <font style="color:rgb(59, 67, 81);">Protobuf</font>

**Protocol Buffers（Protobuf）** 是一种由 Google 开发的高效、语言中立、平台中立的序列化结构数据格式。它比 JSON 和 XML 更加高效，尤其在数据量较大时，Protobuf 能显著减少传输和存储的开销。

#### 如何在 Java 中使用 Protobuf

#### 1. 安装 Protobuf 编译器

首先，确保你已经安装了 Protobuf 编译器。如果还没有安装，可以参考 Protobuf 官方文档 安装。

#### 2. 定义 `.proto` 文件

首先，定义一个数据结构。创建一个 `person.proto` 文件，定义一个 `Person` 类：

```java
syntax = "proto3";

package example;

// 定义 Person 类
message Person {
  string name = 1;
  int32 age = 2;
  string email = 3;
}

```

* <code>**syntax = "proto3";**</code>：指定使用 Protobuf 3 语法。
* <code>**message Person { ... }**</code>：定义了一个 `Person` 消息，包含 `name`（字符串）、`age`（整数）和 `email`（字符串）三个字段。

#### 3. 编译 `.proto` 文件

使用 Protobuf 编译器将 `.proto` 文件编译为 Java 类。假设你已经安装了 Protobuf 编译器，运行以下命令：

```java
protoc --java_out=./src/main/java person.proto
```

#### 4. 使用 Protobuf 进行序列化和反序列化

接下来，你可以在 Java 代码中使用生成的 `Person` 类来进行序列化和反序列化。

```java
import example.Person;
import com.google.protobuf.InvalidProtocolBufferException;

import java.io.IOException;

public class ProtobufExample {
    public static void main(String[] args) {
        try {
            // 创建一个 Person 对象并设置数据
            Person person = Person.newBuilder()
                                  .setName("Alice")
                                  .setAge(25)
                                  .setEmail("alice@example.com")
                                  .build();

            // 序列化：将 Person 对象转为字节数组
            byte[] serializedData = person.toByteArray();
            System.out.println("Serialized Data: " + new String(serializedData));

            // 反序列化：将字节数组恢复为 Person 对象
            Person deserializedPerson = Person.parseFrom(serializedData);
            System.out.println("Deserialized Person: " + deserializedPerson);
        } catch (InvalidProtocolBufferException e) {
            e.printStackTrace();
        }
    }
}

```

<font style="color:rgb(59, 67, 81);">Protobuf 非常高效，但是对于具有反射和动态能力的语言来说，这样用起来很费劲，这一点就不如Hessian。</font>

# 动态代理

提到这个词你可能会比较熟悉，什么是动态代理？举个简单的例子，当我们想使用 RPC 的时候，我们一般是找提供方找接口，我们用<font style="color:rgb(59, 67, 81);">Maven 将依赖注入到项目中就可以了，在后面直接调用接口的方法。接口里不会包含业务逻辑，业务逻辑都在服务提供方的应用中。</font>

<font style="color:rgb(59, 67, 81);">官方点说， 动态代理是面向对象编程中的一种设计模式，它允许在运行时动态地创建代理类，用来代替真实对象执行任务。简单来说，动态代理是“为已有对象提供替代品”，代理类能够拦截方法调用并在其前后插入自定义的逻辑。通过这种方式，开发者可以在不修改原始对象的情况下增强对象的功能，常用于日志记录、安全控制、性能监控等场景。</font>

## <font style="color:rgb(59, 67, 81);">说到动态代理你可能会想到有没有静态代理？ </font>

<font style="color:rgb(59, 67, 81);">静态代理是在编译时生成的代理类，它在代码编写时就已经确定了代理对象，而动态代理则是在</font>**<font style="color:rgb(59, 67, 81);">运行时生成代理类</font>**<font style="color:rgb(59, 67, 81);">。动态代理的一个主要优势是更灵活，因为它可以在运行时根据实际需求创建代理类，而不需要事先写好所有的代理代码。例如，如果你有多个实现类，静态代理需要为每个实现类创建一个代理类，而动态代理只需要一个通用的代理类，就可以代理所有实现了接口的类。</font>

在选择动态代理框架时，我们可以从以下三个角度进行考量：

1. **代理类的生成性能**：因为代理类是在运行时生成的，所以生成速度、字节码的大小都会影响系统的整体性能。代理类生成的速度越快、字节码越小，所占用的系统资源也会更少，这对于高并发应用尤为关键。
2. **代理类的执行效率**：代理类的主要作用是对接口方法进行请求拦截，每次调用接口方法时，都会执行代理逻辑，因此生成的代理类的执行效率必须足够高，以避免成为性能瓶颈。
3. **框架的易用性**：从使用角度来看，选择一个易用的代理框架能大大提高开发效率。可以考虑框架的 API 设计是否易于理解，社区的活跃度如何，依赖是否复杂等因素，以便于后续的维护和扩展。

## 常见的动态代理框架

### JDK 动态代理

JDK 动态代理使用 Java 自带的 `java.lang.reflect.Proxy` 类和 `InvocationHandler` 接口生成代理对象。它要求被代理的对象必须实现一个或多个接口。

**适用场景**：

* 适用于接口驱动的 RPC 场景。
* 被代理的服务接口明确且稳定，且不需要代理具体的类（只代理接口）。

**优缺点**：

* **优点**：JDK 自带，无需引入额外依赖；生成的代理类较轻量，效率较高。
* **缺点**：只能代理实现了接口的类，无法代理普通类；在性能上不如字节码操作的代理（如 CGLIB）。

```java
/*假设有一个 `UserService` 接口和其实现类 `UserServiceImpl`，
我们通过动态代理给 `UserService` 添加日志功能：*/
import java.lang.reflect.*;

public interface UserService {
    void addUser(String name);
    void removeUser(String name);
}

public class UserServiceImpl implements UserService {
    public void addUser(String name) {
        System.out.println("User " + name + " added.");
    }

    public void removeUser(String name) {
        System.out.println("User " + name + " removed.");
    }
}

public class LogInvocationHandler implements InvocationHandler {
    private final Object target;

    public LogInvocationHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("Logging: " + method.getName() + " method called.");
        return method.invoke(target, args);
    }
}

public class Main {
    public static void main(String[] args) {
        UserService userService = new UserServiceImpl();
        UserService proxy = (UserService) Proxy.newProxyInstance(
            UserService.class.getClassLoader(),
            new Class<?>[] { UserService.class },
            new LogInvocationHandler(userService)
        );

        proxy.addUser("Alice");
        proxy.removeUser("Alice");
    }
}

```

### CGLIB 动态代理

CGLIB（Code Generation Library）基于 ASM 库，通过在运行时生成目标类的子类来创建代理，因此不需要接口，能代理任何类。

**适用场景**：

* 适用于类驱动的 RPC 场景，尤其是需要代理没有接口的类。
* 被代理类不便或不能实现接口，或需要代理大量的类。

**优缺点**：

* **优点**：可以代理没有接口的普通类；对于代理普通类的场景，性能优于 JDK 动态代理。
* **缺点**：使用字节码生成，性能稍低；需要额外的库支持，生成的代理类比 JDK 代理类略大。

### Javassist 动态代理

Javassist 也是基于字节码操作的代理技术，通过修改字节码实现代理。与 CGLIB 类似，Javassist 代理可以直接生成类的字节码，但生成方式较为灵活。

**适用场景**：

* 适用于需要更复杂字节码操作的 RPC 框架。
* 需要在运行时修改类结构，或需要生成定制化的代理类。

**优缺点**：

* **优点**：生成字节码的速度较快，且代码更易理解；在高并发环境下效率优于 CGLIB。
* **缺点**：与 JDK 代理相比，稍显复杂；生成的字节码代理类较大。

## 选择动态代理

* **接口代理优先**：如果服务接口稳定且明确，优先选择 **JDK 动态代理**，因为其实现简单且性能较好。
* **类代理或性能要求高**：若需要代理无接口类或对性能要求高，可以选择 **CGLIB** 或 **Javassist**。

本次我们选择 JDK 动态代理，总结一句话，通过动态代理技术，我们可以隐藏 RPC 调用的底层细节，使得使用者能够专注于接口编程，享受与本地调用无异的便捷体验。

# 架构设计

提到架构设计，相信你一定很熟悉。在我看来，架构设计是从顶层视角出发，理清各模块和组件之间的数据交互流程，帮助我们建立对系统的整体宏观认知。接下来，让我们看看RPC中都包含哪些功能模块。

1. 我们通常默认使用TCP协议。为屏蔽网络传输的复杂性，我们可以封装一个独立的数据传输模块，用于收发二进制数据，这个模块可以称为“传输模块”。
2. 用户请求本质上是方法调用，方法的参数和返回值都是对象数据，然而对象无法直接在网络中传输，因此我们需要先将其转换为可传输的二进制数据，这个过程称为**序列化**。但仅传输方法调用的二进制数据还不够，还需要在数据后添加“分隔符”来区分不同的请求，并将请求的二进制内容放置在两个“分隔符”之间，这一过程称为**协议封装**。虽然序列化和协议封装是两个独立的过程，但它们的目的一致，都是为了确保数据在网络中能被正确传输和解析。这里的“正确”不仅指数据能传输，还要保证传输后能够还原出原有的语义。因此，这两个过程可以放在架构中的同一模块中，统称为**协议模块**。
3. 在RPC中，我们希望屏蔽这些底层细节，让开发人员在使用时感觉不到本地调用与远程调用的差异。如果结合Spring框架，我们期望能够将RPC接口定义为一个Spring Bean，这样它就能被Spring的Bean Factory统一管理，并通过Spring的依赖注入机制在项目中轻松引用。这也就是RPC调用的入口模块，通常称为**Bootstrap模块**。
4. 当RPC框架具备了集群能力时，同一个接口可以有多个服务提供者，而这些服务提供者对调用方是透明的。为了实现这一点，RPC框架需要为调用方找到所有的服务提供者，并维护接口与服务提供者地址的映射关系，以便调用方在发起请求时能快速定位目标地址，这就是所谓的**服务发现**。服务发现解决了接口与服务提供方地址的静态映射问题，但在集群环境中，我们还需要管理TCP连接的状态，因为这些连接状态是动态变化的。因此，RPC框架内需要一个**连接管理器**来维护连接的状态。

此外，为了确保服务的稳定性和灵活性，RPC框架还需要内置**服务治理**功能，例如设置服务提供方的权重和调用授权等。我将这些功能模块分为了四层，具体内容见图示：

## 技术总要更新迭代是设计出来就完事了吗？

在设计RPC框架时，往往难以在一开始就顾及所有需求和场景。那么，有没有一种更灵活的方法来解决这些问题呢？这就是**插件化架构**的优势所在。

通过插件化，我们可以将每个功能抽象为接口，形成插件的契约，并将接口与具体实现分离，提供默认的实现。这样，框架就具备了扩展性和灵活性。在Java中，可以利用JDK的SPI（Service Provider Interface）机制实现动态扩展。在SPI机制中，只需在`META-INF/services`目录下创建一个文件，指定接口的实现类，`ServiceLoader`会动态加载实现类。

然而，JDK原生的SPI机制有一些限制：它无法按需加载，加载时会遍历并实例化所有实现类，导致资源浪费。此外，它也不支持自动注入，因此在依赖注入的场景中（如Spring中）不够灵活。为了解决这些问题，通常会采用自定义的插件机制，使得框架不仅能够按需加载，还能支持依赖注入，更加适配实际应用。

这样一来，RPC框架便形成了两个核心体系——核心功能体系和插件体系，让架构更具扩展性和灵活性。如下图所示：

首先，这种架构具备极强的**可扩展性**，实现了开闭原则。用户可以通过插件轻松扩展自己的功能，而无需修改核心代码，保持了系统的稳定性和灵活性。其次，这种架构保证了**核心包的精简**，减少了对外部依赖包的要求，从而有效降低了RPC框架在项目中引入包冲突的风险。

这种微内核架构将核心功能保持最小化，让架构在提供强大功能的同时依然轻量灵活，为未来的扩展和优化预留了空间。

# 网络通信

## 网络通信在 RPC 调用中起的什么作用？

在 RPC 通信中，网络通信充当关键桥梁作用，使得不同服务器或进程之间可以像调用本地函数一样进行远程调用。网络通信负责将客户端的请求数据（参数）传输到服务器，再将服务器的响应结果返回给客户端。它确保数据在传输过程中的完整性和有序性，提供同步和异步调用方式选择，支持跨平台、跨语言通信，同时处理传输中的异常的错误。通过网络通信，RPC 能够在分布式系统中实现高效、可靠的服务调用。

## 常见的 I/O 模型

当谈到网络通信时，我们不可避免地要讨论 I/O 模型 。常见的 I/O 模型主要有四种：**同步阻塞 I/O （BIO）、同步非阻塞 I/O (NIO)、 I/O 多路复用和异步非阻塞 I/O （AIO）**。在四种模型中只有 **AIO** 是异步的，其他都是同步的。然后我们逐一了解这些模型的工作原理，以及它们的应用场景。

### 同步阻塞 I/O （BIO）

同步阻塞I/O 是最常见也是最简单的I/O 模型。在 Linux 系统中，默认情况下所有的 socket 都是阻塞模式的。让我们通过一个简单的流程来了解它：

* 应用程序发起一个I/O 请求（例如发送或接收数据），此时应用进程被阻塞。
* 内核接管这个请求并等待数据准备好。直到数据准备好，内核将数据从内存复制到用户空间。
* 一旦数据被复制到用户空间，应用进程解除阻塞状态，继续执行后续的业务逻辑。

就像你去餐厅点餐，点完之后你必须在餐厅等待，直到服务员把食物送到你面前，你才能开始用餐。在这个过程中，你不能做其他事情，直到这个请求完成。每个 I/O 操作都需要占用一个线程，直到数据准备好并返回给应用程序。

#### 优点

* 简单易理解，适合低并发或请求量不高的场景。

#### 缺点

* 在高并发场景中效率低下，因为每个 I/O 操作都需要一个线程，而且线程在等待时处于阻塞状态。

### I/O 多路复用

I/O 多路复用在高并发场景中非常有用，像 Java 的 NIO（New I/O）和一些高性能服务器如 Redis、Nginx 都使用了这个模型。它的核心思想是通过一个复用器（比如 `select` 或 `poll`）来监视多个 I/O 通道。

**工作流程：**

* 应用进程将多个 socket 注册到一个复用器（比如 `select`）上，然后调用 `select` 等待事件的发生。
* 内核会监控这些注册的 socket，当任何一个 socket 中的数据准备好时，`select` 返回。
* 应用进程再次调用 `read`，从内核中获取数据并继续执行。

这个过程与同步阻塞 I/O 模型相比，稍显复杂，但它的优势在于：一个线程可以同时处理多个 I/O 操作。

**类比**： 想象你和几个朋友一起去餐厅吃饭，你们每个人分头去做不同的事情，有一个人留在餐厅排队等位，其他人去逛街。当排队的朋友通知大家可以用餐时，大家才一同回到餐厅，直接享受美食。这里，排队的那个人相当于复用器（`select`），他在等待，但其他人可以自由活动，直到“有位子了”。

#### 优点：

* 适合高并发的场景，一个线程就可以处理多个 I/O 请求，节省了大量线程开销。

#### 缺点：

* 使用 `select` 等复用器时，当连接数量非常大时，性能会下降，特别是当文件描述符过多时。

### 异步非阻塞 I/O（AIO）

异步非阻塞 I/O 是最复杂的一种模型，也是最具性能优势的一种。在 AIO 模型中，应用进程发起 I/O 请求后，不会等待 I/O 操作完成，而是继续执行其他任务。只有当 I/O 操作完成时，应用程序才会收到通知并获取结果。

**工作流程**：

* 应用进程发起 I/O 请求后，它立即返回，继续执行其他操作。
* 内核在后台处理 I/O 操作，并在完成时通过回调函数或事件通知应用程序。
* 应用程序在收到通知后，处理返回的数据。

这个模型通过回调或事件通知机制避免了阻塞，使得应用程序能够高效处理其他任务。它就像是你在餐厅点餐后，餐厅的服务员会通知你，告诉你饭菜准备好了，你再回去享用，而不是等待在餐厅内。

#### 优点：

* 高效，避免了线程的浪费，适用于需要处理大量 I/O 请求且具有高并发的场景。

#### 缺点：

* 编程复杂度较高，需要处理异步操作和回调函数。

## 网络框架的选择

RPC框架在网络通信框架的选型上，我们最优的选择是基于Reactor模式实现的框架，因为我们使用Java语言，首选的便是Netty框架。

## Netty

Netty 是一个开源的 Java 网络通信框架，专为高性能、异步事件驱动的应用设计。它广泛应用于构建高效的网络系统，如分布式架构、RPC 框架和实时通信等。Netty 提供了简洁、灵活且可扩展的 API，使得开发者能够轻松实现高效的网络通信，同时大大简化了复杂的网络编程工作。

Netty 基于\*\* NIO（非阻塞 I/O）\*\*实现，支持异步通信。这意味着它能在处理请求时不阻塞线程，从而大大提高了并发性能和吞吐量。

# 服务发现

让我们先通过一个例子来理解服务发现的概念。假设你需要联系一位从未合作过的同事并请求帮助，但你不知道他的邮箱地址。这时，你会怎么做呢？如果是我，我会去查阅公司的企业“通信录”来获取他的联系方式。

同样地，在生产环境中，为了确保服务的高可用性，服务提供方通常以集群的方式对外提供服务。集群中的服务节点（即IP地址）可能会随时发生变化。为了应对这一动态变化，我们需要一种类似“通信录”的机制，能够及时地获取到对应的服务节点。这就是我们所说的**服务发现**。

在RPC框架中，服务调用方和服务提供方的契约就是接口，而这些接口就像“通信录”中的姓名。服务节点则是具体实现该接口的服务实例，服务的IP地址集群就像是“通信录”中的地址。通过接口，服务调用方可以查询到服务提供者的IP集合，从而完成服务的发现和连接。

总而言之，**服务发现**就像是查找并联系合适的服务实例的过程，确保调用方能够及时找到并连接到所需的服务提供者。

### 基于Zookeeper的服务发现过程：

**1. 服务注册**： 服务提供方在启动时，会将自己的信息（如IP地址、端口、服务名称等）注册到Zookeeper中。通常，它会在Zookeeper的一个特定节点（如`/services/{service_name}`）下创建一个临时节点来保存服务实例的信息。注册时，服务的IP和端口等信息通常存储为节点的值。

例如，当服务A启动时，它可能会在Zookeeper中创建如下节点：

```java
/services/serviceA/192.168.1.1:8080
/services/serviceA/192.168.1.2:8080
```

**2. 服务发现**： 服务调用方（消费者）通过Zookeeper来查找某个服务的提供者。消费者会查询Zookeeper中指定的路径（如`/services/serviceA`），获取到该路径下所有注册的服务节点信息。这些节点就是服务A的所有提供者。

例如，消费者会通过Zookeeper获取到以下地址：

```java
192.168.1.1:8080
192.168.1.2:8080
```

此时，消费者就知道了可以连接哪些服务实例，并能够进行负载均衡或选择最适合的服务实例。

**3. 服务监控**： Zookeeper的一个重要特性是它的**节点监听**机制。消费者可以在Zookeeper上设置监听器，监听服务节点的变化（如服务实例的增加、删除、状态变化等）。当服务提供方的状态发生变化时（例如，一个实例宕机或新增一个实例），Zookeeper会通知消费者，从而实现服务的动态更新。

例如，如果服务A的实例`192.168.1.1:8080`宕机，Zookeeper会移除该节点，并通知消费者。消费者会收到更新通知并自动从可用服务列表中剔除该实例，确保请求只发送到可用的服务实例上。

**4. 故障恢复**： 由于Zookeeper会在节点宕机或断开时删除临时节点，因此当某个服务实例不可用时，消费者可以及时地从Zookeeper获取到更新后的服务列表，避免调用到不可用的服务。

本项目使用 Zookeeper 作为注册中心。

## 为什么选 Zookeeper?

### 1. **高可用性和容错性**

Zookeeper是一个分布式系统，具有高可用性。它通过**主从机制**和**投票机制**保证即使部分节点出现故障，整个集群仍能正常工作。当Zookeeper的一个节点发生故障时，系统会自动选举新的主节点，保证服务的高可用性。这对于服务注册和发现至关重要，确保服务发现的过程不被中断。

### 2. **强一致性**

Zookeeper提供了**强一致性**保证，确保在任何时刻，集群中的所有客户端都能看到一致的数据。这意味着，当一个服务注册或注销时，所有的消费者都能立即获取到最新的服务信息。这对于分布式服务注册非常重要，因为服务实例的状态需要在整个系统中保持一致，以避免出现调用不可用的服务的情况。

### 3. **高效的节点监听机制**

Zookeeper提供了强大的**监听机制**，允许客户端在某个节点上设置监听器，当节点的状态发生变化时（如节点被删除、数据更新等），Zookeeper会及时通知客户端。这种机制使得服务发现能够实时响应服务注册与注销的变化，确保服务调用方能够动态更新服务实例列表。

# 心跳机制：确保服务的健康与高可用性

在构建高可用、分布式的RPC框架时，我们面临的不仅仅是服务间的网络连接是否正常，更重要的是服务本身的健康状况。正如一个人表面上可能看起来健康，但内在可能已经“生病”了，服务节点也一样，TCP连接虽然没有断开，但服务可能已经“僵死”，无法正常响应请求。这是为什么我们不能简单依赖连接断开事件来判断服务健康，心跳机制因此应运而生。

## 心跳机制：动态监测服务状态

心跳机制的核心思想很简单：定期向服务发送请求，询问其状态，并根据响应结果判断服务的健康状况。具体来说，服务节点的健康状态可以分为三个级别：

* **健康状态**：连接正常，心跳响应持续成功，服务处于正常运行状态。
* **亚健康状态**：连接正常，但心跳连续失败，服务可能存在问题，但尚未完全故障。
* **死亡状态**：连接失败，服务不可用。

这些状态并非一成不变，而是随着心跳请求的反馈动态变化。一个服务节点可能经历从健康到亚健康、再到死亡的过程；同样，也可能从死亡中复活，恢复为健康状态。

![1731309065879-4a23d59d-b0b7-47ae-8efb-61e8311a6c8a.png](./img/VTld-KFQjuZz4IOY/1731309065879-4a23d59d-b0b7-47ae-8efb-61e8311a6c8a-737558.png)

## 状态转化：与人体健康相似

这种状态转化的思路与人体健康的变化类似，服务的健康状态并非是静态的，而是通过持续的监测来不断变化。例如，一个健康的节点如果连续几次无法响应心跳请求，就会被标记为“亚健康”状态，意味着它出现了问题，但还未完全宕机。如果这种问题持续存在，节点最终会被判断为“死亡”，此时服务调用方需要断开连接并做相应的故障处理。

然而，死亡状态并不意味着终结，服务节点仍然有机会通过重连机制重新恢复为健康状态。这种“复活”的设计让系统在遇到暂时性的故障时能保持高度的容错性，提高了服务的可用性。

## 动态选择健康节点：提高服务可用性

心跳机制不仅仅是用来检测节点的健康状态，更重要的是它为服务调用方提供了动态选择健康节点的依据。当服务调用方在进行请求时，会优先选择健康状态的节点进行通信，以保证业务的流畅。如果健康节点不可用，调用方则可以从亚健康状态的节点中选择一个，这就保证了即便有部分节点出现问题，系统依然能够维持高可用性。

## 防止误判：跨机房冗余设计

当然，心跳机制虽然有效，但也并非没有挑战。最常见的问题之一就是网络故障可能导致误判。比如，心跳请求发送失败，可能是由于网络故障，而非目标服务本身的异常。为此，合理的冗余设计显得尤为重要。我们可以通过在多个机房甚至多个机架中部署健康检测程序来降低这种误判的风险，只要某一个检测程序能够正常访问目标服务，就认为服务是健康的。

## 总结：为高可用打下基础

心跳机制不仅仅是一种简单的监测手段，它是保证分布式系统高可用性的核心策略之一。通过精确地管理服务节点的健康状态，并依据动态变化的健康数据来选择合适的服务实例，心跳机制确保了RPC框架在面对节点失效时，依然能够维持稳定运行。这个机制的设计不仅降低了因单点故障带来的风险，还为服务的容错性、可靠性和复原能力打下了坚实基础。

# 负载均衡

## 为什么需要负载均衡？

当单个服务节点的承受能力无法满足当前的访问量，我们通常会部署多个节点，形成一个集群，并通过负载均衡策略将请求合理地分配到集群中的每个节点。这样一来，多个节点可以共同分担请求负载，有效地提升了系统的整体处理能力和可用性。负载均衡不仅仅是均匀分配请求，更在于根据不同节点的特性和状态，只能地分发请求。最大化资源利用率并优化用户体验。

![1731325142618-bd26e2ce-4597-4180-b705-8d11e08bde4d.png](./img/VTld-KFQjuZz4IOY/1731325142618-bd26e2ce-4597-4180-b705-8d11e08bde4d-486459.png)

## 常见的负载均衡算法

\*\*1.轮询法：\*\*依次分配请求到每个服务器节点上，确保分布均匀。其实现简单且无状态，但难以适应性能差异明显的服务器，导致资源分配不均衡。因此，轮询法适合配置相似的服务器集群。

\*\*2.随机法：\*\*随机法通过随机分配请求来平衡负载，有助于避免某一节点接连收到请求的情况。尽管实现简单，但在不同配置的服务器上，随机法可能导致负载分布不均。

\*\*3.一致性哈希法：\*\*一致性哈希根据客户端特征映射到哈希环上，顺时针匹配最近的服务器，实现数据稳定的分布。此方法在节点变更时，避免大量重新映射，但可能存在哈希倾斜问题。为提高均衡性，可引入虚拟节点优化缓存分布。

# 异常重试

## 为什么需要异常重试？

在这种场景中，我们发起一个RPC调用，假设是用户登录操作，首先验证用户名和密码，验证通过后再获取用户的基本信息。可是，天有不测风云，网络波动导致请求失败。此时，我们希望请求能自我恢复，尽可能成功完成。这种时候，直接在代码中 `catch` 异常然后手动重试，显得有点“笨拙”和冗余。更为优雅的做法是，依赖RPC框架自带的重试机制，让它在背后默默为我们处理这种“偶尔的小插曲”。不仅避免了重复代码，还能保持系统的高可用性和可维护性，让我们在面对网络问题时，既不慌张，又不失从容。

## RPC 的重试机制

在使用RPC框架时，我们需要确保被调用的服务的业务逻辑是幂等的——这就像是你去咖啡店点了一杯咖啡，如果你不小心多点了一次，店员也不会给你两个咖啡，只会给你一个。这是因为，幂等性保证了无论调用多少次，结果都是一样的。只有在确保了幂等性后，我们才能放心地启用RPC框架的重试功能。否则，一旦网络抖动或其他原因导致请求失败，重试机制可能就变成了一个双倍烦恼的源头，而不是解决方案。所以，幂等性就像是重试的安全锁，只有它存在，重试才能优雅地工作，而不会把事情搞得一团乱。

## 如何在约定时间内安全可靠的重试？

### 1. 超时问题的解决

当我们使用RPC框架时，异常重试机制可能会导致请求处理时间过长，最终超出用户设定的超时时间。为了优雅地解决这个问题，最直接的方式就是在每次重试后**重置请求的超时时间**。

* **重试前检查超时**：如果调用端发起请求时发生异常并触发重试，首先检查请求是否已经超时。
* **超时处理**：如果请求已经超时，则直接返回超时异常；如果尚未超时，则重置超时时间，再重新发起请求。

这样做可以有效避免由于时间延迟导致的不必要失败，确保重试机制不会受到超时的影响。

### 2.负载均衡与故障节点

解决了超时问题后，我们还需要关注一个细节问题：**重试时选择的服务节点可能与上次失败时相同**。如果这个节点由于负载过重导致的失败问题没有得到解决，重试仍然会失败。

* **避免重复选择故障节点**：为了提高重试的成功率，我们需要在负载均衡时排除之前出问题的节点，这样可以确保请求被发送到健康的节点，从而避免在负载过高的节点上重试，提升重试的成功几率。

### 3. 业务异常与重试策略

即使我们考虑了幂等性、超时重置和去除故障节点，重试机制依然不是完美的。RPC框架的异常重试机制默认只会针对**框架层的异常**（如连接失败、超时等）进行重试。

然而，**服务端的业务逻辑可能抛出一些可以容忍重试的异常**。例如，服务端在执行数据库更新时抛出“更新失败”的异常，调用端可以重新发起调用，尝试重新执行更新操作。这时，框架并不自动识别这些业务异常是否可以重试。

### 4. 重试异常白名单

为了解决这个问题，我们可以在RPC框架的重试机制中增加一个**重试异常白名单**。

* **白名单机制**：用户可以将特定的业务异常添加到白名单中，框架就知道哪些业务异常是可以重试的。
* **重试条件**：当调用端捕获到异常，且该异常属于框架支持的重试异常，或者在白名单中时，重试机制将继续生效，允许重新发起请求。

# 熔断限流

## 为什么需要自我保护？

RPC是分布式系统中解决通信问题的利器，而分布式系统的一大特点就是**高并发**，这也意味着RPC需要在高并发的场景下稳定运行。在这种情况下，服务节点可能会因为访问量过大而遭遇一系列的“麻烦”：处理时间过长、CPU飙升、频繁触发Full GC，甚至整个服务进程崩溃。

然而，在生产环境中，我们的目标是确保服务的**稳定性**和**高可用性**，而不是让这些问题拖垮系统。因此，我们需要让业务具备一定的**自我保护能力**，确保在高访问量、高并发的压力下，应用系统依然能够稳如泰山，服务依然能够保持高可用，避免因为负载过重而导致“崩溃式”的失败。

简单来说，我们要做的是，让我们的系统在遭遇过多请求时，能够优雅地应对压力，**不慌不忙**地保证服务继续运行，而不是被高并发压垮。

## 服务端的自我保护

假设我们要发布一个RPC服务，服务端接收来自调用端的请求。如果此时服务端的某个节点因为负载过高而陷入困境，我们该如何保护这个节点呢？

这个问题其实不难解决——既然服务端负载过高，最直接的办法就是**不让它接收太多请求**，等到接收和处理的请求量降低，负载自然就会缓解。

那么，最直接的方式就是**限流**。没错，限流就是服务端自我保护的法宝。那么，你有没有想过，我们该如何实现限流呢？是不是在每个业务逻辑中都手动加个限流控制？显然，这样做就不够优雅了，也会让代码变得冗余和复杂。

限流本身是一个非常通用的功能，为什么不把它抽象成一个框架层面的功能呢？我们可以把限流机制集成到RPC框架中，让使用者可以方便地配置限流阈值。这样，服务端只需要专注于自己的业务逻辑，不必在每个方法中加繁琐的限流代码。

具体来说，当调用端发送请求时，服务端在执行实际业务逻辑之前，先检查当前的请求量。如果发现访问量过大，超过了限流阈值，服务端就**优雅地**抛回一个限流异常，告知调用端稍后再试，而不是继续执行耗时的业务逻辑。这样不仅让限流机制更加透明和可配置，而且也确保了服务端在高负载下能够稳定运行，避免资源被过度占用。

通过这种方式，限流就变成了一种优雅的**防护机制**，既不影响业务的正常处理，又能有效避免高并发带来的风险，保持服务的高可用性和稳定性。

![1731564679795-75c61e05-a715-4b80-9d76-7c0498a714b6.png](./img/VTld-KFQjuZz4IOY/1731564679795-75c61e05-a715-4b80-9d76-7c0498a714b6-239914.png)

### 服务端的限流如何实现呢？

限流有很多种实现方式，从最基础的**计数器**到更复杂的**滑动窗口、漏斗算法、令牌桶算法**等，最常用的就是**令牌桶算法**。关于这些算法的细节，网上有很多资料，感兴趣的可以自己去深入了解。

假设我们有一个在线商店的服务，提供给不同的客户端调用。这时，某个特定的客户端可能发送的请求比其他客户端多得多，我们就需要对这个客户端的请求流量进行限流。**限流**不仅要考虑服务端的负载问题，还得考虑到**客户端级别**甚至是**IP级别**的流量控制，这样就能更灵活地限制不同来源的流量。

那么，如何方便地配置这些限流策略呢？如果每次都要在代码中硬编码，肯定不太合适。幸运的是，RPC框架的**治理功能**可以帮我们解决这个问题。我们可以通过**RPC治理管理端**配置限流阈值，再通过注册中心或配置中心将这些配置动态下发到各个服务节点，实现灵活的限流控制。

但问题是，如果我们的服务依赖于数据库（例如库存数据库），且数据库的处理能力有限，那么即使我们有多个服务节点，我们的总流量也不能超过数据库的承载能力。例如，如果数据库每秒最多支持1000次查询，而我们有10个服务节点，每个节点的限流阈值是每秒1000次请求，但总流量不能超过1000次。这时我们就需要重新计算并调整限流阈值。假如服务扩容到20个节点，阈值需要调整到每秒500次请求。这样每次扩容或缩容时都需要手动调整限流配置，非常麻烦。

为了解决这个问题，可以让**RPC框架自动计算**。当注册中心或配置中心下发限流配置时，框架可以根据当前服务节点的数量自动调整每个节点的限流阈值，避免了人工计算和配置的麻烦。

不过，即使这样，问题仍然存在。因为每个服务节点接收到的流量可能不均衡，假设我们有20个节点，每个节点的限流阈值是500次，但有些节点的流量已经达到500次，而其他节点可能只有200次，这时虽然整体流量未超标，但可能会错误地触发限流。因此，单机限流的方式会导致不精确的限流。

为了解决这个问题，我们可以引入一个**专门的限流服务**，所有节点在收到请求时，都会通过调用限流服务来判断是否达到限流阈值。甚至，**调用端**也可以先调用限流服务，判断流量是否已经超标，如果超标，就直接返回限流异常，而不发送请求到服务端。这样，整个服务集群的流量控制就能更精确。

当然，依赖限流服务虽然精确，但也会带来一定的**性能开销**，因为每个请求都需要经过限流服务判断。因此，选择哪种限流方式要根据具体的应用场景来决定：小流量可以用单机限流，大流量且需要精确控制的场景则适合分布式限流。

## 调用方的自我保护

刚才我们聊了服务端的自我保护，最常见也最有效的方式就是限流。那么，问题来了，**调用端**需要自我保护吗？

来看看这个场景：假设我们发布了一个**服务B**，而服务B又依赖于另一个服务**C**。某天，**服务A**发起了大量请求调用服务B，而服务B在处理这些请求时，需要调用服务C。但不巧的是，服务C响应超时了，这时候，服务B就会一直等待C的响应。而如果服务A继续频繁地调用服务B，服务B就可能因为不断堆积的请求而**被拖垮**，甚至**宕机**。这样一来，不仅服务B崩溃，整个链条上的服务都可能受到影响。

![1731565276196-b21b68e2-05a4-440f-92fe-5f4afed29e1a.png](./img/VTld-KFQjuZz4IOY/1731565276196-b21b68e2-05a4-440f-92fe-5f4afed29e1a-801727.png)

正如我们刚才讨论的，服务B依赖服务C，而如果服务C在执行时出现了问题，服务B就会被拖累，甚至可能**崩溃**。这只是**A->B->C**的简单情况，想象一下**A->B->C->D->...****这种复杂的调用链。只要链条中的任何一个服务出现问题，都会影响到上游的所有服务，甚至可能导致整个链路的崩溃——这简直就是****&#x591A;米诺骨牌效应**，一旦倒下，整个系统都会陷入瘫痪。

这就像是你在玩一个需要每个环节都稳定的小型乐器合奏，突然一个音符错了，整个曲子就变得无法听了。

所以，为了防止这种问题，**调用端的自我保护变得尤为重要**。最有效的自我保护方式之一就是——**熔断**。当调用端发现被调用的服务响应迟缓、出现异常或者负载过重时，熔断机制会立即切断与该服务的连接，防止请求继续涌入，避免“感染”到整个调用链，保护上游服务不被拖垮。

就像电器上的**保险丝**，当电流过载时，它会自动切断电路，避免设备被烧毁。熔断机制就是为了让你的系统在遇到问题时**及时断开**，保持“冷静”，避免一场灾难性的故障。

![1731565615896-2c7b8eb9-8e59-4797-aa56-9f7c69353e09.png](./img/VTld-KFQjuZz4IOY/1731565615896-2c7b8eb9-8e59-4797-aa56-9f7c69353e09-769632.png)

熔断器的工作机制可以简单理解为一个**三重身份**：**关闭、打开、半打开**。

在正常情况下，熔断器处于**关闭**状态，意味着一切正常，服务之间的调用也都没有问题。然而，当调用端向下游服务发起请求时，如果发现服务出现异常，熔断器就开始“警觉”起来，开始记录异常信息并进行计算。一旦达到设定的熔断条件，熔断器就会**打开**，这时，所有请求都会被熔断器拦截，直接跳过下游服务，避免它继续崩溃或过载，然后快速返回失败响应。

熔断器保持打开状态一段时间后，会转为**半打开**状态，这时，熔断器允许调用端发起一个请求到下游服务。假如服务端能够正常响应，这个熔断器就会恢复到**关闭**状态，表示系统恢复正常。如果这次请求依然失败，熔断器就会再次进入**打开**状态，继续拦截请求，直到达到正常的恢复条件。

看完熔断器的工作原理，你会发现，把熔断器硬塞进业务逻辑中就像是往你的系统里塞了个“安全气囊”，虽然能在崩溃前提供保护，但似乎有点**笨重**。那怎么办呢？我们需要一种更加优雅的方式来在RPC框架中整合熔断器。

这里的关键是：**把熔断器从业务逻辑中抽离出来，交给RPC框架去处理**。就像你不需要自己去驾驭安全气囊一样，RPC框架可以帮你自动监控调用链路中的异常，当异常发生时，熔断器会自动启动，拦截请求，避免灾难传播。通过这种方式，调用端就可以专注于业务逻辑，熔断器的处理则完全由框架来托管，既高效又优雅。

这样的整合，让整个系统更加简洁，同时也不失“智慧”。如果说熔断器是一位医生，它会根据系统的症状进行治疗，而你不必总是盯着它手术，RPC框架就像是它的护士，默默地帮助你处理好一切。

## 哪个步骤整合熔断器比较合适？

在RPC调用的流程中，**动态代理**是调用的第一个关口。当调用端发出请求时，所有请求都会经过这个代理层。在这里，我们可以巧妙地插入熔断器的逻辑：首先检查熔断器的状态。

如果熔断器的状态是**关闭**，说明系统健康，调用端就可以正常发出请求，传递给下游服务；如果熔断器的状态是**打开**，那就直接执行熔断器的**失败策略**，比如快速返回一个错误响应，避免请求继续进入系统，防止系统崩溃。

通过动态代理，我们就能优雅地将熔断器逻辑从业务代码中抽离出来，集中管理。熔断器的触发、状态切换和失败策略都会自动生效，而调用端无需感知这些细节。调用方只需专注于业务逻辑，熔断机制则无缝集成在整个RPC调用的生命周期中。

这种方式就像是给每个服务请求加了一层“安全检查”，既能保证高效性，又不会影响业务代码的简洁性。它使得熔断器的引入变得非常灵活且透明，同时也方便后期的扩展和维护。
