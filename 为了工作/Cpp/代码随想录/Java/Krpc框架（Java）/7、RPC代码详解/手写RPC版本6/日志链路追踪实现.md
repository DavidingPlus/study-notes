# 日志链路追踪实现

<font style="color:rgb(64, 64, 64);">在分布式系统中，一个业务请求往往需要经过多个RPC服务节点处理。当出现以下场景时：</font>

* <font style="color:rgb(64, 64, 64);">跨服务异常定位困难</font>
* <font style="color:rgb(64, 64, 64);">请求响应时间突增但难以定位瓶颈</font>
* <font style="color:rgb(64, 64, 64);">需要分析完整调用链路行为</font>

<font style="color:rgb(64, 64, 64);">  
</font><font style="color:rgb(64, 64, 64);">传统离散的日志记录方式难以满足需求，需要一种能贯穿整个调用链路的追踪方案。</font>

<font style="color:rgb(64, 64, 64);">如果实习过的小伙伴们都知道，在线上发生bug和报警时，第一时间需要去获取报警信息中的traceId，再根据traceId在日志观测平台上拉去整个链路的调用信息，从而进行快速的分析和处理。</font>

这里引入两个 分布式系统中用于跟踪和监控请求处理流程的重要概念：`TraceId` 和 `SpanId`

#### TraceId

**定义**

`TraceId` 是一个全局唯一的标识符，用于标识一个完整的请求链路。当一个请求进入分布式系统后，系统会为该请求生成一个唯一的 `TraceId`，并将其在整个请求处理过程中传递下去。无论这个请求在分布式系统中经过多少个服务节点，只要是处理同一个请求，都会使用相同的 `TraceId`。

**示例**

假设一个用户在电商网站上发起一个下单请求，该请求会经过用户服务、商品服务、订单服务等多个服务处理。系统会为这个下单请求生成一个 `TraceId`，如 `123e4567-e89b-12d3-a456-426614174000`，并将其在各个服务之间传递。在每个服务的日志中，都会记录这个 `TraceId`，这样就可以根据 `TraceId` 追踪整个下单请求的处理过程。

#### SpanId

**定义**

`SpanId` 是一个局部唯一的标识符，用于标识一个请求在某个服务节点内的一次调用。一个 `Trace` （由 `TraceId` 标识）可以包含多个 `Span` （由 `SpanId` 标识），每个 `Span` 代表了请求在某个服务节点内的一个操作或子任务。

**示例**

继续以上述电商网站的下单请求为例，当请求到达订单服务时，订单服务可能会执行多个子任务，如验证订单信息、扣减库存、生成订单记录等。每个子任务都会被分配一个唯一的 `SpanId`，如 `01234567-89ab-cdef-0123-456789abcdef`。通过 `SpanId` 可以详细了解每个子任务的执行时间和执行结果。

# TraceId ,SpanId生成

<font style="color:rgb(64, 64, 64);">在分布式追踪系统中，</font>**<font style="color:rgb(64, 64, 64);">Trace ID</font>**<font style="color:rgb(64, 64, 64);"> 是用于唯一标识一个完整调用链的全局标识符。</font>

**<font style="color:rgb(64, 64, 64);">TraceID的设计原则（也即分布式事务ID）：</font>**

1. **<font style="color:rgb(64, 64, 64);">全局唯一性</font>**<font style="color:rgb(64, 64, 64);">：整个分布式系统中，每个 Trace ID 必须唯一。</font>
2. **<font style="color:rgb(64, 64, 64);">高效生成</font>**<font style="color:rgb(64, 64, 64);">：生成算法需高性能，避免成为系统瓶颈。</font>
3. **<font style="color:rgb(64, 64, 64);">可读性</font>**<font style="color:rgb(64, 64, 64);">：尽量保证 Trace ID 的字符串可读（如 16/32 位十六进制）。</font>

**<font style="color:rgb(64, 64, 64);">常见的生成算法：</font>**

**<font style="color:rgb(64, 64, 64);">1.UUID 生成</font>**

<font style="color:rgb(64, 64, 64);">利用 </font><code><font style="color:rgb(64, 64, 64);">UUID</font></code><font style="color:rgb(64, 64, 64);"> 算法生成全局唯一的字符串。</font>

**<font style="color:rgb(64, 64, 64);">优点</font>**<font style="color:rgb(64, 64, 64);">：简单、无需额外依赖，满足唯一性。\ </font>**<font style="color:rgb(64, 64, 64);">缺点</font>**<font style="color:rgb(64, 64, 64);">：字符串较长（32 位），可能影响日志可读性。</font>

**<font style="color:rgb(64, 64, 64);">2.</font>\*\*\*\*<font style="color:rgb(64, 64, 64);">Snowflake 算法</font>**

<font style="color:rgb(64, 64, 64);">Twitter 开源的分布式 ID 生成算法，生成 64 位长整型，可转为十六进制。</font>

```java
| 时间戳（41 位） | 机器 ID（10 位） | 序列号（12 位） |
```

**<font style="color:rgb(64, 64, 64);">优点</font>**<font style="color:rgb(64, 64, 64);">：高性能、有序、分布式唯一。</font>**<font style="color:rgb(64, 64, 64);">\ </font>\*\*\*\*<font style="color:rgb(64, 64, 64);">缺点</font>**<font style="color:rgb(64, 64, 64);">：需分配机器 ID，时钟回拨需处理。</font>

<font style="color:rgb(64, 64, 64);"></font>

<font style="color:rgb(64, 64, 64);">在这里我们对于TraceId  在使用雪花算法实现时，机器ID默认为0（因为单机）</font>

<font style="color:rgb(64, 64, 64);">而在真实场景中，则可改由配置中心获取</font>

<font style="color:rgb(64, 64, 64);"></font>

在krpc-core项目com.kama下创建trace包，创建TraceIdGenerator类

```java
public class TraceIdGenerator {
    //机器ID默认为0，真实场景中从配置中心获取
    private static final SnowflakeIdGenerator SNOWFLAKE =new SnowflakeIdGenerator(0L);

    public static  String generateTraceId() {
        return Long.toHexString(SNOWFLAKE.nextId());
    }
    public static String generateTraceIdUUID(){
        UUID uuid = UUID.randomUUID();
        String uuidString = uuid.toString();
        // 去掉连字符
        String uuidWithoutHyphens = uuidString.replace("-", "");
        return uuidWithoutHyphens;
    }
    public static String generateSpanId() {
        return String.valueOf(System.currentTimeMillis());
    }
    
    static class SnowflakeIdGenerator {
        // 机器 ID（0~1023）
        private final long workerId;

        // 基准时间（2021-01-01 00:00:00）
        private final long epoch = 1609459200000L;

        // 序列号（0~4095）
        private long sequence = 0L;

        // 上一次生成 ID 的时间戳
        private long lastTimestamp = -1L;

        // 构造函数，传入机器 ID
        public SnowflakeIdGenerator(long workerId) {
            if (workerId < 0 || workerId > 1023) {
                throw new IllegalArgumentException("Worker ID 必须在 0~1023 之间");
            }
            this.workerId = workerId;
        }

        // 生成下一个 ID
        public synchronized long nextId() {
            long timestamp = System.currentTimeMillis();

            // 如果当前时间小于上一次生成 ID 的时间，说明时钟回拨
            if (timestamp < lastTimestamp) {
                throw new RuntimeException("时钟回拨！");
            }

            // 如果当前时间等于上一次生成 ID 的时间，递增序列号
            if (timestamp == lastTimestamp) {
                sequence = (sequence + 1) & 0xFFF; // 12 位序列号，最大 4095
                if (sequence == 0) {
                    // 如果序列号溢出，等待下一毫秒
                    timestamp = waitNextMillis(lastTimestamp);
                }
            } else {
                // 如果当前时间大于上一次生成 ID 的时间，重置序列号
                sequence = 0L;
            }

            // 更新上一次生成 ID 的时间戳
            lastTimestamp = timestamp;

            // 生成 ID
            return ((timestamp - epoch) << 22) | (workerId << 12) | sequence;
        }

        // 等待下一毫秒
        private long waitNextMillis(long lastTimestamp) {
            long timestamp = System.currentTimeMillis();
            while (timestamp <= lastTimestamp) {
                timestamp = System.currentTimeMillis();
            }
            return timestamp;
        }
    }
}
```

# 定义结构保存链路信息

日志链路中包含traceId,spanId等多种信息，我们该使用什么数据结构来保存这些信息，并且保证他们能在不同线程和链路中各自独立的稳定保存和传递呢？

这里当然第一个想到的数据结构是 ThreadLocal，为了便于维护，我们可以配合<font style="color:rgba(0, 0, 0, 0.85);">SLF4J更优雅的解决问题。</font>

**常见的解决方案**是使用<font style="color:rgba(0, 0, 0, 0.85);">Slf4j 的</font><code><font style="color:rgba(0, 0, 0, 0.85);">MDC</font></code><font style="color:rgba(0, 0, 0, 0.85);"> （Mapped Diagnostic Context），是一个线程本地的映射，用于在日志记录时提供额外的上下文信息。</font><code><font style="color:rgba(0, 0, 0, 0.85);">MDC</font></code><font style="color:rgba(0, 0, 0, 0.85);"> 类内部维护了一个 </font><code><font style="color:rgba(0, 0, 0, 0.85);">ThreadLocal</font></code><font style="color:rgba(0, 0, 0, 0.85);"> 变量，用于存储每个线程的 MDC 上下文信息。</font>

<font style="color:rgba(0, 0, 0, 0.85);">以下是MDC部分代码示例</font>

```java
public class MDC {
    private static final ThreadLocal<Map<String, String>> mdcThreadLocal = new ThreadLocal<Map<String, String>>() {
        @Override
        protected Map<String, String> initialValue() {
            return new HashMap<>();
        }
    };

    public static void put(String key, String val) {
        Map<String, String> map = mdcThreadLocal.get();
        map.put(key, val);
    }

//...
```

# 日志链路数据上报与可视化

<font style="color:rgb(64, 64, 64);">在实现调用链可视化时，我们需要先将日志追踪数据发送到一个分布式追踪系统（如 </font>**<font style="color:rgb(64, 64, 64);">Zipkin</font>**<font style="color:rgb(64, 64, 64);"> 或 </font>**<font style="color:rgb(64, 64, 64);">Jaeger</font>**<font style="color:rgb(64, 64, 64);">），然后通过这些系统的 UI 界面查看调用链的可视化结果。</font>

## <font style="color:rgb(64, 64, 64);">设计思路</font>

1. **<font style="color:rgb(64, 64, 64);">数据格式</font>**<font style="color:rgb(64, 64, 64);">：</font>
   * <font style="color:rgb(64, 64, 64);">调用链数据需要符合分布式追踪系统的数据格式（如 Zipkin 的 JSON 格式）。</font>
   * <font style="color:rgb(64, 64, 64);">每个调用链的节点（Span）需要包含以下信息：</font>
     * <code><font style="color:rgb(64, 64, 64);">traceId</font></code><font style="color:rgb(64, 64, 64);">：全局唯一的追踪 ID。</font>
     * <code><font style="color:rgb(64, 64, 64);">spanId</font></code><font style="color:rgb(64, 64, 64);">：当前 Span 的唯一 ID。</font>
     * <code><font style="color:rgb(64, 64, 64);">parentId</font></code><font style="color:rgb(64, 64, 64);">：父 Span 的 ID（用于构建调用链的层级关系）。</font>
     * <code><font style="color:rgb(64, 64, 64);">name</font></code><font style="color:rgb(64, 64, 64);">：Span 的名称（通常是服务名或方法名）。</font>
     * <code><font style="color:rgb(64, 64, 64);">timestamp</font></code><font style="color:rgb(64, 64, 64);">：Span 的开始时间。</font>
     * <code><font style="color:rgb(64, 64, 64);">duration</font></code><font style="color:rgb(64, 64, 64);">：Span 的持续时间。</font>
     * <code><font style="color:rgb(64, 64, 64);">tags</font></code><font style="color:rgb(64, 64, 64);">：附加信息（如请求参数、响应状态等）。</font>
2. **<font style="color:rgb(64, 64, 64);">数据上报</font>**<font style="color:rgb(64, 64, 64);">：</font>
   * <font style="color:rgb(64, 64, 64);">在每个 Span 结束时，将数据发送到分布式追踪系统。</font>
   * <font style="color:rgb(64, 64, 64);">可以通过 HTTP 或消息队列（如 Kafka）将数据发送到追踪系统。</font>
3. **<font style="color:rgb(64, 64, 64);">调用链可视化</font>**<font style="color:rgb(64, 64, 64);">：</font>
   * <font style="color:rgb(64, 64, 64);">使用 Zipkin 或 Jaeger 的 UI 界面查看调用链的可视化结果。</font>
   * <font style="color:rgb(64, 64, 64);">调用链会展示每个服务的调用顺序、耗时、层级关系等信息。</font>

### 2.增加zipkin数据上报功能

在krpc-core项目com.kama.trace下

创建ZipkinReporter类，实现与zipkin数据交互

```java
@Slf4j
public class ZipkinReporter {
    private static final String ZIPKIN_URL = "http://localhost:9411/api/v2/spans"; // Zipkin 服务器地址
    private static final AsyncReporter<Span> reporter;

    static {
        // 初始化 Zipkin 上报器
        OkHttpSender sender = OkHttpSender.create(ZIPKIN_URL);
        reporter = AsyncReporter.create(sender);
    }

    /**
     * 上报 Span 数据到 Zipkin
     */
    public static void reportSpan(String traceId, String spanId, String parentSpanId,
                                  String name, long startTimestamp, long duration,
                                  String serviceName,String type) {
        Span span = Span.newBuilder()
        .traceId(traceId)
        .id(spanId)
        .parentId(parentSpanId)
        .name(name)
        .timestamp(startTimestamp * 1000) // Zipkin 使用微秒
        .duration(duration * 1000) // Zipkin 使用微秒
        .putTag("service",serviceName)
        .putTag("type",type)
        .build();
        reporter.report(span);
        log.info("当前traceId:{}正在上报日志-----",traceId);
    }

    public static void close() {
        reporter.close();
    }
}
```

### 3.创建客户端和服务端拦截器，上报span数据

在krpc-core项目com.kama.trace包下创建包interceptor

创建ClientTraceInterceptor类

beforeInvoke()用于初始化和保存日志链路数据

afterInvoke() 用于上报日志链路数据

```java
public class ClientTraceInterceptor {
    public static void beforeInvoke() {
        String traceId = TraceContext.getTraceId();
        if (traceId == null) {
            traceId = TraceIdGenerator.generateTraceId();
            TraceContext.setTraceId(traceId);
        }
        String spanId = TraceIdGenerator.generateSpanId();
        TraceContext.setSpanId(spanId);

        // 记录客户端 Span
        long startTimestamp = System.currentTimeMillis();
        TraceContext.setStartTimestamp(String.valueOf(startTimestamp));
    }

    public static void afterInvoke(String serviceName) {
        long endTimestamp = System.currentTimeMillis();
        long startTimestamp = Long.valueOf(TraceContext.getStartTimestamp());
        long duration = endTimestamp - startTimestamp;

        // 上报客户端 Span
        ZipkinReporter.reportSpan(
            TraceContext.getTraceId(),
            TraceContext.getSpanId(),
            TraceContext.getParentSpanId(),
            "client-" + serviceName,
            startTimestamp,
            duration,
            serviceName,
            "client"
        );

        // 清理 TraceContext
        TraceContext.clear();
    }
}
```

### 4.在客户端和服务端选择合适位置 拦截和上报

#### <font style="color:rgb(64, 64, 64);">RPC客户端拦截器</font>

**<font style="color:rgb(64, 64, 64);">在发起请求前设置Trace ID和Span ID，请求返回时上报数据</font>**

<font style="color:rgb(64, 64, 64);">自然可以想到 在动态代理invoke的位置加入</font>

<font style="color:rgb(64, 64, 64);">krpc-core项目com.kama.client.proxy包下的ClientProxy中</font>

```java
//jdk动态代理，每一次代理对象调用方法，都会经过此方法增强（反射获取request对象，socket发送到服务端）
@Override
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    //trace记录
    ClientTraceInterceptor.beforeInvoke();
    
    //构建request
    RpcRequest request = RpcRequest.builder()
    .type(RequestType.NORMAL)
    .interfaceName(method.getDeclaringClass().getName())
    .methodName(method.getName())
    .params(args).paramsType(method.getParameterTypes()).build();
    //获取熔断器
    CircuitBreaker circuitBreaker = circuitBreakerProvider.getCircuitBreaker(method.getName());
    //判断熔断器是否允许请求经过
    if (!circuitBreaker.allowRequest()) {
        log.warn("熔断器开启，请求被拒绝: {}", request);
        //这里可以针对熔断做特殊处理，返回特殊值
        return null;
    }
    //数据传输
    RpcResponse response;
    //后续添加逻辑：为保持幂等性，只对白名单上的服务进行重试
    // 如果启用重试机制，先检查是否需要重试
    String methodSignature = getMethodSignature(request.getInterfaceName(), method);
    log.info("方法签名: " + methodSignature);
    InetSocketAddress serviceAddress = serviceCenter.serviceDiscovery(request);
    rpcClient = new NettyRpcClient(serviceAddress);
    if (serviceCenter.checkRetry(serviceAddress, methodSignature)) {
        //调用retry框架进行重试操作
        try {
            log.info("尝试重试调用服务: {}", methodSignature);
            response = new GuavaRetry().sendServiceWithRetry(request, rpcClient);
        } catch (Exception e) {
            log.error("重试调用失败: {}", methodSignature, e);
            circuitBreaker.recordFailure();
            throw e;  // 将异常抛给调用者
        }
    } else {
        //只调用一次
        response = rpcClient.sendRequest(request);
    }
    //记录response的状态，上报给熔断器
    if (response != null) {
        if (response.getCode() == 200) {
            circuitBreaker.recordSuccess();
        } else if (response.getCode() == 500) {
            circuitBreaker.recordFailure();
        }
        log.info("收到响应: {} 状态码: {}", request.getInterfaceName(), response.getCode());
    }
    
    //trace上报
    ClientTraceInterceptor.afterInvoke(method.getName());

    return response != null ? response.getData() : null;
}
```

### 5.持有和传递日志数据

在客户端生成的traceId等信息，需要被传递到服务端，服务端获取后在TraceContext中持有

C-S间的传递，可以配合netty实现

模仿HTTP，在消息编解码处 **加一段trace消息头，用于传输日志链路数据**

krpc-common项目下common.serializer.mycoder中

* MyEncoder类 获取当前TraceContext中traceId，spanId，写入消息头
* MyDecoder类 按格式获取写入的trace消息头，并存放到TraceContext中

```java
@Slf4j
@AllArgsConstructor
public class MyEncoder extends MessageToByteEncoder {
    private Serializer serializer;

    @Override
    protected void encode(ChannelHandlerContext ctx, Object msg, ByteBuf out) throws Exception {
        log.debug("Encoding message of type: {}", msg.getClass());
        //1.写入trace消息头
        String traceMsg= TraceContext.getTraceId() +";"+TraceContext.getSpanId();
        byte[] traceBytes=traceMsg.getBytes();
        //  1.1写入traceMsg长度
        out.writeInt(traceBytes.length);
        //  1.2写入traceBytes
        out.writeBytes(traceBytes);

        //2.写入消息类型
        if (msg instanceof RpcRequest) {
            out.writeShort(MessageType.REQUEST.getCode());
        } else if (msg instanceof RpcResponse) {
            out.writeShort(MessageType.RESPONSE.getCode());
        } else {
            log.error("Unknown message type: {}", msg.getClass());
            throw new IllegalArgumentException("Unknown message type: " + msg.getClass());
        }
        //3.写入序列化方式
        out.writeShort(serializer.getType());
        //得到序列化数组
        byte[] serializeBytes = serializer.serialize(msg);
        if (serializeBytes == null || serializeBytes.length == 0) {
            throw new IllegalArgumentException("Serialized message is empty");
        }
        //4.写入长度
        out.writeInt(serializeBytes.length);
        //5.写入序列化数组
        out.writeBytes(serializeBytes);
    }
}


@Slf4j
public class MyDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext channelHandlerContext, ByteBuf in, List<Object> out) throws Exception {
        //检查可读字节数
        if (in.readableBytes() < 6) {  // messageType + serializerType + length
            return;
        }
        //1.读取traceMsg
        int traceLength=in.readInt();
        byte[] traceBytes=new byte[traceLength];
        in.readBytes(traceBytes);
        serializeTraceMsg(traceBytes);
        //2.读取消息类型
        short messageType = in.readShort();
        // 现在还只支持request与response请求
        if (messageType != MessageType.REQUEST.getCode() &&
                messageType != MessageType.RESPONSE.getCode()) {
            log.warn("暂不支持此种数据, messageType: {}", messageType);
            return;
        }
        //3.读取序列化的方式&类型
        short serializerType = in.readShort();
        Serializer serializer = Serializer.getSerializerByCode(serializerType);
        if (serializer == null) {
            log.error("不存在对应的序列化器, serializerType: {}", serializerType);
            throw new SerializeException("不存在对应的序列化器, serializerType: " + serializerType);
        }
        //4.读取序列化数组长度
        int length = in.readInt();
        if (in.readableBytes() < length) {
            return;  // 数据不完整，等待更多数据
        }
        //5.读取序列化数组
        byte[] bytes = new byte[length];
        in.readBytes(bytes);
        log.debug("Received bytes: {}", Arrays.toString(bytes));
        Object deserialize = serializer.deserialize(bytes, messageType);

        out.add(deserialize);
    }
    //解析并存储traceMsg
    private void serializeTraceMsg(byte[] traceByte){
        String traceMsg=new String(traceByte);
        String[] msgs=traceMsg.split(";");
        if(!msgs[0].equals("")) TraceContext.setTraceId(msgs[0]);
        if(!msgs[1].equals("")) TraceContext.setParentSpanId(msgs[1]);
    }
}
```

```java
    @Override
    public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise) throws Exception {
        // 从Channel属性中获取Trace上下文
        Map<String, String> traceContext =
        ctx.channel().attr(TRACE_CONTEXT_KEY).get();

            // 设置到当前线程的TraceContext或MDC

        } else {
            log.error("Trace上下文未设置!");
        }

        // 继续传递请求
        super.write(ctx, msg, promise);
    }
```
