# 4. 常见面试题 - 项目实现

## 4.1 Agent Loop 实现
### 4.1.1 Agent Loop 是如何实现的？
#### 回答要点
1. Think-Execute 循环机制
2. 状态管理
3. 循环控制
4. 工具调用流程

#### 标准回答
Agent Loop 的核心是 Think-Execute 循环，我这样实现的：

1. 循环结构：

```java
for (int i = 0; i < MAX_STEPS && agentState != AgentState.FINISHED; i++) {
    if (think()) {  // Think 阶段
        execute();  // Execute 阶段
    } else {
        break;  // 无工具调用，直接返回
    }
}
```

2. Think 阶段：
    1. 构建包含历史消息的 Prompt
    2. 调用 ChatClient，传入可用工具
    3. LLM 分析任务，决定是否调用工具
    4. 如果有工具调用，返回 true
3. Execute 阶段：
    1. 使用 ToolCallingManager 执行工具调用
    2. 获取工具执行结果
    3. 更新对话历史（包含工具调用和结果）
4. 循环控制：
    1. 最多执行 MAX_STEPS（20）次
    2. 如果状态变为 FINISHED，提前退出
    3. 防止无限循环
5. 状态管理：
    1. IDLE：空闲状态
    2. THINKING：思考中
    3. EXECUTING：执行中
    4. FINISHED：完成
    5. ERROR：错误

#### 深入问题
+ **Q：为什么需要禁用自动工具执行？**
    - A：Spring AI 默认会自动执行工具，但我们需要手动控制流程，实现 Think-Execute 循环。禁用后，我们可以先获取工具调用信息，然后手动执行，更好地控制流程。
+ **Q：如何防止无限循环？**
    - A：设置了 MAX_STEPS（20）限制，最多执行 20 轮循环。同时，Agent 可以调用 terminate 工具明确结束任务。

### 4.1.2 工具调用机制是如何设计的？
#### 回答要点
1. 工具定义和注册
2. 工具选择机制
3. 工具执行流程
4. 结果处理

#### 标准回答
工具调用机制的设计

1. 工具定义

```java
@Tool(name = "getWeather", description = "获取天气信息")
public String getWeather(String city) {
    return "北京：晴天，25°C";
}
```

2. 工具分类
    1. 固定工具（Fixed Tools）：KnowledgeTool、DirectAnswerTool、TerminateTool
    2. 可选工具（Optional Tools）：DataBaseTools、EmailTools、FileSystemTools
3. 工具注册

```java
// 转换为 ToolCallback
MethodToolCallbackProvider provider = MethodToolCallbackProvider.builder()
    .toolObjects(tool1, tool2, tool3)
    .build();
List<ToolCallback> tools = Arrays.asList(provider.getToolCallbacks());
```

4. 工具选择
    1. Think 阶段，LLM 分析任务
    2. 根据工具描述，决定调用哪个工具
    3. 传入工具参数
5. 工具执行
    1. ToolCallingManager.executeToolCalls() 执行工具
    2. 获取工具返回结果
    3. 创建 ToolResponseMessage
6. 结果处理
    1. 将工具结果添加到对话历史
    2. LLM 根据结果继续思考
    3. 如果需要，继续调用其他工具

#### 深入问题
+ **Q：如何确保工具调用的准确性？**
    - A：通过清晰的工具描述（description），LLM 能够准确理解工具功能。同时，工具参数类型明确，减少参数解析错误。
+ **Q：工具调用失败怎么办？**
    - A：工具方法内部有异常处理，返回错误信息。LLM 可以根据错误信息调整策略，或调用其他工具。

## 4.2 RAG 检索流程
### 4.2.1 RAG 检索流程是怎样的？
#### 回答要点
1. 文档处理流程
2. Embedding 生成
3. 向量存储
4. 相似度搜索
5. 结果返回

#### 标准回答
RAG 检索的完整流程：

1. 文档上传
    1. 用户上传 Markdown 文档
    2. 保存文档到文件系统
    3. 创建文档记录到数据库
2. 文档解析
    1. 使用 Flexmark 解析 Markdown
    2. 按章节（# 标题）分块
    3. 每个章节作为一个 chunk
3. Embedding 生成
    1. 对每个 chunk 的标题生成 Embedding
    2. 使用 BGE-M3 模型，生成 1024 维向量
    3. 调用本地/远程 Embedding 服务
4. 向量存储
    1. 创建 ChunkBgeM3 记录
    2. 存储 content（章节内容）和 embedding（向量）
    3. 使用 PostgreSQL vector(1024) 类型
5. 相似度搜索

```sql
SELECT content, embedding
FROM chunk_bge_m3
WHERE kb_id = CAST(#{kbId} AS uuid)
ORDER BY embedding <-> #{vectorLiteral}::vector
LIMIT 3
```

+ 将查询文本转换为向量
+ 使用余弦距离（<->）计算相似度
+ 返回 Top-3 最相似的文档片段
6. 结果返回
    1. 将检索到的文档片段作为上下文
    2. LLM 基于上下文生成回答
    3. 返回给用户

#### 深入问题
+ **Q：为什么对标题生成 Embedding 而不是内容？**
    - A：标题通常包含章节的核心信息，向量更能代表章节的语义。同时，标题长度适中，不会超出模型限制。
+ **Q：如何优化检索性能？**
    - A：使用 ivfflat 索引优化向量检索，检索速度提升 50%+。同时，限制检索数量（Top-3），减少计算量。

### 4.2.2 文档分块策略是什么？
#### 回答要点
1. 分块方式
2. 分块大小
3. 重叠处理

#### 标准回答
**文档分块策略**

1. 分块方式
    1. 按 Markdown 标题（#）分块
    2. 每个章节作为一个独立的 chunk
    3. 保留章节的层级结构
2. 分块大小
    1. 不固定大小，按章节自然分割
    2. 每个章节包含标题和内容
    3. 内容长度从几十字到几千字不等
3. 重叠处理
    1. 当前没有实现重叠
    2. 未来可以添加滑动窗口重叠
4. 元数据存储
    1. 存储章节标题到 metadata
    2. 存储文档 ID 和知识库 ID
    3. 便于追溯和过滤

**优势**

+ 保持章节的完整性
+ 语义更连贯
+ 检索结果更准确

#### 深入问题
+ **Q：为什么不使用固定大小的分块？**
    - A：固定大小分块可能会切断语义连贯的内容。按章节分块保持了内容的完整性，检索结果更准确。
+ **Q：如何处理长文档？**
    - A：长文档会被分成多个章节，每个章节独立存储和检索。检索时返回最相关的章节，而不是整个文档。

## 4.3 多模型支持
### 4.3.1 如何实现多模型支持？
#### 回答要点
1. 注册表模式
2. Bean 管理
3. 动态切换

#### 标准回答
多模型支持的实现

1. 创建多个 ChatClient Bean

```java
@Bean("deepseek-chat")
public ChatClient deepSeekChatClient(DeepSeekChatModel model) {
    return ChatClient.create(model);
}

@Bean("glm-4.6")
public ChatClient zhiPuAiChatClient(ZhiPuAiChatModel model) {
    return ChatClient.create(model);
}
```

2. 注册表管理

```java
@Component
public class ChatClientRegistry {
    private final Map<String, ChatClient> chatClients;
    
    public ChatClientRegistry(Map<String, ChatClient> chatClients) {
        // Spring 自动注入所有 ChatClient Bean
        this.chatClients = chatClients;
    }
    
    public ChatClient get(String modelName) {
        return chatClients.get(modelName);
    }
}
```

3. 动态切换

```java
// 根据 Agent 配置的模型名称获取 ChatClient
ChatClient chatClient = chatClientRegistry.get(agent.getModel());
```

4. 优势
    1. 解耦模型创建和使用
    2. 支持动态添加新模型
    3. 代码可扩展性强
    4. 无需修改代码即可支持新模型

#### 深入问题
+ **Q：如何添加新模型？**
    - A：只需添加新的 ChatClient Bean，配置 application.yaml，无需修改其他代码。注册表会自动识别新模型。
+ **Q：模型切换的性能影响？**
    - A：模型切换是即时的，没有性能影响。每个模型都是独立的 Bean，互不干扰。

## 4.4 SSE 实时推送
### 4.4.1 SSE 实时推送是如何实现的？
#### 回答要点
1. SSE 协议
2. 连接管理
3. 消息推送
4. 状态更新

#### **标准回答**
SSE 实时推送的实现

1. SSE 连接建立：

```java
@RequestMapping(value = "/connect/{chatSessionId}", 
                produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter connect(@PathVariable String chatSessionId) {
    return sseService.connect(chatSessionId);
}
```

2. 连接管理

```java
private final ConcurrentMap<String, SseEmitter> clients = new ConcurrentHashMap<>();

public SseEmitter connect(String chatSessionId) {
    SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);  // 30分钟超时
    clients.put(chatSessionId, emitter);
    
    emitter.onCompletion(() -> clients.remove(chatSessionId));
    emitter.onTimeout(() -> clients.remove(chatSessionId));
    emitter.onError((error) -> clients.remove(chatSessionId));
    
    return emitter;
}
```

3. 消息推送

```java
public void send(String chatSessionId, SseMessage message) {
    SseEmitter emitter = clients.get(chatSessionId);
    if (emitter != null) {
        String json = objectMapper.writeValueAsString(message);
        emitter.send(SseEmitter.event()
            .name("message")
            .data(json)
        );
    }
}
```

4. Agent 状态推送
    1. AI_PLANNING：规划阶段
    2. AI_THINKING：思考阶段
    3. AI_EXECUTING：执行阶段
    4. AI_DONE：完成状态
5. 前端接收

```javascript
const es = new EventSource(`/sse/connect/${chatSessionId}`);
es.addEventListener("message", (event) => {
    const message = JSON.parse(event.data);
    // 处理消息
});
```

#### 深入问题
+ **Q：为什么选择 SSE 而不是 WebSocket？**
    - A：SSE 更适合服务端单向推送的场景，实现更简单。WebSocket 需要双向通信，对于只需要推送的场景，SSE 更合适。
+ **Q：如何处理连接断开？**
    - A：使用 onCompletion、onTimeout、onError 回调，自动清理断开的连接。前端可以监听 error 事件，自动重连。

## 4.5 消息持久化
### 4.5.1 消息持久化策略是什么？
#### 回答要点
1. 消息类型
2. 持久化时机
3. 数据结构
4. 历史加载

#### 标准回答
消息持久化策略

1. 消息类型
    1. UserMessage：用户消息，立即持久化
    2. AssistantMessage：AI 回复，包含工具调用信息
    3. ToolResponseMessage：工具调用结果
2. 持久化时机
    1. 用户消息：用户发送后立即持久化
    2. AI 回复：Think 阶段生成后持久化
    3. 工具结果：Execute 阶段执行后持久化
3. 数据结构

```java
CREATE TABLE chat_message (
    id UUID PRIMARY KEY,
    session_id UUID NOT NULL,
    role VARCHAR(50) NOT NULL,  -- user, assistant, tool, system
    content TEXT NOT NULL,
    metadata JSONB,  -- 存储工具调用信息等
    created_at TIMESTAMPTZ NOT NULL
);
```

4. 历史加载
    1. 创建 Agent 时，加载会话的历史消息
    2. 恢复到 ChatMemory 中
    3. 保持对话上下文
5. 元数据存储
    1. tool_calls：工具调用信息（JSON）
    2. tool_response：工具响应信息（JSON）
    3. 便于追溯和调试

#### 深入问题
+ **Q：为什么需要持久化？**
    - A：持久化可以保存对话历史，用户下次对话时可以继续之前的上下文。同时，便于问题追溯和系统调试。
+ **Q：如何处理大量历史消息？**
    - A：使用 MessageWindowChatMemory，只保留最近的 N 条消息（默认 20 条）。加载历史时也只加载最近的消息，避免内存溢出。

## 4.6 数据库设计
### 4.6.1 数据库表设计有什么亮点？
#### 回答要点
1. 表结构设计
2. 索引优化
3. 数据类型选择
4. 外键关系

#### 标准回答
数据库设计的亮点

1. UUID 主键
    1. 使用 PostgreSQL 的 gen_random_uuid() 生成
    2. 分布式友好，避免主键冲突
    3. 安全性好，不易被猜测
2. JSONB 类型
    1. allowed_tools、allowed_kbs、chat_options 使用 JSONB
    2. 灵活的配置存储
    3. 支持 JSON 查询和索引
3. vector 类型
    1. chunk_bge_m3.embedding 使用 vector(1024)
    2. 支持向量相似度搜索
    3. 使用 ivfflat 索引优化
4. 外键关系
    1. document.kb_id → knowledge_base.id
    2. chunk_bge_m3.kb_id → knowledge_base.id
    3. chat_message.session_id → chat_session.id
    4. 保证数据一致性
5. 索引设计
    1. 主键索引：自动创建
    2. 外键索引：加速关联查询
    3. 向量索引：ivfflat 加速相似度搜索
    4. 时间索引：加速时间范围查询
6. 时间字段
    1. 使用 TIMESTAMPTZ 类型
    2. 自动记录创建和更新时间
    3. 支持时区转换

#### 深入问题
+ **Q：为什么使用 UUID 而不是自增 ID？**
    - A：UUID 在分布式环境下更安全，不会暴露业务信息。同时，PostgreSQL 的 UUID 性能也很好。
+ **Q：JSONB 和 JSON 的区别？**
    - A：JSONB 是二进制格式，查询性能更好，支持索引。JSON 是文本格式，存储空间更小，但查询性能较差。

## 4.7 异常处理
### 4.7.1 异常处理机制是什么？
#### 回答要点
1. 全局异常处理
2. 业务异常
3. 异常分类
4. 错误响应

#### 标准回答
异常处理机制

1. 全局异常处理器

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ApiResponse<Void> handleBizException(BizException e) {
        return ApiResponse.error(e.getMessage());
    }
    
    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return ApiResponse.error("系统异常，请稍后重试");
    }
}
```

2. 业务异常

```java
public class BizException extends RuntimeException {
    public BizException(String message) {
        super(message);
    }
}
```

3. 异常分类
    1. BizException：业务异常，返回给用户
    2. 系统异常：记录日志，返回通用错误信息
4. 统一响应格式

```java
public class ApiResponse<T> {
    private boolean success;
    private String message;
    private T data;
}
```

5. Agent 异常处理
    1. 捕获异常，设置状态为 ERROR
    2. 记录错误日志
    3. 返回错误信息给用户

#### 深入问题
+ **Q：如何区分业务异常和系统异常？**
    - A：业务异常（如"文档不存在"）使用 BizException，直接返回给用户。系统异常（如数据库连接失败）记录日志，返回通用错误信息。
+ **Q：Agent 执行失败怎么办？**
    - A：捕获异常，设置状态为 ERROR，记录错误日志。将错误信息通过 SSE 推送给前端，用户可以重试或联系管理员。

## 4.8 性能优化
### 4.8.1 做了哪些性能优化？
#### 回答要点
1. 数据库优化
2. 向量检索优化
3. 缓存策略
4. 并发处理

#### 标准回答
性能优化措施

1. 数据库优化
    1. 创建合适的索引（外键、时间、向量）
    2. 使用 ivfflat 索引优化向量检索
    3. 优化 SQL 查询，避免全表扫描
    4. 使用连接池，复用数据库连接
2. 向量检索优化
    1. 使用 ivfflat 索引，检索速度提升 50%+
    2. 限制检索数量（Top-3），减少计算量
    3. 使用余弦距离，计算效率高
3. 对话历史优化
    1. MessageWindowChatMemory 只保留最近 N 条消息
    2. 减少内存占用和查询时间
    3. 加载历史时只加载最近的消息
4. 并发处理
    1. 使用 ConcurrentHashMap 管理 SSE 连接
    2. Agent 执行使用异步处理（可选）
    3. 数据库连接池支持并发
5. 代码优化
    1. 使用 Lombok 减少样板代码
    2. 使用 Builder 模式，代码更简洁
    3. 避免不必要的对象创建

#### 深入问题
+ **Q：向量检索的性能瓶颈是什么？**
    - A：主要是向量相似度计算。使用 ivfflat 索引可以大幅提升性能。对于更大规模的数据，可以考虑使用 hnsw 索引。
+ **Q：如何进一步提升性能？**
    - A：可以引入缓存机制（Redis），缓存常用的检索结果。使用异步处理，提升并发能力。优化 Embedding 生成，使用批量处理。
