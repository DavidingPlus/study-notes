## 2.3 技术亮点深度解析

### 2.3.1 Agent Loop 设计

**技术点**：

* Think-Execute 循环机制
* 状态机管理
* 多轮工具调用

**实现亮点**：

```java
// 核心循环逻辑
for (int i = 0; i < MAX_STEPS && agentState != AgentState.FINISHED; i++) {
    if (think()) {  // Think 阶段：分析任务，决定动作
        execute();  // Execute 阶段：执行工具调用
    } else {
        break;  // 无工具调用，直接返回
    }
}
```

**技术价值**：

* 实现了自主决策和执行的能力
* 支持复杂的多步骤任务
* 可扩展性强，易于添加新功能

**面试回答**：

```plain
我设计并实现了 Think-Execute 循环机制，这是 Agent 的核心。
Think 阶段让 LLM 分析任务并决定是否需要调用工具，Execute 阶段
执行工具调用并处理结果。通过状态机管理循环流程，支持最多 20 轮
循环，能够处理复杂的多步骤任务。
```

### 2.3.2 注册表模式实现多模型支持

**技术点**：

* 设计模式：注册表模式
* Spring Bean 管理
* 动态模型切换

**实现亮点**：

```java
@Component
public class ChatClientRegistry {
    private final Map<String, ChatClient> chatClients;
    
    public ChatClientRegistry(Map<String, ChatClient> chatClients) {
        // Spring 自动注入所有 ChatClient Bean
        this.chatClients = chatClients;
    }
    
    public ChatClient get(String modelName) {
        return chatClients.get(modelName);
    }
}
```

**技术价值**：

* 解耦模型创建和使用
* 支持动态添加新模型
* 代码可扩展性强

**面试回答**：

```plain
我使用注册表模式实现多模型支持。通过 Spring 的依赖注入，将所有
ChatClient Bean 自动注入到 Map 中，Key 为模型名称。这样 Agent
可以根据配置动态选择模型，无需修改代码即可支持新模型。
```

### 2.3.3 自定义 TypeHandler 处理向量类型

**技术点**：

* MyBatis TypeHandler
* PostgreSQL vector 类型
* 类型转换

**实现亮点**：

```java
@MappedJdbcTypes(JdbcType.OTHER)
@MappedTypes(float[].class)
public class PgVectorTypeHandler extends BaseTypeHandler<float[]> {
    // 实现向量序列化和反序列化
    @Override
    public void setNonNullParameter(...) {
        // float[] -> "[1.0,2.0,3.0]" -> PostgreSQL vector
    }
    
    @Override
    public float[] getNullableResult(...) {
        // PostgreSQL vector -> "[1.0,2.0,3.0]" -> float[]
    }
}
```

**技术价值**：

* 解决了 Java 类型与 PostgreSQL 特殊类型的映射问题
* 代码复用，所有 Mapper 自动使用
* 类型安全，编译期检查

**面试回答**：

```plain
PostgreSQL 的 vector 类型是自定义类型，MyBatis 默认不支持。
我实现了 PgVectorTypeHandler，继承 BaseTypeHandler，处理
float[] 与 vector 类型的转换。通过注解标记，MyBatis 会自动
使用这个 TypeHandler，实现了类型无缝转换。
```

### 2.3.4 RAG 检索实现

**技术点**：

* 向量相似度搜索
* Embedding 生成
* 文档分块和索引

**实现亮点**：

```sql
-- 向量相似度搜索
SELECT content, embedding
FROM chunk_bge_m3
WHERE kb_id = CAST(#{kbId} AS uuid)
ORDER BY embedding <-> #{vectorLiteral}::vector
LIMIT #{limit}
```

**技术价值**：

* 实现了语义检索，而非关键词匹配
* 性能优秀，支持大规模数据

**面试回答**：

```plain
我实现了基于 pgvector 的 RAG 检索。文档上传后，使用 BGE-M3 模型
生成 Embedding，存储到 PostgreSQL 的 vector 类型字段。查询时，
将查询文本转换为向量，使用余弦距离（<->）进行相似度搜索，返回
最相关的文档片段。
```

### 2.3.5 SSE 实时通信

**技术点**：

* Server-Sent Events
* 服务端推送
* 连接管理

**实现亮点**：

```java
@Service
public class SseServiceImpl implements SseService {
    private final ConcurrentMap<String, SseEmitter> clients = new ConcurrentHashMap<>();
    
    public SseEmitter connect(String chatSessionId) {
        SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);
        clients.put(chatSessionId, emitter);
        return emitter;
    }
    
    public void send(String chatSessionId, SseMessage message) {
        SseEmitter emitter = clients.get(chatSessionId);
        emitter.send(SseEmitter.event().name("message").data(message));
    }
}
```

**技术价值**：

* 实现了服务端主动推送
* 用户体验好，实时看到 Agent 状态
* 比 WebSocket 更简单，适合单向推送

**面试回答**：

```plain
我使用 SSE 实现实时通信，让前端能够实时看到 Agent 的执行状态。
使用 ConcurrentHashMap 管理连接，Key 为会话 ID。Agent 执行时
会推送状态更新（THINKING、EXECUTING、DONE），前端实时展示，
提升了用户体验。
```

## 2.4 技术选型理由

### 2.4.1 为什么选择 Spring AI 而不是直接调用 API？

**理由**：

1. **统一接口**：不同模型使用相同接口，代码复用
2. **自动配置**：Spring Boot 自动配置，减少代码
3. **工具支持**：内置工具调用和记忆管理
4. **生态集成**：与 Spring 生态无缝集成

**对比**：

```plain
直接调用 API：
- 需要为每个模型写不同的调用代码
- 需要手动管理 HTTP 请求和响应
- 需要自己实现工具调用逻辑

使用 Spring AI：
- 统一接口，代码简洁
- 自动处理 HTTP 请求
- 内置工具调用支持
```

### 2.4.2 为什么选择 PostgreSQL + pgvector 而不是专门的向量数据库？

**理由**：

1. **系统简化**：不需要额外的数据库服务
2. **数据一致性**：结构化数据和向量数据在同一数据库
3. **事务支持**：支持 ACID 事务
4. **成熟稳定**：PostgreSQL 是成熟的关系型数据库

**对比**：

```plain
专门的向量数据库（Milvus、Qdrant）：
- 需要额外的服务部署
- 数据同步复杂
- 事务支持有限

PostgreSQL + pgvector：
- 单一数据库，部署简单
- 数据一致性好
- 完整的事务支持
```

### 2.4.3 为什么选择 MyBatis 而不是 JPA？

**理由**：

1. **SQL 控制**：可以精确控制 SQL，优化性能
2. **复杂查询**：向量相似度搜索需要自定义 SQL
3. **学习成本**：团队熟悉 MyBatis
4. **性能**：接近 JDBC 性能

**对比**：

```plain
JPA：
- 自动生成 SQL，难以优化
- 复杂查询需要写 JPQL
- 学习曲线陡峭

MyBatis：
- 直接写 SQL，易于优化
- 支持复杂查询
- 学习成本低
```

## 2.5 技术难点和解决方案

### 2.5.1 难点 1：工具调用流程控制

**问题**：\
Spring AI 默认会自动执行工具调用，但我们需要手动控制流程。

**解决方案**：

```java
ChatOptions chatOptions = DefaultToolCallingChatOptions.builder()
    .internalToolExecutionEnabled(false)  // 禁用自动执行
    .build();

// 手动控制流程
if (think()) {  // 有工具调用
    execute();  // 执行工具
}
```

**收获**：

* 理解了 Spring AI 的工具调用机制
* 学会了如何自定义工具调用流程
* 提升了问题分析和解决能力

### 2.5.3 难点 3：对话历史管理

**解决方案**：

\*\*问题：\

**解决方案：**

