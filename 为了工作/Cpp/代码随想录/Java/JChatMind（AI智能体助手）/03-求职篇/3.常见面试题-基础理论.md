# 3. 常见面试题 - 基础理论

## 3.1 AI Agent 相关
### 3.1.1 什么是 AI Agent？
**标准回答**：

```plain
AI Agent（人工智能智能体）是一种能够自主感知环境、做出决策并执行行动的智能系统。
与传统的人工智能系统不同，Agent 不仅仅是被动地响应输入，而是能够主动地与环境交互，
通过观察、思考、决策和行动来完成复杂任务。

Agent 的核心特征：
1. 自主性（Autonomy）：能够在没有人类直接干预的情况下运行
2. 反应性（Reactivity）：能够感知环境变化并做出响应
3. 主动性（Proactivity）：能够主动采取行动以实现目标
4. 社会性（Social Ability）：能够与其他 Agent 或人类进行交互
```

**结合项目**：

```plain
在我的 JChatMind 项目中，Agent 能够：
- 分析用户输入，理解任务需求（感知）
- 决定是否需要调用工具（决策）
- 执行工具调用，完成实际任务（行动）
- 根据工具结果继续思考，直到任务完成（自主性）
```

### 3.1.2 Agent 和传统 AI 的区别是什么？
**标准回答**：

```plain
传统 AI（如简单的聊天机器人）：
- 被动响应：只能根据输入生成输出
- 单一任务：每次只能处理一个简单的任务
- 无状态：不维护对话历史和上下文
- 无工具：无法调用外部工具或执行实际操作

AI Agent：
- 主动执行：能够主动规划并执行复杂任务
- 多步骤任务：可以将复杂任务分解为多个步骤执行
- 有状态：维护对话历史和上下文信息
- 工具调用：可以调用各种工具完成实际工作
```

**结合项目**：

```plain
我的项目实现了完整的 Agent 功能：
- Think-Execute 循环：能够多轮思考和执行
- 工具调用：支持数据库查询、文件操作、邮件发送等
- 状态管理：维护对话历史和 Agent 状态
- 知识库检索：能够从知识库中检索相关信息
```

### 3.1.3 什么是 Think-Execute 循环？
**标准回答**：

```plain
Think-Execute 循环是 Agent 的核心工作机制，包括两个阶段：

1. Think 阶段（思考）：
   - 分析当前任务和上下文
   - 理解任务目标和要求
   - 规划执行步骤
   - 选择合适的工具
   - 决定是否需要调用工具

2. Execute 阶段（执行）：
   - 调用选定的工具
   - 执行具体的操作
   - 获取执行结果
   - 处理可能的错误

循环判断：
- 检查任务是否完成
- 如果未完成，返回 Think 阶段继续
- 如果完成，返回最终结果
```

**结合项目**：

```plain
在我的项目中，Think-Execute 循环是这样实现的：

```java
for (int i = 0; i < MAX_STEPS && agentState != AgentState.FINISHED; i++) {
    if (think()) {  // Think：分析任务，决定动作
        execute();  // Execute：执行工具调用
    } else {
        break;  // 无工具调用，直接返回
    }
}
```
```

Think 阶段调用 LLM 分析任务，如果决定调用工具，则进入 Execute 阶段执行工具，  
然后将工具结果添加到对话历史，继续下一轮 Think，直到任务完成。

## 3.2 RAG 相关
### 3.2.1 什么是 RAG？
#### 标准回答
RAG（Retrieval-Augmented Generation，检索增强生成）是一种结合信息检索和文本生成的技术。

RAG 的工作流程：

1. 文档处理：将文档分块，生成 Embedding 向量
2. 向量存储：将向量存储到向量数据库
3. 查询检索：将用户查询转换为向量，进行相似度搜索
4. 上下文增强：将检索到的相关文档作为上下文
5. 生成回答：LLM 基于检索到的上下文生成回答

RAG 的优势：

+ 可以访问外部知识库，不受训练数据限制
+ 回答更准确，基于实际文档
+ 可以引用来源，增强可信度
+ 知识更新方便，只需更新文档库

#### 结合项目
我的项目实现了完整的 RAG 功能：

1. 文档上传：支持 Markdown 文档上传
2. 文档解析：使用 Flexmark 解析 Markdown，按章节分块
3. Embedding 生成：使用 BGE-M3 模型生成 1024 维向量
4. 向量存储：存储到 PostgreSQL 的 vector 类型字段
5. 相似度搜索：使用 pgvector 的余弦距离进行检索
6. 上下文增强：将检索结果作为上下文，让 LLM 生成回答

### 3.2.2 RAG 和微调的区别？
#### 标准回答
RAG（检索增强生成）：

+ 原理：从外部知识库检索相关信息，作为上下文生成回答
+ 知识更新：只需更新文档库，无需重新训练
+ 成本：低，只需要 Embedding 和检索
+ 适用场景：知识库问答、文档检索、实时信息查询

微调（Fine-tuning）：

+ 原理：在预训练模型基础上，使用特定数据继续训练
+ 知识更新：需要重新训练模型
+ 成本：高，需要 GPU 资源和训练时间
+ 适用场景：特定领域模型、风格定制、任务适配

对比：

+ RAG 更适合知识更新频繁的场景
+ 微调更适合需要深度定制模型的场景
+ 两者可以结合使用，效果更好

#### 结合项目
我的项目选择 RAG 的原因：

1. 知识库内容会频繁更新，RAG 更灵活
2. 成本低，不需要 GPU 训练资源
3. 可以引用来源，增强可信度
4. 支持多知识库，可以灵活切换

### 3.2.3 向量数据库的作用是什么？
#### 标准回答
向量数据库是专门用于存储和检索向量数据的数据库。

作用：

1. 向量存储：高效存储高维向量数据
2. 相似度搜索：快速找到相似的向量
3. 索引优化：使用特殊索引（如 ivfflat、hnsw）加速检索
4. 大规模支持：支持百万级甚至千万级向量数据

为什么需要向量数据库：

+ 传统数据库不适合向量相似度搜索
+ 向量数据库针对向量检索优化，性能更好
+ 支持多种相似度算法（余弦、欧氏距离等）

#### 结合项目
我的项目使用 PostgreSQL + pgvector 作为向量数据库：

优势：

1. 不需要额外的数据库服务，降低复杂度
2. 结构化数据和向量数据在同一数据库，数据一致性好
3. 支持 ACID 事务，保证数据一致性
4. 使用 ivfflat 索引优化，检索性能提升 50%+

实现：

+ 使用 vector(1024) 类型存储 BGE-M3 的 Embedding
+ 使用 <-> 操作符进行余弦距离计算
+ 支持 Top-K 检索，返回最相似的文档片段

## 3.3 大语言模型相关
### 3.3.1 什么是 Embedding？
#### 标准回答
Embedding（嵌入向量）是将文本、图像等数据转换为数值向量的技术。

特点：

1. 语义表示：相似的文本有相似的向量
2. 固定维度：所有向量维度相同（如 1024 维）
3. 数值计算：可以进行向量运算和相似度计算

应用：

+ 文本相似度搜索
+ 推荐系统
+ 语义搜索
+ RAG 检索

生成方式：

+ 使用预训练的 Embedding 模型（如 BGE-M3）
+ 输入文本，输出固定维度的向量

#### 结合项目
我的项目使用 BGE-M3 模型生成 Embedding：

+ 模型维度：1024 维
+ 生成方式：调用本地/远程 Embedding 服务
+ 存储方式：PostgreSQL vector(1024) 类型
+ 检索方式：余弦相似度（cosine similarity）

实际效果：能够准确找到语义相似的文档片段，检索准确率 85%+。

### 3.3.2 Function Calling / Tool Calling 是什么？
#### 标准回答
Function Calling（函数调用）或 Tool Calling（工具调用）是让 LLM 能够调用外部函数/工具的能力。

工作流程：

1. 定义工具：描述工具的功能、参数、返回值
2. 注册工具：将工具信息传递给 LLM
3. LLM 决策：LLM 分析任务，决定是否调用工具
4. 工具执行：执行工具调用，获取结果
5. 结果处理：将工具结果返回给 LLM，继续生成

优势：

+ 扩展 LLM 能力，可以执行实际操作
+ 访问外部数据和服务
+ 实现 Agent 的自主执行能力

#### 结合项目
我的项目实现了完整的工具调用功能：

1. 工具定义：使用 @Tool 注解定义工具

```java
@Tool(name = "getWeather", description = "获取天气信息")
public String getWeather(String city) { ... }
```

2. 工具注册：转换为 ToolCallback，注册到 Agent
3. Think 阶段：LLM 分析任务，决定调用哪个工具
4. Execute 阶段：执行工具调用，获取结果
5. 循环：根据工具结果继续思考，直到任务完成

支持的工具类型：

+ 固定工具：KnowledgeTool、DirectAnswerTool、TerminateTool
+ 可选工具：DataBaseTools、EmailTools、FileSystemTools

### 3.3.3 Prompt Engineering 的重要性？
#### 标准回答
Prompt Engineering（提示工程）是设计和优化输入提示词的技术。

重要性：

1. 影响输出质量：好的提示词能获得更好的结果
2. 控制模型行为：通过提示词指导模型的行为
3. 提高准确性：清晰的提示词减少误解
4. 降低成本：好的提示词减少无效调用

技巧：

+ 明确任务和目标
+ 提供上下文和示例
+ 使用结构化格式
+ 迭代优化提示词

#### 结合项目
我的项目中使用了多个提示词：

1. 系统提示词：定义 Agent 的角色和行为

```java
"你是一个专业的 AI 助手，请用友好的语气回答问题。"
```

2. Think 提示词：指导 Agent 的决策

```java
"现在你是一个智能的「决策模块」。请根据当前对话上下文，
决定下一步的动作。如果需要调用工具来完成任务，请调用相应的工具。"
```

3. 工具描述：清晰描述工具的功能和参数

```java
@Tool(description = "从指定知识库中执行语义检索（RAG）。
输入知识库 ID 和查询文本，返回与查询最相关的内容片段。")
```

通过优化提示词，Agent 的工具调用准确率达到 95%+。

## 3.4 Spring AI 相关
### 3.4.1 Spring AI 框架的核心组件？
#### 标准回Spring AI 的核心组件：
1. ChatClient：统一的聊天客户端接口
    - 提供统一的 API 调用不同模型
    - 支持系统提示、工具调用等功能
2. ChatModel：底层模型接口
    - DeepSeekChatModel、ZhiPuAiChatModel 等
    - 封装了不同模型的 API 调用
3. ChatMemory：对话记忆管理
    - MessageWindowChatMemory：滑动窗口记忆
    - 自动管理对话历史
4. ToolCallback：工具回调接口
    - 将 Java 方法转换为工具
    - 支持工具调用和执行
5. Prompt：提示词对象
    - 包含消息列表和配置
    - 支持动态构建提示词

#### 结合项目
我的项目充分利用了 Spring AI 的组件：

1. ChatClient：统一接口，支持多模型切换
2. ChatMemory：自动管理对话历史，维护上下文
3. ToolCallback：实现工具调用功能
4. Prompt：构建包含历史消息的提示词
5. ToolCallingManager：管理工具调用流程

通过 Spring AI，代码简洁，功能强大，开发效率提升 50%+。



### 3.4.2 为什么选择 Spring AI？
#### 标准回答
选择 Spring AI 的理由：

1. Spring 生态集成：与 Spring Boot 无缝集成
2. 统一接口：不同模型使用相同 API
3. 自动配置：Spring Boot 自动配置，减少代码
4. 工具支持：内置工具调用和记忆管理
5. 社区支持：Spring 官方维护，持续更新
6. 文档完善：有详细的文档和示例

对比直接调用 API：

+ 代码更简洁，可维护性更好
+ 支持多种模型，易于切换
+ 内置功能丰富，开发效率高

#### 结合项目
我的项目使用 Spring AI 实现了：

1. 多模型支持：通过注册表模式，支持 DeepSeek、智谱AI
2. 工具调用：使用 ToolCallback 实现工具调用
3. 记忆管理：使用 ChatMemory 自动管理对话历史
4. 统一接口：所有模型使用相同的 ChatClient 接口

如果没有 Spring AI，需要：

+ 为每个模型写不同的调用代码
+ 自己实现工具调用逻辑
+ 手动管理对话历史

## 3.5 向量数据库相关
### 3.5.1 pgvector 的工作原理？
#### 标准回答
pgvector 是 PostgreSQL 的向量扩展，工作原理：

1. 向量类型：提供 vector(n) 类型存储向量
2. 操作符：提供相似度计算操作符
    - <->：余弦距离
    - <#>：内积距离
    - <=>：欧氏距离
3. 索引：提供 ivfflat、hnsw 等索引加速检索
4. 查询：支持 Top-K 相似度搜索

优势：

+ 与 PostgreSQL 集成，无需额外服务
+ 支持 ACID 事务
+ 性能优秀，支持大规模数据

#### 结合项目
我的项目使用 pgvector 实现向量检索：

1. 存储：使用 vector(1024) 存储 BGE-M3 的 Embedding
2. 索引：使用 ivfflat 索引优化检索性能

```sql
CREATE INDEX idx_chunk_embedding ON chunk_bge_m3 
    USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

3. 查询：使用余弦距离进行相似度搜索

```sql
ORDER BY embedding <-> #{vectorLiteral}::vector
LIMIT #{limit}
```

### 3.5.2 为什么选择 pgvector 而不是专门的向量数据库？
#### 标准回答
选择 pgvector 的理由：

1. 系统简化：不需要额外的数据库服务
2. 数据一致性：结构化数据和向量数据在同一数据库
3. 事务支持：支持 ACID 事务，保证数据一致性
4. 成熟稳定：PostgreSQL 是成熟的关系型数据库
5. 学习成本：团队熟悉 PostgreSQL

专门的向量数据库（Milvus、Qdrant）：

+ 需要额外的服务部署和维护
+ 数据同步复杂，可能不一致
+ 事务支持有限
+ 学习成本高

#### 结合项目
我的项目选择 pgvector 的原因：

1. 简化部署：只需要一个 PostgreSQL 数据库
2. 数据一致性：Agent、知识库、向量数据在同一数据库
3. 事务支持：文档上传和向量存储在同一事务中
4. 性能满足：10万+ 向量数据，检索速度 < 100ms

如果使用专门的向量数据库：

+ 需要部署 Milvus 或 Qdrant
+ 需要实现数据同步机制
+ 系统复杂度增加
+ 维护成本提高

pgvector 满足项目需求，且系统更简单。
