# 常见面试题-项目相关

## 项目与架构类

1. **你这个项目是做什么的？**\
   是一个分布式网盘系统，包含注册登录、文件管理、分享、回收站等核心功能，后端按 auth/files/user/share/recycle/ai 模块拆分。
2. **为什么要做多模块拆分？你这个网盘怎么拆的？**\
   把高频变更域（文件、认证、用户）解耦，降低耦合和发布风险；同时便于团队并行开发和后续服务扩容。我按业务边界拆成了 files、share、recycle、user、auth、gateway和ai等，公共能力下沉到 networkdisk-common。

好处是：

```
1. 业务职责清晰，文件上传和分享过期清理互不影响。
2. 服务独立，比如搜索可以只改 files 模块。
3. 公共能力可以复用，比如登录切面、分布式锁、延迟队列统一封装。代价是跨模块调用复杂度上升，我用 Dubbo + Facade 做了收敛。
```

3\. **项目模块间怎么通信？为什么需要 Facade？**\
前端到后端主要是使用HTTP/REST通信，服务间通过 Dubbo 调用 API 层定义的接口，比如 auth 调 user 注册、调 files 创建根目录。业务模块提供 Facade 实现。Facade 的价值是：把“参数校验、异常包装、DTO 转换”统一起来，调用方不需要知道内部 Service 细节。比如注册后创建用户根目录，就是 auth 调 user + files Facade 串起来完成。
4\. **网关在项目里起什么作用？**\
网关模块有 Sa-Token 鉴权过滤配置，负责统一路由和入口鉴权；不过当前开发环境前端多为直连各业务服务端口联调。
5\. **项目的核心数据模型是怎样的？**\
核心是 user\_file（用户视图文件树）和 file（物理文件元数据）分离，user\_file.parent\_id 维护层级关系，便于复制/移动/回收站操作。
6\. **为什么要把用户文件和物理文件分开？**\
同一物理文件可被多个用户引用，用户侧主要改user\_file的关系，避免重复物理存储，支持秒传和软删除。
7\. **你们项目里“目录树”是怎么组织的？**\
查询当前用户所有文件夹记录后，在内存按 parentId 分组组装成树，返回 parentId=0 的根节点列表。
8\. **项目里有哪些典型跨服务流程？**\
注册流程是 auth -> userFacade.register -> user表落库 -> filesFacade.createUserRootFile，最终完成账号和根目录初始化。
9\. **项目还有哪些改进空间？**

后期可以更新个人信息管理模块，文件版本控制与用户空间配额管理等。

## 认证与权限类

1. **注册流程是怎样的？**\
   /api/v1/auth/register 校验参数后调用用户服务注册，再调用文件服务创建用户根目录，保证新用户首次登录可直接进入文件空间。
2. **登录态是怎么校验的？你们登录态是怎么校验的？**

登录后发 JWT，并把 token 放 Redis（USER\_LOGIN\_{userId}）。每次请求由 AOP 切面校验：

1. 业务职责清晰，文件上传和分享过期清理互不影响。

2. 服务演进独立，比如搜索可以只改 files 模块。

3. 公共能力复用，比如登录切面、分布式锁、延迟队列统一封装。代价是跨模块调用复杂度上升，我用 Dubbo + Facade 做了收敛。

4. **为什么要用 Redis 再做一次 token 比对？**\
   支持主动失效和服务端可控登出，不只依赖 JWT 自身过期时间，便于风控和会话管理。

5. **前端有没有做权限保护？**\
   有路由守卫，requiresAuth 页面未登录会跳 /login；但这只是体验层，真正安全仍在后端鉴权。

6. **登录参数校验做了什么？**\
   登录/注册分开 VO，对 email 格式、密码长度、昵称非空等做了 Bean Validation，避免参数污染到业务层。

7. **你如何处理“未登录访问”异常？**\
   统一异常处理器返回标准 Result 结构，前端拦截到未登录状态后清 token 并跳转登录页。

8. **你们 token 失效后前端怎么处理？**\
   Axios 响应拦截器检测异常码或 401，调用 logout 清理状态并跳转登录页，避免脏登录态。

9. **你怎么看当前认证实现的风险点？**\
   我会主动讲两个：登录密码校验要严格比对 hash；鉴权机制要收敛成一套，减少“网关与业务服务规则不一致”风险。

10. **如果要增强安全性，你会先做什么？**\
    密码从 MD5 升级为 BCrypt/Argon2；登录加限流和验证码；token 黑名单与设备维度会话控制。

11. **你们怎么拿到当前用户ID？**\
    鉴权切面校验后写入 UserIdUtil（ThreadLocal），控制器/服务通过 UserIdUtil.get() 读取用户上下文。

12. **ThreadLocal 会有什么问题？**\
    线程复用下如果不清理会串用户上下文；生产实践要在请求完成后统一 remove，保证线程安全。

## 文件功能类

1. **断点续传是怎么做的？端到端说一下。**

流程是：

前端先算文件 MD5 作为 identifier。先调秒传接口，命中则只写用户文件映射；未命中走分片上传：POST /file/chunk-upload。

前端通过 GET /file/chunk-upload?identifier=... 获取已传分片，跳过重传。

全部分片就绪后调用 POST /file/merge。

后端按 chunkNumber 排序合并，并清理分片记录和分片文件。

2. **文件列表接口核心查询条件是什么？**\
   user\_id + deleted + parent\_id + file\_type，并走组合索引，支持按目录和类型筛选。
3. **目录树接口如何保证只返回目录？**\
   查询条件限制 folder\_flag=1，再按 parent\_id 组装树结构，不把普通文件节点放进目录树。
4. **重命名接口都做了哪些校验？**\
   答：校验目标文件存在、归属当前用户、新旧名字不相同、同目录下名称不冲突，然后再更新 filename。
5. **移动和复制的核心区别是什么？**\
   答：移动是更新现有记录的 parent\_id；复制是递归创建新记录并生成新 id，形成一棵新子树。
6. **复制为什么要递归？**\
   答：目录复制不仅复制目录节点，还要复制全部子文件/子目录关系，递归最直接表达树结构克隆。
7. **移动时怎么避免“移动到自己的子目录”？**\
   答：先收集被操作目录及其全部子目录 ID，若目标目录在集合内则拒绝，避免形成循环父子关系。
8. **复制时也要做这个校验吗？**\
   答：要做，同样不能把目录复制到自己的子孙目录下，否则会出现逻辑环和无限递归风险。
9. **同名冲突怎么处理？**\
   答：统一走 handleDuplicateFilename，按“文件名(1)(2)...”策略自动重命名，避免接口直接报冲突失败。
10. **文件删除是物理删还是逻辑删？**\
    答：文件模块删除是逻辑删，更新 deleted 字段，后续由回收站管理恢复或彻底删除。
11. **为什么先逻辑删除？**\
    答：降低误删不可恢复风险，符合网盘场景预期，也便于做审计和恢复窗口。
12. **你们怎么实现秒传？**\
    答：按文件 identifier 查可复用的物理文件记录，命中后只新增 user\_file 关系，不重复上传物理内容。
13. **大文件上传怎么做？**\
    答：支持分片上传、已上传分片查询、合并分片。分片上传用了分布式锁防并发重复写。
14. **怎么保证分片并发上传不乱、不重复？**

我用了三层保护：

1. 分布式锁：userId + identifier 维度加锁。

2. 数据库唯一键：(identifier, chunk\_number, create\_user)。

3. 写入前清理失效记录，再判断分片是否已存在。

这样即使重试/并发，也不会多写同一分片。\
15\. **分片上传为什么需要分布式锁？**\
答：同一用户+同一文件标识可能并发上传，锁住关键路径可防止分片状态竞争和重复合并。\
16\. **下载/预览怎么区分？**\
答：都先通过 user\_file 找到 real\_file\_id，再读物理文件流；下载设附件响应头，预览走对应 content-type。\
17\. **文件复制会不会复制物理文件？**\
答：当前是“元数据复制”，复用 real\_file\_id，所以不会重复占用物理存储空间。\
18\. **文件移动会影响物理文件吗？**\
答：不会，移动只改变用户视图树中的父子关系，不变更物理文件路径。\
19\. **批量删除如何保证同一用户？**\
答：先查出选中记录，校验 userId 集合只有一个且等于当前用户，再执行逻辑删除。\
20\. **你觉得文件模块还可优化哪里？**\
答：批量操作应补“请求ID数量与查出数量一致性校验”；复杂树操作可加事务和审计日志。\
21\. **目录树性能怎么优化？**\
答：先按用户过滤再全量目录查询，一次内存组树；大规模用户可做分页加载或缓存热门目录分支。\
22\. **为什么 user\_file 里有 file\_id/update\_time 兼容字段？**\
答：为兼容历史 mapper SQL 字段映射，底层通过生成列映射到 id、gmt\_modified，减少改造成本。\
23\. **你们接口里 ID 为什么是字符串？**\
答：对外是加密ID字符串，避免直接暴露数据库自增/雪花ID，降低枚举风险。\
24\. **前端对文件操作是如何刷新状态的？**\
答：操作成功后重新拉当前目录列表，并在目录场景下同步刷新面包屑状态。\
25\. **下载怎么避免内存溢出？**

不做整文件读内存，走流式输出：本地文件通过 FileChannel.transferTo 写到响应流。分享下载通过 InputStream.transferTo(outputStream)。核心思想是“边读边写”，大文件下载内存占用稳定。

26. **你们支持文件夹下载吗？**

当前代码只支持单文件下载/预览，文件夹和批量 ZIP 还没落地。如果要做 ZIP 下载，我会采用“临时目录 + 流式压缩 + 限流 + 清理任务”。

## 分享模块

1. **分享过期怎么处理？**

双保险兼顾实时性和数据清理：

```
1. 访问时实时校验 shareEndTime，过期直接拒绝。
2. 创建分享时投递 Redisson 延迟队列，到期执行逻辑删除。
```

2\. **支持手动续期吗？**

当前不支持。后端没有续期接口，前端按钮是占位。\
如果扩展，我会加：

1. PATCH /share/expire 接口

2. 更新 DB 到期时间

3. 取消旧延迟任务并重投新任务

4. 幂等校验防重复续期

## 搜索模块相关

1. **为什么用 ES，不直接 MySQL like？**

MySQL like 在大规模下性能和扩展性差。ES 更适合全文检索、复杂匹配和横向扩展。当前实现是 ES 优先，空结果或不可用时回退 MySQL，保证可用性。

2. **MySQL 到 ES 怎么同步？一致性怎么保证？**

用 Canal 订阅 user\_file binlog：

* INSERT/UPDATE -> upsert ES
* DELETE -> delete ES

批处理成功 ack，失败 rollback 重试，比业务代码双写耦合更低。\
3\. **如果 ES 宕机，搜索会挂吗？**

不会直接挂。files 模块里有回退逻辑，ES 查不到或不可用时走 MySQL。代价是性能和搜索能力下降，但功能可用。

## AI 模块相关

1. **项目里的 AI 模块主要做什么？**\
   答：当前不是通用聊天模块，而是围绕单文件能力做增强，主要提供四类能力：文档索引、文档摘要、文档标签、单文件问答。HTTP 接口分别是 `/api/v1/ai/files/index`、`/summary`、`/tags`、`/question`，另外还有一个免登录的 `/api/v1/ai/capabilities` 用来查看能力状态。
2. **为什么把 AI 单独拆成一个服务？**\
   答：模型调用、Apache Tika 文档解析、pgvector/PostgreSQL 向量检索、异步预热这些能力都比普通文件 CRUD 更重，单独拆服务可以把依赖和资源消耗隔离开，也方便后续独立扩容。
3. **AI 模块的整体处理链路是什么？**\
   答：前端传 `fileId` 后，AI 服务先按当前登录用户读取文件，再把文件字节交给 Tika 解析成纯文本，然后按段落切块、生成 embedding、写入 pgvector。摘要和标签是把文档内容交给模型生成；单文件问答则先做向量召回，再把召回片段拼成上下文去回答。
4. **AI 服务怎么拿到文件内容？为什么不直接查文件表？**\
   答：AI 服务不直接访问 files 模块的表，而是通过 Dubbo 调 `FileFacadeService.getFileReadInfo`。files 模块先校验当前用户是否有权限访问该 `user_file`，再返回 `realPath`、`filename`、`realFileId` 等信息，最后 AI 服务再通过 `StorageEngine` 去读原始文件字节。这样权限和存储实现都收敛在 files 模块里。
5. **AI 模块怎么保证用户隔离？**\
   答：AI 接口除了 `/capabilities` 外都走登录态，从 `UserIdUtil` 取当前用户。读文件时，files Facade 会校验 `request.userId` 和 `user_file.user_id` 一致，还会拦掉文件夹。向量表和结果表也都是按 `user_id + user_file_id` 组织，不会跨用户混查。
6. **为什么这里用了 Apache Tika？**\
   答：因为当前要支持多种文档格式，像 `pdf/doc/docx/txt/md/csv/xls/xlsx/ppt/pptx/html/xml/json/sql/java/js/css` 都在支持列表里。Tika 负责统一做类型探测和正文提取，解析后再做换行清洗、空白压缩和文本截断。
7. **文档索引是怎么做的？**\
   答：`/files/index` 先判断 pgvector 是否可用；如果当前文件已经有索引且 `forceReindex=false`，就直接返回已有索引元信息，不重复计算。否则重新读取文件、解析文本、切块、批量生成 embedding，然后覆盖 `ai_document_index` 和 `ai_document_chunk_vector` 两张表，最后把旧的摘要/标签缓存清掉。
8. **为什么要做分块？当前分块策略是什么？**\
   答：长文档不能整篇都塞给模型，所以要先切 chunk，既便于向量检索，也便于控制上下文长度。当前实现是先按空行切成文档块，再对每个块按 `chunk-size=1200`、`chunk-overlap=200` 滑窗切分，优先在空白处分界，并按 `字符数 / 4` 估算 token 数。
9. **为什么问答要走 pgvector，不直接把全文发给模型？**\
   答：直接发全文成本高，而且长文档容易超上下文窗口。pgvector 存的是每个 chunk 的 embedding，提问时先把问题向量化，再在当前文件的 chunk 里按向量距离取最相关的前 `topK` 片段，这样模型看到的是更聚焦的上下文。
10. **单文件问答具体是怎么做的？**\
    答：先检查该文件是否已有索引；如果有，就把问题做 embedding，在 `ai_document_chunk_vector` 里取前 `retrievalTopK=6` 个相似片段，并把这些片段拼成上下文。如果没索引，或者向量库不可用，就退化成“实时读文件 + Tika 解析 + 截断正文”后直接问模型。当前只支持单文件问答，不支持多文件聚合问答。
11. **摘要和标签结果会缓存吗？**\
    答：会，落在 `ai_document_result` 表里。摘要只有在“没有自定义 prompt”的情况下才会命中缓存；如果用户传了自定义 prompt，就每次重新生成。标签会优先复用已存结果，只要库存标签数量不少于本次请求的 `topK`。
12. `forceReindex`\*\* 的作用是什么？\*\*\
    答：默认同一个文件只要已经建过索引，就直接返回，不再重复做解析和 embedding。传 `forceReindex=true` 时会重建当前文件索引，并清掉旧摘要和旧标签，避免索引内容和缓存结果不一致。
13. **文件上传后会不会自动触发 AI 处理？**\
    答：会，但只对支持的非文件夹类型生效。files 模块在保存 `user_file` 成功后，会在事务提交后发送 `ai-document-warmup` 消息；AI 服务消费后会按顺序执行“建索引 -> 生成摘要 -> 生成标签”。
14. **AI 模块有哪些降级策略？**\
    答：有两层。第一层是模型侧，如果没有装配真实 Provider，就会落到 `MockAiProviderClient` 和 `MockEmbeddingClient`；第二层是向量库侧，如果 pgvector 没启用，就会注入 `DisabledVectorStore`。这时索引接口不可用，但摘要、标签和问答接口本身仍然可以走“即时解析文档”的方式运行，只是没有真正的向量召回能力。
15. `/capabilities`\*\* 接口有什么用？\*\*\
    答：它相当于一个 AI 探活和配置透出接口，前端抽屉打开后会先调它。返回值里会带当前 provider、chatModel、是否 mock、向量库是否可用、embedding 维度、chunk 配置，以及当前声明支持的 feature。
16. **当前 AI 模块的边界和风险点是什么？**\
    答：边界上，它目前只支持单文件问答，不支持多文件检索、会话记忆、流式输出、重排序和精确页码级引用。风险点上，异步预热链路默认先做索引，如果 pgvector 关闭，这条预热线路会在索引阶段失败，所以当前“自动预热”实际上依赖向量库处于可用状态。

## 回收站类

1. **回收站的本质是什么？**\
   答：基于 user\_file.deleted 的二阶段删除机制：先逻辑删除进回收站，再可还原或彻底删除。
2. **回收站列表查的是什么数据？**\
   答：查 user\_file 中 deleted != 0 且 user\_id = 当前用户 的记录，按修改时间倒序返回。
3. **回收站还原怎么实现？**\
   答：按用户和ID集合更新记录，deleted 置 0，并更新 update\_user/gmt\_modified。
4. **回收站彻底删除怎么实现？**\
   答：按用户和ID集合执行 DELETE 物理删记录，只删除已在回收站中的数据（deleted != 0）。
5. **如何保证用户数据隔离？**\
   答：SQL 全部强制带 user\_id 条件，回收站增删改查都在用户维度隔离。
6. **回收站支持批量吗？**\
   答：支持，接口接收 fileIds 集合，服务层在事务中批量更新或删除。
7. **回收站和文件删除模块的边界是什么？**\
   答：文件模块负责“放入回收站”（逻辑删除），回收站模块负责“恢复/彻底删除”。
8. **回收站功能有哪些联调风险点？**\
   答：常见是接口方法与前端调用不一致、fileIds 结构不一致、返回码判断不一致、前端代理未配置。
9. **回收站数据为什么不单独建表？**\
   答：当前设计复用 user\_file，简化模型和恢复逻辑；单表即可满足“可恢复删除”核心诉求。
10. **彻底删除后能恢复吗？**\
    答：不能，彻底删除是物理删除 user\_file 记录，属于不可逆操作。
11. **回收站是否影响物理文件表 file？**\
    答：当前回收站操作主要作用于 user\_file 关系，不直接删除物理文件元数据。
12. **你会怎么加强回收站？**\
    答：补自动过期清理策略、彻底删除审计日志、恢复冲突处理（原目录不存在时的回落策略）。

## 数据库、性能、稳定性与排障

1. **你怎么做索引设计？**\
   答：围绕高频查询场景（用户、删除状态、父目录、类型）建立组合索引，优先保证列表和目录查询。
2. **你们用缓存了吗？**\
   答：用户查询用 JetCache 注解缓存；登录态依赖 Redis；并发场景用 Redisson 锁。
3. **遇到过 Dubbo 超时怎么处理？**\
   答：先按调用链定位慢点（下游接口/DB），再优化 SQL 和调用顺序，必要时调整超时阈值并加降级兜底。
4. **你怎么处理参数非法导致的 400？**\
   答：统一用 @Valid/@Validated + 全局异常处理器，标准化返回，前端可统一提示和重试。
5. **如何做问题定位？**\
   答：按“请求入口日志 -> 参数 -> RPC耗时 -> SQL行为 -> 返回结构”逐层排查，先复现再最小改动修复。
6. **你如何保证批量操作的稳定性？**\
   答：服务层事务包裹、入参非空校验、用户归属校验、失败回滚，避免部分成功造成脏数据。
7. **你会怎么讲一次真实排障经历？**\
   答：我会讲“登录后取不到用户信息”：先看后端校验异常，再查前端传参和接口字段，最后统一 VO 与请求字段并修复。
8. **项目里错误处理是怎么统一的？**\
   答：GlobalWebExceptionHandler 统一接管校验异常、业务异常、系统异常，响应格式统一为 Result。
9. **你觉得这项目最需要补的工程化能力是什么？**\
   答：接口契约自动化测试（后端契约 + 前端集成），以及 CI 中的模块化联调检查。
10. **如果面试官问“你下一步会重构什么”？**\
    答：第一步收敛鉴权体系；第二步统一接口契约与响应码；第三步补回收站和文件批量操作的端到端测试。
