# 常见面试题-基础理论

# 1. Spring 框架

## 1.1 什么是 Spring？它的核心特性是什么？

Spring 是一个轻量级 Java 开发框架，核心目标是**简化企业级开发**。它最核心的两个思想是：

* **IoC（控制反转）**：对象的创建和依赖关系交给 Spring 容器管理
* **AOP（面向切面编程）**：将日志、事务、权限等公共逻辑从业务代码中抽离出来统一处理

Spring 的优点：

* 降低对象之间耦合
* 提高代码可维护性和可测试性
* 提供事务管理、MVC、数据访问等完整生态

***

## 1.2 什么是 IoC？什么是 DI？

### IoC（控制反转）

传统开发中，对象由程序员主动 new 出来；IoC 是指把对象的创建和管理权交给 Spring 容器。

### DI（依赖注入）

DI 是 IoC 的实现方式。Spring 在创建对象时，把它依赖的其他对象自动注入进去。

常见注入方式：

* 构造器注入
* setter 注入
* 字段注入（`@Autowired`）

***

## 1.3 BeanFactory 和 ApplicationContext 的区别是什么？

两者都是 Spring 容器。**BeanFactory 更底层，ApplicationContext 功能更完整，实际开发几乎都用 ApplicationContext。**

### BeanFactory

* Spring 最基础的容器
* 采用延迟加载，只有获取 Bean 时才创建对象
* 功能较简单

### ApplicationContext

* 是 BeanFactory 的子接口
* 功能更强大，通常开发中使用它
* 支持国际化、事件机制、AOP、自动注册 BeanPostProcessor 等
* 默认单例 Bean 会在容器启动时初始化

***

## 1.4 Spring Bean 的生命周期是什么？

\*\*\*\*Spring Bean 的生命周期大致如下：

1. 实例化 Bean
2. 依赖注入
3. 执行 `Aware` 接口相关方法
4. 执行 `BeanPostProcessor` 的前置处理
5. 执行初始化方法（如 `afterPropertiesSet`、`init-method`）
6. 执行 `BeanPostProcessor` 的后置处理
7. Bean 可以被使用
8. 容器关闭时执行销毁方法（如 `destroy-method`）

如果面试官追问，可以补充：

* 初始化前后扩展点：`BeanPostProcessor`
* 实例化前后扩展点：`InstantiationAwareBeanPostProcessor`

***

## 1.5 Spring 中 Bean 的作用域有哪些？

常见作用域有：

* **singleton**：单例，默认作用域，整个容器中只有一个 Bean
* **prototype**：多例，每次获取都会创建新对象
* **request**：每次 HTTP 请求创建一个 Bean
* **session**：每个 Session 创建一个 Bean
* **application**：整个 Web 应用共享一个 Bean

**常考点：**\
Spring 默认作用域是 **singleton**。

***

## 1.6 Spring 是如何解决循环依赖的？

Spring 解决的是**单例 Bean 的 setter 注入循环依赖**，主要依靠**三级缓存**。

### 三级缓存：

* **一级缓存**：`singletonObjects`，存放完全初始化好的单例对象
* **二级缓存**：`earlySingletonObjects`，存放提前曝光的半成品对象
* **三级缓存**：`singletonFactories`，存放对象工厂，用于生成早期对象引用

### 解决思路：

当 A 依赖 B，B 又依赖 A 时：

1. A 实例化后先放入三级缓存
2. A 依赖 B，开始创建 B
3. B 又依赖 A，此时从三级缓存中拿到 A 的早期引用
4. B 完成初始化
5. A 再完成初始化

### 注意：

Spring **不能解决**以下情况：

* 构造器循环依赖
* 原型 Bean 的循环依赖

***

## 1.7 @Autowired 和 @Resource 的区别是什么？

Spring 项目中更常用 `@Autowired`，想精确按名称注入时可用 `@Resource`

### `@Autowired`

* Spring 提供的注解
* 默认按**类型**注入
* 可配合 `@Qualifier` 按名称注入

### `@Resource`

* JSR 规范提供的注解
* 默认按**名称**注入
* 找不到再按类型注入（具体实现和环境有关）

***

## 1.8 Spring 事务失效的场景有哪些？

Spring 的事务本质是 AOP 代理，**同类内部方法调用不会经过代理对象，所以事务会失效。**

常见事务失效场景：

1. 方法不是 public
2. 同一个类内部自调用
3. 异常被吃掉，没有抛出
4. 抛出的不是运行时异常，且没配置回滚
5. 数据库引擎不支持事务
6. 没有被 Spring 容器管理
7. 多线程场景下事务无法传播到新线程

***

# 2. Spring AOP

## 2.1 什么是 AOP？

\_**AOP **\_即面向切面编程。\
它的核心思想是：把日志、事务、权限校验、性能监控等**横切关注点**从业务代码中抽离出来，统一增强。

AOP 的好处：

* 减少重复代码
* 降低业务代码耦合
* 提高代码可维护性

***

## 2.2 AOP 的底层实现是什么？

*\_**Spring AOP 的底层是**\_*动态代理**。

两种实现方式：

* **JDK 动态代理**：基于接口代理
* **CGLIB 动态代理**：基于继承代理目标类

### 选择规则：

* 如果目标对象实现了接口，默认优先用 **JDK 动态代理**
* 如果没有实现接口，则用 **CGLIB**
* 也可以强制使用 CGLIB

***

## 2.3 JDK 动态代理和 CGLIB 的区别是什么？

有接口优先 JDK，无接口使用 CGLIB，Spring Boot 中很多场景也会直接使用 CGLIB。

### JDK 动态代理

* 必须基于接口
* 生成的是接口的代理对象
* Java 原生支持

### CGLIB

* 不需要接口
* 通过继承目标类生成子类代理
* 不能代理 `final` 类和 `final` 方法

***

## 2.4 AOP 中的核心概念有哪些？

* **Aspect（切面）**：封装横切逻辑的类
* **JoinPoint（连接点）**：程序执行过程中可被拦截的点
* **Pointcut（切点）**：对连接点的筛选规则
* **Advice（通知）**：切面在特定时机执行的增强逻辑
* **Weaving（织入）**：把切面应用到目标对象生成代理对象的过程
* **Target（目标对象）**：被代理、被增强的对象

***

## 2.5 Spring AOP 有哪些通知类型？

常见通知类型：

* **Before**：前置通知，方法执行前
* **After**：后置通知，方法执行后
* **AfterReturning**：返回通知，方法正常返回后
* **AfterThrowing**：异常通知，方法抛异常后
* **Around**：环绕通知，功能最强，可控制目标方法是否执行

开发中最常用的是 **Around**，因为它既能做前置逻辑，也能做后置逻辑。

***

## 2.6 Spring AOP 和 AspectJ 的区别是什么？

**Spring AOP 更轻量，适合业务开发；AspectJ 更强大，适合复杂切面场景。**

### Spring AOP

* 只支持方法级别的连接点
* 基于动态代理实现
* 功能相对简单，但足够应对大部分业务开发

### AspectJ

* 功能更强
* 支持字段、构造器等更多连接点
* 一般通过编译期织入或类加载期织入实现

***

## 2.7 为什么 Spring 事务是基于 AOP 实现的？

因为事务本质上也是一种**通用的横切逻辑**。\
比如方法执行前开启事务，执行成功提交事务，执行失败回滚事务，这些逻辑和具体业务无关，适合通过 AOP 统一处理。所以 `@Transactional` 本质上就是通过 AOP 在目标方法前后增强事务逻辑。

***

# 3. Dubbo

## 3.1 什么是 Dubbo？

Dubbo 是一个高性能的 **Java RPC 分布式服务框架**。它主要用于微服务或分布式系统中的服务调用。

核心能力包括：

* 服务注册与发现
* 远程调用
* 负载均衡
* 容错机制
* 服务治理

***

## 3.2 Dubbo 的架构组成有哪些？

\*\*\*\*Dubbo 核心角色通常有：

* **Provider**：服务提供者
* **Consumer**：服务消费者
* **Registry**：注册中心，如 Zookeeper、Nacos
* **Monitor**：监控中心
* **Container**：服务运行容器

### 调用流程：

1. Provider 启动后将服务注册到注册中心
2. Consumer 从注册中心订阅服务列表
3. Consumer 通过负载均衡选择 Provider 发起调用
4. 调用结果返回给 Consumer

***

## 3.3 Dubbo 和 Spring Cloud 有什么区别？

\*\*Dubbo 擅长高性能 RPC，Spring Cloud 擅长微服务全套生态。\*\*现在也可以结合使用，例如 Spring Cloud Alibaba + Dubbo。

### Dubbo

* 更专注于 **RPC 调用**
* 性能高，适合 Java 内部服务调用
* 服务治理能力强

### Spring Cloud

* 是一整套微服务生态
* 包括配置中心、网关、链路追踪、熔断等全家桶
* 更偏向 HTTP/REST 风格和云原生治理

***

## 3.4 Dubbo 支持哪些通信协议？

**Dubbo 默认常用的是 Dubbo 协议，底层通常基于 Netty 实现高性能通信。**

常见协议有：

* **Dubbo 协议**：默认协议，单一长连接，适合小数据量高并发场景
* **HTTP 协议**
* **RMI 协议**
* **Hessian**
* **gRPC（三方扩展或集成场景）**

***

## 3.5 Dubbo 的负载均衡策略有哪些？

\*\*\*\*常见策略：

* **Random**：加权随机，默认策略，简单且效果好
* **RoundRobin**：加权轮询
* **LeastActive**：最少活跃调用数
* **ConsistentHash**：如果希望同一参数总落到同一台机器上，可用一致性哈希

***

## 3.6 Dubbo 的容错策略有哪些？

\*\*\*\*常见容错策略：

* **Failover**：失败自动切换，是默认策略，查询类接口常用
* **Failfast**：快速失败，失败立即报错，新增/更新类操作常用
* **Failsafe**：失败安全，忽略异常
* **Failback**：失败自动恢复，后台重试
* **Forking**：并行调用多个服务，只要一个成功就返回
* **Broadcast**：广播调用所有提供者，任意一台失败则失败

***

## 3.7 Dubbo 的服务超时、重试机制是怎样的？

Dubbo 支持配置调用超时时间和重试次数。

对于服务超时，如果在规定时间内没有返回结果，就认为调用失败。默认失败后会进行重试（通常适用于幂等查询接口）。非幂等操作不建议重试，否则可能导致重复提交、重复扣款等问题

***

## 3.8 Dubbo 为什么需要注册中心？

注册中心的作用：

* 管理服务地址
* 实现服务注册与发现
* 实现服务上下线感知
* 降低服务消费者和提供者的耦合

如果没有注册中心，消费者就要写死提供者地址，扩容、迁移、故障恢复都很麻烦。

***

# 4. MySQL

## 4.1 MySQL 中常见的存储引擎有哪些？InnoDB 和 MyISAM 有什么区别？

常见存储引擎有InnoDB和MyISAM，**现在生产环境基本都优先使用 InnoDB。**

### InnoDB

* 支持事务
* 支持行锁
* 支持外键
* 支持 MVCC
* 是 MySQL 默认引擎

### MyISAM

* 不支持事务
* 只支持表锁
* 不支持外键
* 查询速度在某些简单场景下较快

***

## 4.2 什么是事务？事务的四大特性 ACID 是什么？

**事务**是数据库操作的最小执行单元，要么全部成功，要么全部失败。

### ACID：

* **A（Atomicity）原子性**：事务中的操作不可分割
* **C（Consistency）一致性**：事务前后数据保持一致
* **I（Isolation）隔离性**：多个事务互不干扰
* **D（Durability）持久性**：事务提交后数据永久保存

***

## 4.3 MySQL 的隔离级别有哪些？

\*\*\*\*四种隔离级别：

* **Read Uncommitted（读未提交）**
* **Read Committed（读已提交）**
* **Repeatable Read（可重复读）：MySQL的默认隔离级别。**
* **Serializable（串行化）**

### 会产生的问题：

* 读未提交：脏读、不可重复读、幻读
* 读已提交：避免脏读，但可能不可重复读、幻读
* 可重复读：避免脏读、不可重复读，MySQL 中通过 MVCC 和间隙锁大幅减少幻读
* 串行化：完全串行，性能最差

***

## 4.4 什么是索引？索引为什么能提高查询效率？

**索引**是帮助数据库快速查找数据的数据结构。MySQL 中常见索引底层数据结构使用 **B+ 树**。

索引提高效率的原因：

* 减少全表扫描
* 缩小数据查找范围
* 利用树结构快速定位记录

但索引会占用额外存储空间，还会降低插入、删除、更新性能。

***

## 4.5 B+ 树和 B 树有什么区别？为什么 MySQL 用 B+ 树？

### B+ 树特点：

* 非叶子节点只存键，不存数据
* 所有数据都存储在叶子节点
* 叶子节点之间通过链表相连

与其相比**B树**在叶子节点和非叶子节点都存储数据，每个节点存储的索引值少，树的深度大，且叶子节点之间没有关联，进行范围查询时需要进行回溯，效率比较低。

### 为什么适合数据库？

1. **更适合范围查询**：叶子节点链表天然支持范围扫描
2. **磁盘 IO 更高效**：非叶子节点不存数据，单页可存更多键，树更矮
3. **查询更稳定**：所有数据都在叶子节点，查询路径长度更一致

***

## 4.6 什么情况下索引会失效？

\*\*\*\*常见索引失效场景：

1. 使用联合索引，但是没有遵循**最左前缀原则**
2. 对索引列使用函数、运算、类型转换
3. 使用 `%xxx` 这种左模糊查询
4. `or` 两边条件索引使用不当
5. 数据分布问题导致优化器认为全表扫描更快
6. 使用不等于 `!=`、`<>`、范围查询后，后续列可能无法继续使用索引

***

## 4.7 什么是最左前缀原则？

\*\*\*\*对于联合索引 `(a, b, c)`：

* 可以使用 `a`
* 可以使用 `a, b`
* 可以使用 `a, b, c`
* 不能跳过 `a` 直接用 `b, c`

也就是说，联合索引从最左边开始匹配，不能中断太早。

***

## 4.8 什么是回表？什么是覆盖索引？

### 回表

先通过二级索引查到主键，再根据主键去聚簇索引中查完整数据，这个过程叫**回表**。

### 覆盖索引

查询的字段都能直接从索引中拿到，不需要回表，叫**覆盖索引**。

### 优点：

覆盖索引性能通常更高，因为减少了一次回表查询。

***

## 4.9 什么是聚簇索引和非聚簇索引？

### 聚簇索引

聚簇索引的数据和索引放在一起，在一张表只能有一个聚簇索引，如InnoDB 的主键索引就是聚簇索引。

### 非聚簇索引（二级索引）

非聚簇索引的索引和数据是分开的，叶子节点存的是主键值，查询完整记录通常需要回表。

***

## 4.10 MySQL 为什么会出现慢查询？怎么优化？

慢查询常见原因：

* 没有索引或索引失效
* SQL 写法不合理
* 回表过多
* 联表过多
* 数据量太大
* 锁竞争严重
* 服务器资源不足

### 优化思路：

1. 看执行计划 `explain`
2. 建合适索引
3. 尽量使用覆盖索引
4. 避免 `select *`
5. 优化 join、子查询、分页
6. 分库分表或冷热分离

***

# 5. Redis

## 5.1 Redis 为什么快？

Redis 快的原因主要有：

1. **基于内存操作**
2. **单线程模型避免线程切换开销**（核心命令执行模型）
3. **高效的数据结构**
4. **IO 多路复用机制**
5. 操作简单，CPU 消耗低

### 面试常说法：

Redis 是**内存型 KV 数据库**，因此速度远高于基于磁盘的关系型数据库。

***

## 5.2 Redis 常见数据类型有哪些？

常见五大基本数据类型：

* **String**
* **Hash**
* **List**
* **Set**
* **ZSet（Sorted Set）**

扩展结构还包括：

* Bitmap
* HyperLogLog
* Geo
* Stream

***

## 5.3 Redis 的 String 底层是怎么实现的？

\*\*\*\*Redis 的 String 底层通常基于 **SDS（Simple Dynamic String）简单动态字符串** 实现。

SDS 相比 C 字符串的优点：

* 记录字符串长度，获取长度是 O(1)
* 避免缓冲区溢出
* 支持二进制安全
* 支持空间预分配，减少扩容次数

***

## 5.4 Redis 持久化机制有哪些？

Redis持久化就是把内存中的数据写到磁盘中，防止服务宕机导致数据丢失。主要方式有RDB（内存快照）和AOF（日志文件），还有Redis4.0新增的AOF+RDB混合持久化方式。

### RDB

* 定时把内存数据快照保存到磁盘
* 恢复速度快
* 可能丢失最后一次快照后的数据

### AOF

* 以日志形式记录每次写命令
* 数据更安全
* 文件通常更大，恢复速度可能更慢

***

## 5.5 Redis 过期键删除策略有哪些？

Redis 采用的是**定期删除 + 惰性删除**。

### 定期删除

定时随机抽查设置了过期时间的 key，删除已过期的 key。

### 惰性删除

当访问某个 key 时，发现它已过期，再删除它。

### 为什么不主动立即删除？

因为如果为每个 key 单独维护定时器，开销会很大。

***

## 5.6 Redis 内存淘汰策略有哪些？

当内存不足时，Redis 会根据淘汰策略删除部分 key。缓存场景一般常用 **allkeys-lru** 或 **allkeys-lfu**。

常见策略：

* `noeviction`：不淘汰，直接报错
* `volatile-lru`：从设置过期时间的 key 中淘汰最近最少使用的
* `allkeys-lru`：从所有 key 中淘汰最近最少使用的
* `volatile-lfu`：从设置过期时间的 key 中淘汰访问频次最低的键值。
* `allkeys-lfu`：从所有 key 中淘汰访问频次最低的键值。
* `volatile-random`
* `allkeys-random`
* `volatile-ttl`

***

## 5.7 Redis 是单线程吗？

Redis 常说的“单线程”主要是指：**命令执行线程是单线程的。**

但 Redis 并不是所有工作都单线程，例如持久化、异步删除、网络读写在新版本中也有多线程优化能力

### 为什么单线程还能快？

* 内存操作快
* 避免加锁竞争
* IO 多路复用
* 数据结构高效

***

## 5.8 Redis 缓存穿透、击穿、雪崩分别是什么？怎么解决？

### 缓存穿透

查询一个**不存在的数据**，缓存和数据库都没有，请求全部打到数据库。

**解决：**

* 缓存空值
* 布隆过滤器
* 参数校验

### 缓存击穿

某个**热点 key 过期**瞬间，大量请求直接打到数据库。

**解决：**

* 热点 key 永不过期或逻辑过期
* 加互斥锁 / 分布式锁
* 提前刷新缓存

### 缓存雪崩

大量 key 在同一时间过期，导致大量请求打到数据库。

**解决：**

* 过期时间加随机值
* 多级缓存
* 限流降级
* 服务预热

***

## 5.9 Redis 如何保证缓存和数据库一致性？

\*\*强一致性很难，业务上通常追求最终一致性，\*\*常见方案是 **旁路缓存模式（Cache Aside Pattern）**。

### 写操作一般流程：

1. 更新数据库
2. 删除缓存

### 为什么不是先删缓存再更新数据库？

因为可能出现并发问题导致旧值回写缓存。

### 常见优化：

* 延迟双删
* MQ 异步删除缓存
* 订阅 binlog 同步缓存

***

## 5.10 Redis 分布式锁怎么实现？有什么问题？

最常见做法：

```latex
SET lockKey uniqueValue NX PX 30000
```

* `NX`表示不存在才加锁
* `PX`表示设置过期时间，防止死锁

释放锁时，要保证**只能删除自己的锁**，通常用 Lua 脚本校验 `uniqueValue` 再删除。

### 存在的问题：

* 锁过期业务未执行完
* 主从复制下锁丢失问题
* 时钟漂移、网络分区等复杂问题

所以生产中通常会使用 **Redisson** 封装好的分布式锁。

***

# 6. Redisson

## 6.1 什么是 Redisson？

Redisson 是一个基于 Redis 实现的 **Java 分布式工具包**。它不仅提供了对 Redis 的操作封装，还提供了很多分布式对象和并发工具。

常见功能：

* 分布式锁
* 分布式读写锁
* 分布式信号量
* 分布式队列
* 延迟队列
* 分布式 Map / Set / List

***

## 6.2 Redisson 分布式锁的底层原理是什么？

Redisson 分布式锁底层也是基于 Redis 实现的，核心是：

* 使用 `SET NX PX` 完成加锁
* 使用 Lua 脚本保证解锁原子性
* 使用唯一标识区分锁的持有者

Redisson 相比手写 Redis 锁，更完善的点在于：

* 可以自动续期（看门狗机制）
* 可重入
* 支持公平锁、读写锁等丰富能力

***

## 6.3 什么是 Redisson 的看门狗机制？

看门狗机制是 Redisson 分布式锁的重要特性。

如果业务执行时间超过锁默认过期时间，Redisson 会自动给锁**续期**，避免锁提前释放。避免业务未执行完，锁却过期，导致其他线程误拿到锁。

### 原理：

* 在加锁成功后启动后台线程
* 定期检查锁是否仍由当前线程持有
* 如果持有，就延长锁过期时间

***

## 6.4 Redisson 锁为什么是可重入的？

可重入指的是同一个线程在持有锁的情况下，可以再次获取同一把锁而不会死锁。

Redisson 在 Redis 中不仅记录“是否加锁”，还记录：

* 持有锁的线程标识
* 重入次数

同一线程再次加锁时，重入次数加 1；解锁时重入次数减 1，减到 0 才真正释放锁。

***

## 6.5 Redisson 有哪些常见锁？

常见锁类型：

* **RLock**：可重入锁
* **FairLock**：公平锁
* **ReadWriteLock**：读写锁
* **MultiLock**：组合锁
* **RedLock**：红锁
* **Semaphore**：信号量
* **CountDownLatch**：闭锁

***

## 6.6 Redisson 锁适合用在什么场景？

如果只是单机应用，用 `synchronized` 或 `ReentrantLock` 就够了；\
如果是分布式多实例，就需要用 Redisson 这类分布式锁。

常见场景：

* 秒杀防止超卖
* 防止重复下单
* 分布式任务调度互斥执行
* 缓存重建互斥
* 抢单系统并发控制

***

# 7. Elasticsearch

## 7.1 什么是 Elasticsearch？

Elasticsearch（ES）是一个基于 Lucene 的**分布式全文检索引擎**，也支持结构化搜索、聚合分析。

主要特点：

* 全文搜索能力强
* 分布式、高可用
* 近实时搜索
* 支持复杂聚合分析

常见应用场景：

* 搜索框
* 日志检索
* 商品搜索
* 文章检索
* 推荐系统的召回阶段

***

## 7.2 Elasticsearch 中的核心概念有哪些？

常见核心概念：

* **Index**：索引，类似数据库中的库
* **Document**：文档，类似数据库中的一行记录
* **Field**：字段，类似数据库中的列
* **Mapping**：映射，定义字段类型
* **Shard**：分片
* **Replica**：副本

***

## 7.3 Elasticsearch 为什么搜索快？

ES 查询快主要因为：

1. **倒排索引**
2. 分词后按 term 建立索引
3. 支持分片并行搜索
4. 底层 Lucene 查询能力强
5. 近实时机制高效

数据库适合精确查询，ES 更擅长**全文检索和复杂搜索**。

***

## 7.4 什么是倒排索引？

* 传统索引通过文档找内容，**倒排索引**则是**通过词项找包含该词的文档列表**

例如：

```latex
"java" -> 文档1、文档3、文档8
"redis" -> 文档2、文档3
```

这样用户搜索关键词时，就能快速定位包含该词的文档。

***

## 7.5 Elasticsearch 中 keyword 和 text 有什么区别？

**全文检索用 text，精确匹配用 keyword**

### text

* 会分词
* 适合全文搜索
* 如文章标题、内容

### keyword

* 不分词
* 适合精确匹配、过滤、排序、聚合
* 如手机号、订单号、状态字段、标签

***

## 7.6 Elasticsearch 的写入流程是怎样的？

ES 写入大致流程：

1. 文档先写入内存缓冲区
2. 同时写入 translog 日志
3. refresh 后数据可被搜索到
4. flush 后数据真正落盘并清理 translog

需要注意的是，ES 是**近实时搜索**，不是强实时。通常写入后不是立刻绝对可搜，而是经过 refresh 后可搜。

***

## 7.7 什么是分片和副本？

### 分片（Shard）

一个索引的数据可以拆分成多个分片，分布到不同节点上，便于水平扩展，分片解决数据量和性能问题。

### 副本（Replica）

分片的备份副本，用于提高可用性和提高查询吞吐量，副本解决高可用和读性能问题。

***

## 7.8 Elasticsearch 查询为什么不能替代 MySQL？

因为两者定位不同：ES 一般作为**搜索引擎**，MySQL 作为**主存储数据库**，二者常常配合使用。

### MySQL

* 强事务
* 强一致性
* 适合关系型数据存储和复杂事务

### Elasticsearch

* 擅长搜索和分析
* 近实时
* 不适合复杂事务和强一致性场景

***

## 7.9 MySQL 和 Elasticsearch 如何同步数据？

常见同步方案：

1. **业务代码双写**
2. **MQ 异步同步**
3. \*\*监听 MySQL binlog 同步到 ES，\*\*生产中常用，且对业务侵入性低。
4. 定时全量/增量同步

***

## 7.10 Elasticsearch 常见问题有哪些？

常见问题：

* mapping 设计不合理
* text/keyword 使用错误
* 深分页性能差
* 聚合查询过重
* 分片数设置不合理
* 写入和刷新频繁导致性能下降

### 深分页优化：

传统 `from + size` 深分页性能差，可以用`search_after`和scroll（偏向批量导出场景）进行深分页优化。

***

# 8. AI 基础概念

## 8.2 机器学习、深度学习、大模型之间是什么关系？

它们是一个逐步细化、逐步增强的关系。

### 机器学习

* 广义上指让机器从数据中学习规律的算法集合，常见算法有逻辑回归、决策树、随机森林、SVM 等

### 深度学习

* 是机器学习的一个分支
* 主要基于多层神经网络
* 更擅长处理图像、语音、文本这类复杂数据

### 大模型

* 通常指参数规模非常大的深度学习模型
* 例如大语言模型（LLM）、多模态模型
* 依赖海量数据和大规模算力训练

***

## 8.3 什么是大语言模型（LLM）？

大语言模型（Large Language Model）是指基于海量文本数据训练出来的、具备自然语言理解与生成能力的模型。

它能做的事包括：

* 对话问答
* 文本总结
* 翻译
* 代码生成
* 信息抽取
* 分类与改写

它的核心本质可以简单理解为：

* **根据上下文预测下一个最可能出现的 token**

但由于训练规模很大，它不仅能“续写文本”，还表现出较强的推理、归纳、生成和泛化能力。

***

## 8.4 什么是 Token？

Token 是大模型处理文本时的**最小计量单位**，不是“一个字”也不是“一个单词”的简单等价物。

例如：

* 中文里，一个汉字可能是一个 token，也可能不是
* 英文里，一个单词可能被拆成多个 token

Token 常见用途：

* 统计输入长度
* 统计输出长度
* 计费
* 控制上下文窗口

模型一般不按照“字符数”理解上下文，而是按 **token 数** 来限制输入输出规模

***

## 8.5 什么是 Prompt（提示词）？

Prompt 就是用户提供给模型的输入指令，用来告诉模型“你要做什么、按什么方式做、输出成什么格式”。

Prompt 常见组成部分：

* **角色**：例如“你是一名 Java 面试官”
* **任务**：例如“请总结下面这段内容”
* **约束**：例如“用中文回答，不超过 200 字”
* **上下文**：例如用户给出的材料、文档片段、历史对话
* **输出格式**：例如 JSON、Markdown、分点列表

好的 Prompt 能提升：输出稳定性、结果可控性以及格式的一致性

***

## 8.6 什么是上下文窗口（Context Window）？

上下文窗口是模型一次能看到的最大上下文范围，通常以 **token 数** 来衡量。

它包括：

* 用户当前输入
* 系统提示词
* 历史对话
* 附带的文档内容
* 模型即将生成的输出空间

如果输入太长超过窗口大小，就会出现：

* 部分内容被截断
* 早期对话被丢失
* 模型忽略某些信息

所以在实际应用中，必须控制输入长度，不能无限制往模型里塞全文。

***

## 8.7 什么是 Temperature（温度）？Top P 又是什么？

它们都是控制模型生成随机性的参数。

### Temperature

* 值越低，输出越稳定、越保守
* 值越高，输出越发散、越有创造性

一般理解：

* **低温度**：适合问答、摘要、信息抽取
* **高温度**：适合创作、发散式写作

### Top P

* 表示从累计概率达到某个阈值的候选 token 中进行采样
* 本质上也是控制输出多样性

如果面试官问怎么理解，可以简单说：

* `temperature` 更像调“随机程度”
* `top_p` 更像调“候选范围”

***

## 8.8 什么是 Embedding（向量化）？

Embedding 是把文本、图片等数据转换成一组高维数字向量的过程。

它的作用是：

* 让机器能计算“语义相似度”
* 让非结构化数据可以做检索、聚类、匹配、推荐

例如两句话：

* “如何学习 Java”
* “Java 入门路线”

虽然字面不一样，但语义接近，转成向量后在空间中的距离通常也会更近。

因此 Embedding 经常用于：

* 语义搜索
* 相似文本匹配
* 推荐召回
* RAG 检索

***

## 8.9 什么是向量数据库？它和普通数据库有什么区别？

向量数据库是专门用于存储和检索高维向量的数据系统。它最核心的能力是：根据“向量距离”找相似内容，而不是只按字段精确匹配。

**普通数据库**更擅长：

* 精确查询
* 范围查询
* 事务处理
* 结构化数据管理

**向量数据库**更擅长：

* 相似度检索
* 语义召回
* ANN（近似最近邻）查询

因此两者通常是**配合关系**：

* 普通数据库存业务主数据
* 向量数据库存语义向量和检索索引

***

## 8.10 什么是 RAG？

RAG 全称是 **Retrieval-Augmented Generation**，中文通常叫**检索增强生成**。

它的核心思想是：

1. 先从外部知识库中检索相关内容
2. 再把检索结果连同用户问题一起喂给大模型生成答案

这样做的好处：能够减少模型胡编乱造，利用外部最新知识让回答更贴近指定资料，同时不需要频繁重训模型。

RAG 的典型流程：

1. 文档切分
2. 文本向量化
3. 把向量写入向量库
4. 用户提问
5. 对问题向量化
6. 检索相似片段
7. 将检索片段拼到 Prompt 中
8. 大模型基于这些上下文生成答案

***

## 8.11 什么是微调（Fine-tuning）？它和 Prompt Engineering 有什么区别？

### Prompt Engineering

* 不改模型参数
* 通过更好的提示词引导模型输出
* 成本低、迭代快

### Fine-tuning

* 在已有模型基础上继续训练
* 会更新模型参数
* 能让模型更适配特定领域或特定风格

两者区别可以简单理解为：

* **Prompt Engineering**：像“更会提问”
* **Fine-tuning**：像“重新训练模型的一部分能力”

通常优先级是：

1. 先试 Prompt Engineering
2. 再试 RAG
3. 最后再考虑 Fine-tuning

因为微调成本更高，维护也更复杂。

***

## 8.12 什么是幻觉（Hallucination）？

幻觉是指模型生成了**看起来合理、但实际上不真实或没有依据**的内容。

幻觉常见表现：

* 编造事实
* 引用不存在的数据
* 输出错误但很像真的结论
* 对不知道的问题也强行回答

为什么会有幻觉？

* 模型本质上是概率生成，不是真正“知道”
* 训练数据不完整
* 上下文不足
* Prompt 不够明确

常见缓解方式：

* 使用 RAG
* 要求模型“只基于给定资料回答”
* 给出引用依据
* 对关键结果增加规则校验和人工审核

***

## 8.13 什么是 Agent（智能体）？

Agent 可以理解为“会思考 + 会调用工具 + 会分步骤完成任务”的 AI 系统形态。

普通对话模型像是你问一句，它答一句

但是Agent 更像：

* 接到目标后，能自己拆任务、调用搜索、数据库、代码执行、外部 API，再汇总结果

Agent 常见能力包括：

* 任务规划
* 工具调用
* 记忆管理
* 多轮决策
* 结果反思与修正

***

# 9. 高频综合题

## 9.1 Redis 和 Elasticsearch 的区别是什么？

**Redis 更偏缓存和高性能读写，ES 更偏搜索和分析。**

* **Redis**：内存型 KV 数据库，适合缓存、计数器、分布式锁等
* **Elasticsearch**：全文检索引擎，适合搜索、检索、聚合分析

***

## 9.2 为什么分布式锁一般推荐 Redisson，而不是自己手写 Redis 锁？

因为自己手写 Redis 锁容易遗漏很多边界问题，比如：

* 锁续期
* 解锁的原子性
* 可重入
* 锁误删
* 多线程线程标识管理

Redisson 对这些问题做了比较完整的封装，生产中更可靠。

***

## 9.3 Dubbo 调用超时怎么排查？

从 **消费端、网络、提供端、下游依赖** 四个方向排查，排查思路：

1. 看消费端超时配置是否过短
2. 看提供者接口执行是否慢
3. 看数据库、缓存、ES 查询是否慢
4. 看网络是否抖动
5. 看线程池是否满了
6. 看注册中心是否异常
7. 看是否发生 GC 或机器资源打满

***

## 9.4 MySQL 索引和 Elasticsearch 倒排索引有什么区别？

**MySQL 解决“按字段找记录”，ES 解决“按关键词找文档”。**

### MySQL 索引

* 常见是 B+ 树
* 擅长精确查询、范围查询
* 适合结构化数据

### Elasticsearch 倒排索引

* 擅长全文搜索
* 通过词项找文档
* 适合非结构化文本检索

***

# 10. 面试回答模板建议

## 10.1 八股题通用回答结构

面试时推荐按这个结构答：

1. **先下定义**
2. **再讲核心原理**
3. **再说应用场景**
4. **最后补充优缺点或注意点**

例如回答 Redis 为什么快：

* 先说它是内存数据库
* 再说单线程 + IO 多路复用 + 高效数据结构
* 再补充适用于缓存等高并发场景
* 最后说也受内存容量限制

这样回答会更像“理解型”，而不是死记硬背。
