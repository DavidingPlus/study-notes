# Docker Compose

Docker Compose 是一个用于定义和运行多容器 Docker 应用程序的工具。通过使用一个 YAML 文件来配置应用服务，给予Docker Compose 我们就可以通过一个单独的命令来创建和启动所有服务。可以大大的简化配置环境的复杂度。利用Docker Compose ，可以实现以下常见功能：

* **服务定义**：可以在一个文件中定义一组相互关联的服务（如数据库、后端应用、前端应用等），这些服务将被同时管理。
* **一键部署**：通过一个简单的命令 docker-compose up，可以同时启动或停止所有定义的服务。
* **环境隔离**：每个项目可以使用单独的隔离环境，通过在不同的项目中使用不同的 Docker Compose 文件来实现。
* **简化配置**：通过 YAML 文件配置服务，使得配置过程标准化且易于理解和维护

## 核心配置文件（docker-compose.yml）

* 该配置文件是 Docker Compose 的核心，采用 YAML 格式，**核心顶层关键字**为 `version`、`services`、`networks`、`volumes`，所有服务配置均嵌套在`services`下  。
* 有了 `docker-compose.yml` 文件后，核心操作围绕**文件所在目录**执行：在docker-compose.yml文件所在目录执行docker-compose up即可配置所有服务。

## docker-compose常见命令

* \*\*docker-compose up：\*\*创建并启动所有服务
* \*\*docker-compose down：\*\*停止并删除所有服务、容器。网络（保留命名卷）
* \*\*docker-compose start/stop：\*\*启动/停止服务
* \*\*docker-compose restart：\*\*重启服务
* \*\*docker-compose images：\*\*列出Compose文件构建的镜像
* \*\*docker-compose logs：\*\*日志查看
  * **docker-compose logs -f** ：跟踪指定服务日志

## Docker常见命令

* **docker ps -a**：列出所有容器

* \*\*docker logs ：\*\*查看日志
  * \*\*docker logs -f \*\*：实时跟踪日志输出
  * \*\*docker logs --tail 50 \*\*：查看最新的50行日志
  * \*\*docker logs --since 30m \*\*：查看最近30分钟的日志

# Maven

### 依赖范围

#### 常见的范围是 compile、test、provided、runtime、system

* compile：缺省值，适用于所有阶段，会随着项目一起发布
* test：范围依赖，在一般的编译和运行时都不需要
* provided：打包的时候可以不用包进去。比如 [servlet.jar](http://servlet.jar/) 在开发阶段用到，但是部署的时候，由于 Tomcat\lib 有 [servlet.jar](http://servlet.jar/) 了，打包的时候可以去掉它
* runtime：无需参与项目的编译，不过后期的测试和运行周期需要其参与。与 compile 相比，跳过编译而已
* system：和 provide 相同，不过被依赖项不会从 maven 仓库抓，而是从本地系统文件拿，一定要配合 systemPath 使用

### 生命周期

#### Maven 生命周期定义了各个构建环节的执行顺序，有了这个清单，Maven 就可以自动化的执行构建命令了

* Clean Lifecycle 在进行真正的构建之前进行一些清理工作
* Default Lifecycle 构建的核心部分，编译，测试，打包，安装，部署
* Site Lifecycle 生成项目报告，站点，发布站点
* 它们是相互独立的，你可以仅仅调用 clean 来清理工作目录，仅仅调用 site 来生成站点。当然你也可以直接运行 mvn clean install site 运行所有这三套生命周期

### 常见的命令

* mvn clean 表示清理
* mvn compile 表示编译主程序
* mvn test 表示执行测试
* mvn package 表示打包，打包之后再 target 目录下会生成打包文件
* mvn install：将包安装至本地仓库
* mvn deploay：将最终的包复制到远程的仓库

# Dubbo

Dubbo可以帮助开发者快速构建分布式服务架构，实现服务之间的透明化远程调用。  因此常常作为微服务间的通信框架，实现服务解耦和独立部署。

其分层架构与核心调用流程示意如下图：

![1770799855001-9e2a1b98-6145-4a8c-b18b-dd54d1a46442.png](./img/XNrCW8Zm9usOoRI7/1770799855001-9e2a1b98-6145-4a8c-b18b-dd54d1a46442-760396.png)

Dubbo从下到上可以分为Remoting层、RPC层和Business层。其中**Remoting**层可以负责网络通信、数据序列化和线程调度，是底层通信的基石；**RPC层**封装了服务代理、集群路由、负载均衡等核心RPC

逻辑；**Business层**是框架的应用入口，由用户定义的业务服务接口和实现。

Dubbo会从以下几个方面参与微服务调用：

1. **服务发布与引用**：对应实现是图里的**Proxy服务代理层**，Proxy根据客户端和服务端的接口描述，生成接口对应的客户端和服务端的Stub，使得客户端调用服务端就像本地调用一样。
2. **服务注册与发现**：对应实现是图里的**Registry注册中心层**，Registry根据客户端和服务端的接口描述，解析成服务的URL格式，然后调用注册中心的API，完成服务的注册和发现。
3. **服务调用**：对应实现是**Protocol远程调用层**，Protocol把客户端的本地请求转换成RPC请求。然后通过Transporter层来实现通信，Codec层来实现协议封装，Serialization层来实现数据序列化和反序列化。
4. **服务监控**：对应实现层是**Monitor调用链层**，通过MonitorFilter，实现对每一次调用的拦截，在调用前后进行埋点数据采集，上传给监控系统。
5. **服务治理**：对应实现层是**Cluster层**，负责服务节点管理、负载均衡、服务路由以及服务容错。

在Dubbo框架下，**客户端发起服务调用**的过程：

* 首先根据接口定义，通过Proxy层封装好的透明化接口代理，发起调用。
* 通过Registry层封装好的服务发现功能，获取所有可用的服务提供者节点列表。
* 再根据Cluster层的负载均衡算法从可用的服务节点列表中选取一个节点发起服务调用，如果调用失败，根据Cluster层提供的服务容错手段进行处理。
* 同时通过Monitor层拦截调用，实现客户端的监控统计。
* 最后在Protocol层，封装成Dubbo RPC请求，发给服务端节点。

通过上述操作，客户端的请求从一个本地调用转化成一个远程RPC调用，经过服务调用框架的处理，通过网络传输到达服务端，其中服务调用框架包括通信协议框架Transporter、通信协议Codec、序列化Serialization三层处理。**服务端接收到请求**后，首先在Protocol层，把网络上的请求解析成Dubbo RPC请求。然后通过Monitor拦截调用，实现服务端的监控统计。最后通过Proxy层的处理，把Dubbo RPC请求转化为接口的具体实现，执行调用。

因此Dubbo的**核心能力如下**：

1. 实现像调用本地方法一样调用远程服务，其余底层网络通信、序列化等细节对开发者屏蔽。
2. Dubbo内置多种负载均衡策略，会自动分发流量，能够避免单点压力过大。
3. 能够通过注册中心管理服务地址，服务上下线自动感知，无需手动配置。
4. 支持失败重试、熔断降级和灰度发布等策略，能够保障服务在异常情况下的可用性。
5. Dubbo基于SPI机制，协议、序列化、传输层等核心组件可以灵活替换和扩展。

如果不使用Dubbo进行服务间通信，使用传统的HttpClient模拟Http发起请求，会出现以下**问题**：

1. 服务迁移，导致被调用服务不可用，需要手动改调用方相关的IP地址，当然将IP这些可变配置写在配置中心也OK，可以避免服务的重新部署，但仍较为繁琐，始终需要耗费人力去配置相关信息
2. 无法及时感知服务状况，被调用方宕机，调用方无法及时感知，无有效的容错机制
3. 如果被调用方式集群模式，那么调用方需要手动实现负载均衡算法

```java
@ControllerAdvice
public class GlobalExceptionHandler {
   @ResponseBody
   @ExceptionHandler(value = NetworkDiskException.class)
   public Result handle(NetworkDiskException e) {
     if (e.getErrorCode() != null) {
       return ResultUtil.failed(e.getErrorCode());

     }

     return ResultUtil.failed(e.getMessage());
   }

```

```java
   }

   }

   }

     return result;

   }

}
```

# 认证与请求入口技术

这一类技术主要解决三个问题：

1. 当前请求是谁发起的。
2. 该用户是否已经登录、是否有权限访问。
3. 请求在进入具体业务服务前，是否需要统一做鉴权、路由和过滤。

## Sa-Token

Sa-Token 是一个轻量级的 Java 权限认证框架，主要用于处理登录认证、权限校验、会话管理等问题。它的目标是把“用户登录态”这件事从业务代码中抽离出来，避免每个模块都重复编写登录校验逻辑。

Sa-Token 常见的作用包括：

* 登录认证：判断用户是否已经登录。
* 权限校验：判断当前用户是否拥有某类角色或权限。
* 会话管理：管理用户登录状态、退出登录、踢下线等操作。
* 统一拦截：把权限控制前置到框架层，而不是散落在业务方法中。

如果不使用这类认证框架，系统往往会出现这些问题：

1. 登录校验逻辑散落在多个接口中，代码重复。
2. 权限控制规则不统一，后期维护困难。
3. 会话失效、强制下线、并发登录控制等功能实现成本较高。

## JWT

JWT（JSON Web Token）是一种用于在各方之间安全传递信息的令牌格式。它本质上是一段经过签名的字符串，内部可以保存用户标识、过期时间、业务标记等信息。

JWT 的核心特点在于“自描述”：

* 服务端拿到 Token 后，可以直接从中解析出用户身份等信息。
* 只要签名合法，就能确认这段 Token 没有被篡改。
* 它天然适合在多服务之间传递用户身份信息。

JWT 常见的价值在于：

1. 减少服务器对传统 Session 的强依赖。
2. 适合前后端分离和微服务场景。
3. 便于把身份信息在网关、业务服务、RPC 调用链路中进行传递。

需要注意的是，JWT 适合承载身份信息，但并不等于“完全不需要状态管理”。在很多系统中，它仍然会和 Redis 等存储一起使用，用于控制过期、注销、黑名单或单点登录等能力。

## Redis

Redis 是一个基于内存的 Key-Value 数据库，读写速度快，常用于缓存、会话、排行榜、分布式锁、消息队列等场景。

在认证链路中，Redis 常见的作用包括：

* 保存登录态。
* 保存 Token 与用户之间的映射关系。
* 控制 Token 过期时间。
* 支持退出登录、踢下线等需要“主动失效”的场景。

Redis 之所以常和认证系统配合使用，是因为它既快，又支持过期时间和丰富的数据结构，适合存放短期、高频访问的数据。

## Spring Cloud Gateway

Spring Cloud Gateway 是 Spring Cloud 体系中的网关组件，主要负责所有外部请求的统一入口。客户端不必直接访问所有后端服务，而是先访问网关，由网关把请求转发到对应的服务。

网关的主要作用包括：

* 统一路由：把不同路径的请求转发到不同服务。
* 统一鉴权：在请求进入业务服务前先校验身份。
* 统一过滤：处理日志、跨域、限流、黑名单、Header 处理等通用逻辑。
* 统一治理：把原本散落在各服务中的公共控制能力前置。

如果没有网关，客户端往往需要直接面对多个服务地址，这会带来：

1. 调用入口分散，前端或调用方需要记住多个地址。
2. 鉴权、限流、跨域等逻辑容易在多个服务中重复实现。
3. 后端服务一旦扩容、迁移或拆分，调用方改造成本较高。

# 数据访问与缓存技术

这一类技术主要负责“数据怎么存、怎么查、怎么更高效地查”。

## MyBatis Spring Boot Starter 与 MyBatis-Plus

MyBatis 是 Java 生态中非常常见的持久层框架，核心思想是：开发者自己掌控 SQL，框架负责把 SQL 执行结果映射为 Java 对象。`MyBatis Spring Boot Starter` 的作用主要是把 MyBatis 和 Spring Boot 的自动配置整合起来，简化项目接入。

MyBatis 的特点是：

* SQL 可控，适合复杂查询场景。
* 映射关系清晰，便于和数据库结构对应。
* 对业务复杂度高、SQL 定制要求强的系统比较友好。

MyBatis-Plus 是在 MyBatis 基础上的增强工具，主要作用是减少重复的基础 CRUD 代码。它更像是“在保留 MyBatis 可控性的前提下，提高开发效率”。

MyBatis-Plus 常见能力包括：

* 通用增删改查。
* 条件构造器。
* 分页支持。
* 代码生成。

因此这两者的关系可以理解为：

* MyBatis 负责“灵活、可控”。
* MyBatis-Plus 负责“高效、少写重复代码”。

## Druid

Druid 是一个数据库连接池组件，用于管理应用和数据库之间的连接。应用在访问数据库时，不会每次都重新创建连接，而是优先从连接池中获取，用完后归还。

连接池存在的意义在于：

1. 数据库连接的创建和销毁成本较高。
2. 高并发场景下频繁新建连接会带来明显性能损耗。
3. 连接池可以统一做监控、回收、超时控制和异常检测。

Druid 的常见特点包括：

* 提供稳定的连接池能力。
* 具备监控与统计能力。
* 可以帮助定位慢 SQL、连接泄露等问题。

## Redis、Redisson、JetCache、Caffeine

缓存的核心目标是：把“访问频率高、变化相对没那么快”的数据提前放到更快的位置，以减少数据库压力并提升响应速度。

### Redis

Redis 适合作为分布式缓存，因为它独立于应用进程之外，多个服务都可以访问同一份缓存数据。因此它更适合：

* 用户登录态共享。
* 热点数据缓存。
* 分布式场景下的数据共享。

### Redisson

Redisson 是 Redis 的 Java 客户端增强组件，它不只是简单地读写 Redis，而是进一步封装了很多分布式场景常用能力，例如：

* 分布式锁。
* 分布式集合。
* 延迟队列。
* 统一的同步控制能力。

它的价值在于让开发者不必直接围绕 Redis 命令手工实现这些复杂逻辑。

### JetCache

JetCache 是一个缓存框架，它的目标不是替代 Redis，而是把本地缓存、远程缓存、缓存注解等能力统一抽象起来。开发者可以用一致的方式管理缓存逻辑，而不必到处手写缓存读写代码。

JetCache 的意义主要在于：

* 统一缓存接入方式。
* 支持多级缓存模型。
* 通过注解和统一配置降低缓存开发成本。

### Caffeine

Caffeine 是一个本地缓存组件，数据直接保存在应用进程内存中，因此访问速度非常快。它适合：

* 读多写少。
* 生命周期短。
* 单机内高频访问的数据。

它和 Redis 的区别在于：

* Redis 是远程缓存，适合多实例共享。
* Caffeine 是本地缓存，适合追求极致访问速度。

因此在实际系统中，常会把 Redis 和 Caffeine 配合起来使用，形成“本地缓存 + 分布式缓存”的多级缓存结构。

# 搜索与消息技术

这一类技术解决的是“如何快速检索数据”和“如何让系统异步解耦”。

## Elasticsearch、Spring Data Elasticsearch 与 Easy-ES

Elasticsearch 是一个分布式搜索引擎，特别适合处理全文检索、复杂条件筛选、聚合统计等场景。和传统数据库相比，它更擅长“搜索”而不是“事务处理”。

Elasticsearch 常见优势包括：

* 适合全文检索。
* 支持分词、相关性评分。
* 查询灵活，适合搜索类业务。
* 适合海量数据的快速检索。

Spring Data Elasticsearch 的作用主要是把 Elasticsearch 的访问方式和 Spring 体系整合起来，让开发者可以用更统一的方式进行文档映射和检索操作。

Easy-ES 则可以理解为 Elasticsearch 场景下的开发增强工具，它的目标和 MyBatis-Plus 有些类似，都是在保留底层能力的同时，提高日常开发效率。

因此它们的关系可以理解为：

* Elasticsearch：核心搜索引擎。
* Spring Data Elasticsearch：Spring 生态中的访问抽象。
* Easy-ES：进一步提升搜索开发效率的增强工具。

## RocketMQ 与 Spring Cloud Stream

RocketMQ 是一个分布式消息中间件，它的核心价值是“异步”和“解耦”。当一个操作不适合在主流程里同步完成时，可以先把消息投递出去，再由消费者异步处理。

消息队列常见的使用目的包括：

* 异步处理：缩短接口主流程耗时。
* 系统解耦：发送方不需要直接依赖接收方实现。
* 流量削峰：高峰流量先进入队列，再由消费者平滑处理。
* 广播通知：一个事件可以被多个系统同时消费。

Spring Cloud Stream 的作用是给消息中间件再加一层抽象，让开发者更关注“生产和消费消息”本身，而不必过早耦合到底层具体的 MQ 实现。

因此二者的关系可以理解为：

* RocketMQ 负责真正的消息传输。
* Spring Cloud Stream 负责提供更统一的编程模型。

# 文件存储与文档理解技术

这一类技术主要负责“文件存在哪里”“如何读取文件内容”“如何让文档具备可搜索、可分析的能力”。

## Aliyun OSS

Aliyun OSS 是阿里云提供的对象存储服务，适合存放图片、视频、文档、备份文件等非结构化数据。对象存储的特点是：按对象管理文件，而不是按传统磁盘目录来管理。

OSS 的常见优势包括：

* 容量扩展方便。
* 适合海量文件存储。
* 访问方式标准化，便于和应用系统集成。
* 由云厂商负责底层存储可靠性和可用性。

## FastDFS

FastDFS 是一个分布式文件系统，主要用于解决海量文件的存储与访问问题。它强调的是“分布式文件管理”，适合图片、附件、资源文件等场景。

与对象存储相比，FastDFS 更像是自建式的分布式文件方案，适合对文件服务有更强自主控制需求的场景。

它的典型价值在于：

* 分布式存储文件。
* 提供文件上传、下载、定位能力。
* 适合构建独立的文件服务体系。

## Apache Tika

Apache Tika 是一个文档内容解析工具，核心能力是“识别文件类型并提取文本内容与元数据”。它特别适合处理 PDF、Word、Excel、PPT、TXT 等多种文档格式。

Tika 的意义在于：

* 让系统能够理解“文件里写了什么”。
* 把原本难以处理的二进制文档转化为可分析文本。
* 为全文检索、摘要提取、标签生成、问答检索提供基础输入。

## PostgreSQL 与 pgvector

PostgreSQL 是一个功能强大的关系型数据库，除了常规的结构化数据存储能力外，还具备较强的扩展性。

pgvector 是 PostgreSQL 的向量扩展，它的核心作用是：让数据库能够存储向量，并进行向量相似度检索。向量检索常用于语义搜索、知识库问答、推荐系统等场景。

这组技术的核心意义在于：

* PostgreSQL 负责存储结构化数据与业务数据。
* pgvector 负责存储文本、图片等内容转换后的向量表示。
* 通过向量相似度计算，可以按“语义相近”而不是“关键词完全匹配”来检索内容。

因此在 AI 文档场景下，它们常被用来支撑：

1. 文档切片后的向量存储。
2. 相似片段召回。
3. 语义检索与问答增强。

# 前端工程基础技术

前端部分虽然不像后端中间件那样强调基础设施治理，但它同样需要一套稳定的工程化体系来支撑页面开发、状态管理、路由组织与接口请求。

## Vue 3

Vue 3 是一个渐进式前端框架，主要用于构建用户界面。它的特点是组件化开发，即把页面拆分成多个可复用的小模块，每个模块负责一部分界面与交互逻辑。

Vue 3 的核心价值在于：

* 组件化开发。
* 数据驱动视图。
* 更适合中大型前端项目的组织与维护。

## Vite

Vite 是一个前端构建工具，主要负责开发环境启动、模块打包和资源构建。它的目标是提升前端开发体验，尤其是在本地开发阶段提供更快的启动速度和更快的热更新。

Vite 的意义在于：

* 启动快。
* 构建效率高。
* 更适合现代前端模块化开发。

## Element Plus

Element Plus 是 Vue 3 生态中的一套 UI 组件库，提供按钮、表单、表格、弹窗、分页等常见组件。

UI 组件库的价值在于：

* 减少重复造轮子。
* 保证页面风格相对统一。
* 提高中后台类系统的页面开发效率。

## Pinia

Pinia 是 Vue 生态中的状态管理工具。它主要用于管理“多个页面或多个组件都需要共享的数据”，例如用户信息、当前目录状态、任务列表、全局界面状态等。

如果没有状态管理，前端项目在规模变大后容易出现：

1. 数据在多个组件之间传递复杂。
2. 状态来源不清晰，难以维护。
3. 不同页面之间共享状态成本较高。

## Vue Router

Vue Router 是 Vue 官方路由管理器，主要负责“URL 路径”和“页面组件”之间的映射关系。

它的核心作用包括：

* 定义页面路径。
* 控制页面跳转。
* 支持路由守卫。
* 让单页应用具备接近传统多页面站点的访问体验。

## Axios

Axios 是一个基于 Promise 的 HTTP 客户端，前端通常通过它向后端发送请求并接收响应。

Axios 的常见价值包括：

* 统一封装请求逻辑。
* 统一处理鉴权信息。
* 统一处理错误、超时、响应拦截等公共逻辑。

因此从工程角度看，这些前端技术的分工可以概括为：

* Vue 3 负责界面组织。
* Vite 负责工程构建。
* Element Plus 负责界面组件。
* Pinia 负责状态管理。
* Vue Router 负责页面路由。
* Axios 负责与后端通信。
