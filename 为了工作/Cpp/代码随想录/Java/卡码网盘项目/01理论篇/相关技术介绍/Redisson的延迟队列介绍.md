# Redisson的延迟队列介绍

## Redisson 是什么

Redisson 是一个基于 Redis 的 Java 客户端增强框架。它进一步提供了很多更贴近业务开发的“分布式对象”和“分布式能力”。

可以把它理解为：

1. Redis 提供底层存储和原子操作能力。
2. Redisson 在 Redis 之上封装出锁、队列、集合、延迟队列、布隆过滤器等高级能力。
3. 业务系统通过这些高级 API，更方便地完成分布式场景下的并发控制与任务调度。

因此，Redisson 的核心价值在于“让 Redis 更容易被业务系统直接使用”。

## Redisson 常见能力

Redisson 常被用在以下几类场景：

* 分布式锁：控制并发写、避免重复操作。
* 分布式队列：在多实例环境下传递任务。
* 延迟队列：让任务在未来某个时间点再被消费。
* 分布式集合与对象：把常见的数据结构扩展到 Redis 上。
* 分布式同步工具：如信号量、闭锁、读写锁等。

这些能力的共同特点是：它们本质上都依赖 Redis 的数据结构和原子操作，但 Redisson 帮开发者封装掉了底层细节。

## Redisson 在本项目中的主要作用

从当前仓库代码看，Redisson 在本项目里主要承担三类职责：

### 1. 分布式锁

项目里通过 `RedissonClient.getLock()` 获取锁对象，并结合自定义注解切面实现分布式锁控制。

这类能力适合解决：

* 同一个文件分片重复上传。
* 同一业务对象被多个请求同时修改。
* 同一个资源在多实例部署下被重复处理。

分布式锁的核心目标是：在单机锁已经失效的多实例环境中，仍然保证同一时刻只有一个线程或一个实例能处理某个关键资源。

### 2. 延迟队列

项目里存在基于 Redisson 延迟队列的封装，用于把“现在不执行、未来再执行”的任务先存起来，等到延迟时间到了再消费。

这种能力适合处理：

* 分享到期后的延迟删除。
* 某些需要延后触发的补偿任务。
* 与业务对象生命周期绑定的轻量级定时任务。

### 3. 远程缓存支撑

项目的缓存配置里还使用了 `Redisson` 作为远程缓存底座，配合 `JetCache` 组成缓存体系。

它的意义在于：

* 把缓存数据放到 Redis 中，供多个服务实例共享。
* 复用 Redisson 对 Redis 连接与操作的封装能力。

## 为什么很多项目会选择 Redisson

如果系统只是简单读写缓存，直接用 Spring Data Redis 往往已经够用；但只要业务进入分布式场景，通常就会开始遇到这些问题：

1. 如何安全地加分布式锁。
2. 如何做延迟任务而不是普通队列。
3. 如何避免自己用原生命令拼装复杂逻辑。
4. 如何让多个服务实例共享同一套同步控制能力。

Redisson 的优势就在于它已经把这些常见能力做成了可直接使用的抽象，因此开发成本和出错概率都会更低。

## Redisson 延迟队列是什么

Redisson 延迟队列的本质是：任务先进入一个“暂时不可消费”的存储结构，等到延迟时间到达后，再被搬运到真正可消费的阻塞队列中。

所以它不是“消息一进队列就立即消费”，而是“先保存、等时间到了再投递”。

延迟队列特别适合这类任务：

* 到某个时间点自动失效。
* 延后一段时间再检查状态。
* 将即时操作改成异步延迟处理。

它解决的核心问题是：让系统具备“按时间触发任务”的能力，而不需要每种业务都自己维护定时扫描逻辑。

## Redisson 延迟队列的核心思路

Redisson 延迟队列不是依赖 Redis 的 key 过期通知来做任务调度，而是自己维护一套“延迟任务存储 + 到期搬运”的机制。

可以把它概括为四部分：

### 1. timeoutSet

这是一个有序集合 `ZSet`，用来保存所有延迟任务，并按照“到期时间”排序。

它的作用是：

* 存放所有尚未到期的任务。
* 让系统随时能知道“哪个任务最早到期”。

### 2. taskList

这是一个辅助列表，用于保存任务的内部记录，配合移除、检查和搬运逻辑使用。

更准确地说，它不是业务消费队列，而是 Redisson 内部为了维护延迟任务状态而保留的辅助结构。

### 3. readyQueue

这是最终供消费者获取数据的阻塞队列。

只有已经到达延迟时间的任务，才会被放入这个队列。消费者真正消费的，其实是这里面的数据，而不是前面的 `timeoutSet`。

### 4. Pub/Sub 通知频道

Redisson 还会配合一个发布订阅频道，用来通知客户端“最新最早到期任务的时间点发生了变化”。

这个频道的定位非常重要：

* 它负责通知。
* 它不负责持久化任务本身。

也就是说，真正的任务数据仍然保存在 Redis 的数据结构中，Pub/Sub 只是让客户端更快地感知“应该重新安排一次调度”。

## Redisson 延迟队列的执行流程

把一个延迟任务从“提交”到“消费”串起来看，大致可以分成下面几个步骤：

### 第一步：提交任务

业务方把任务放入延迟队列，并指定延迟时间。

此时系统会把任务写入 `timeoutSet`，并记录对应的内部信息。这个阶段任务只是“被登记”，还不能被消费。

### 第二步：安排最近一次触发时间

如果新加入的任务比当前队列中的其它任务更早到期，Redisson 会通知客户端更新本地调度时间。

这里的本质是：客户端始终只需要重点关注“当前最近要到期的那个任务”。

### 第三步：客户端等待触发时机

Redisson 客户端内部会维护定时调度逻辑。当最早到期时间快到了，就会触发一次检查。

需要注意的是，这里的“到期检查”主要是由客户端配合 Redis 完成的，并不是 Redis 服务端自动把任务推给业务线程。

### 第四步：搬运到期任务

当到期时刻到来后，Redisson 会通过 Lua 脚本把已经到期的任务从 `timeoutSet` 中取出，并原子地搬运到 `readyQueue`。

这一步的关键点有两个：

1. 到期任务和未到期任务是分开的。
2. 搬运过程借助 Lua 脚本保证原子性，避免并发搬运带来重复问题。

### 第五步：消费者真正消费

业务消费者阻塞地监听 `readyQueue`，当任务被搬运进去之后，就可以被 `take()` 之类的阻塞方法获取并执行。

所以从消费视角看，消费者面对的只是一个普通阻塞队列；真正的“延迟调度”逻辑发生在任务进入阻塞队列之前。

## 为什么不直接用 Redis 的 key 过期事件

很多人第一次接触延迟任务时，都会想到“给 key 设置过期时间，过期后监听通知不就行了”。这个方案听起来简单，但问题很多。

### 1. 触发时机不够稳定

Redis 的过期事件并不是严格在过期时间点立刻触发，而是发生在 key 真正被清理时。

而 Redis 对过期 key 的处理本身就存在：

* 惰性清除：访问时才发现过期。
* 定期清除：后台定时抽样扫描。

这意味着“过期通知时间”和“设置的过期时间”并不严格等价，不适合要求相对精确的延迟任务。

### 2. 过期事件不是可靠消息队列

过期通知和普通 Pub/Sub 一样，都不是面向可靠消费设计的。

如果消费者当时不在线，或者没有及时订阅到事件，消息本身不会像 MQ 那样被可靠保存和重投。

### 3. 表达能力有限

基于 key 过期事件的方案，更像“某个 key 到期了通知一下”，而 Redisson 延迟队列解决的是“任务先存储、到时再投递给真正消费者”的问题，两者抽象层级并不一样。

## Redisson VS RocketMQ

* Redisson 延迟队列适合轻量级、和 Redis 生态紧密结合的延迟任务。
* RocketMQ 更偏向完整消息中间件，适合更标准的异步消息链路、削峰填谷、广播通知、跨系统解耦。

对于当前项目来说，分享过期删除这类任务更接近“轻量级业务延迟任务”，直接基于 Redisson 完成，接入成本更低，也更符合现有 Redis/缓存体系。

## Redisson 延迟队列适合什么场景

Redisson 延迟队列通常更适合下面这些场景：

* 延迟删除。
* 延迟关闭。
* 订单超时、分享超时、状态超时检查。
* 需要按时间触发、但任务量没有大到必须引入专门 MQ 调度模型的场景。

它的优势在于：

* 轻量、接入简单、与 Redis 生态融合自然、适合做业务型延迟任务。

## Redisson 延迟队列不适合什么场景

它并不适合所有延迟任务，尤其不适合下面这些场景：

* 超大规模、超高吞吐的消息链路。
* 对消息可靠投递、消费确认、失败重投要求极高的场景。
* 需要非常完整消息治理能力的系统。

这些场景下，使用专业消息中间件通常更合适。

因此把 Redisson 放到项目里看，可以这样理解：

1. Redis 提供底层存储和原子操作。
2. Redisson 在 Redis 之上封装出分布式锁、延迟队列等高级能力。
3. 项目借助 Redisson 主要解决“并发控制”和“轻量级延迟任务”两类问题。
4. Redisson 延迟队列的核心不是“直接消费”，而是“先存储，再在到期时搬运到可消费队列”。
5. Pub/Sub 在这里是通知机制，不是任务本体。
6. 完成轻量级延迟任务，注意不等同于专业消息中间件。
