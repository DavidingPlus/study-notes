# 05-文档搜索功能

## 功能说明

1. 当前项目的搜索能力不是单独做了一个页面，而是集成在 `disk-by-cursor/src/views/Files.vue` 的工具栏搜索框里。
2. 当前搜索针对的是“当前登录用户自己的文件名”，不是文档正文、标签、分享信息或回收站内容。
3. 当前搜索范围受前端 `fileTypes` 过滤控制，和“当前目录”无关。
   * 也就是说，搜索会跨目录搜索当前用户在当前文件分类下的文件，而不是只搜当前打开文件夹。
4. 当前搜索结果直接复用文件列表表格展示，进入搜索模式后，`fileStore.files` 会被搜索结果替换。
5. 当前高亮不是由前端本地计算，也不是直接依赖 ES 返回的高亮字段，而是由后端统一生成 `highlightFilename` HTML 字符串后返回给前端。
6. 当前后端的查询策略是：
   * 优先查 ES 索引 `user_file_index`
   * ES 没有结果时回退 MySQL `user_file` 表，保证搜索可用
7. 当前 ES 增量同步代码已经接入 Canal，`networkdisk-files` 模块默认会加载 `canal.yml` 和 `es.yml`。

## 功能需求

文件搜索功能的目标，是让用户在当前文件分类下快速找到目标文件，并且在结果列表里直接继续原有的文件操作。

从业务角度看，这类能力通常需要满足以下几点：

1. 用户可以在文件页直接输入关键字并触发搜索，不需要跳转到新页面。
2. 搜索要支持模糊匹配，而不是只支持完整文件名精确命中。
3. 中文关键字需要具备一定的部分匹配能力，例如输入“代码随想录”时，也能命中只包含其中部分词片段的文件名。
4. 搜索结果最好附带高亮，方便用户快速判断命中位置。
5. 搜索在 ES 数据未同步完成或 ES 结果为空时，仍然要有数据库回退能力。
6. 搜索结果返回后，用户还能像普通文件列表一样继续点击文件夹、预览文件、下载文件或进入 AI 面板。

## 功能实现

### 整体思路

当前项目里的搜索链路可以概括为：

1. 用户在 `Files.vue` 顶部工具栏输入关键字。
2. 点击搜索按钮或按回车后，前端调用 `POST /api/v1/files/file/search`。
3. 前端把 `keyword` 和当前文件分类对应的 `fileTypes` 一起提交给后端。
4. 后端从登录态获取当前用户 `userId`，组装成 `FileSearchContext`。
5. 服务层先根据关键字构建搜索词集合 `searchTerms`。
6. 搜索服务优先查 ES 索引 `user_file_index`。
7. 如果 ES 没有结果，则回退到 MySQL `user_file` 表做 `like` 搜索。
8. 后端补齐每条结果的 `parentFilename`，并统一生成 `highlightFilename`。
9. 前端把结果直接放进当前文件列表，切换到 `isSearchMode = true`。
10. 用户点击“清空搜索”，或者切换分类、切换目录、点击面包屑后，页面退出搜索模式并恢复普通目录列表。

当前这条链路涉及的关键位置包括：

* 前端页面：`disk-by-cursor/src/views/Files.vue`
* 前端文件接口：`disk-by-cursor/src/api/file.js`
* 前端文件状态：`disk-by-cursor/src/stores/file.js`
* 后端控制器：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/controller/UserFileController.java`
* 后端搜索请求对象：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/request/FileSearchParamVO.java`
* 后端搜索上下文：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/context/FileSearchContext.java`
* 后端返回对象：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/response/FileSearchVO.java`
* 后端服务实现：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/service/impl/UserFileServiceImpl.java`
* ES 文档实体：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/infrastructure/es/entity/UserFileESEntity.java`
* ES Mapper：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/infrastructure/es/mapper/UserFileESMapper.java`
* Canal 同步任务：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/infrastructure/canal/sync/CanalUserFileEsSyncRunner.java`

### 3.1.1 当前前端交互形态

当前搜索交互完全发生在文件页内部，没有单独的搜索结果页。

在当前页面里：

* 顶部搜索框支持回车触发，也支持点击按钮触发。
* 搜索请求调用的是 `searchFiles(data)`，也就是 `POST /api/v1/files/file/search`。
* 提交参数中的 `fileTypes` 来自 `fileStore.fileTypes`，不是当前目录 ID。
* 文件分类和 `fileTypes` 的前端映射当前是：
  * `all -> -1`
  * `image -> 7`
  * `document -> 3,4,5,6,10,11,12`
  * `video -> 9`
  * `music -> 8`
  * `other -> 1,2`
* 只要处于搜索模式，表格里优先渲染 `row.highlightFilename`，通过 `v-html` 展示高亮。
* 点击“清空搜索”后，页面会重新按当前目录和当前文件分类拉取普通文件列表。
* 监听文件分类或根目录变化的 `watch` 会自动把 `isSearchMode` 置为 `false`。
* `openFolder()`、`navigateToFolder()`、`refreshCurrentFolder()` 这些动作也都会退出搜索模式。

需要特别说明的是：

* 当前前端提示文案写的是“搜索当前类型下的文件名”，这和代码是一致的。
* 当前搜索不是“当前目录内搜索”，因为请求里根本没有 `parentId`。
* 后端会返回 `parentFilename`，但当前前端列表没有把它展示出来。

### 搜索接口

当前后端提供的搜索接口为：

* `POST /api/v1/files/file/search`

当前请求参数为：

* `keyword`：必填，搜索关键字
* `fileTypes`：可选，多个文件类型用逗号分隔，`-1` 表示全部

控制器层的真实处理方式是：

1. 从登录态获取当前用户 `userId`
2. 把前端传来的 `keyword` 写入 `FileSearchContext`
3. 如果 `fileTypes` 不为空且不等于 `-1`，则拆成 `List<Integer>`
4. 调用 `userFileService.search(context)`

当前返回结果主要包括：

* `fileId`
* `parentId`
* `parentFilename`
* `filename`
* `highlightFilename`
* `fileSizeDesc`
* `folderFlag`
* `fileType`
* `updateTime`

其中：

* `fileId` 和 `parentId` 对外返回时会经过 `IdEncryptSerializer` 序列化成加密字符串
* `highlightFilename` 是后端拼装好的 HTML 字符串
* `updateTime` 来自 `gmt_modified`

### 搜索时的查询策略

搜索功能最核心的点，不在于“发一个关键字到后端”，而在于“如何在保证可用性的前提下做尽量合理的召回和展示”。

当前项目采用的是“关键字拆词 + ES 优先 + MySQL 回退 + 服务端统一高亮”的策略。

#### 搜索词构建

`UserFileServiceImpl.buildSearchTerms(...)` 当前会这样处理关键字：

1. 对原始关键字做 `trim`
2. 先把完整关键字本身加入搜索词集合
3. 再按空白字符拆词，把非空 token 加进去
4. 从关键字里提取纯中文串
5. 如果纯中文长度大于 2，则继续生成：
   * 所有 2 字子串
   * 所有 3 字子串
6. 最终去重，并按词长度从长到短排序

这意味着当前像“代码随想录”这样的关键字，不只会搜完整词，也会生成“代码”“随想”“想录”“代码随”“随想录”这类子串命中词。

#### ES 优先查询

当前 `UserFileServiceImpl.search(...)` 会优先使用 `UserFileESMapper` 查询 ES。

当前 ES 查询条件包括：

1. `filename like 搜索词集合中的任一词`
2. `userId = 当前登录用户`
3. `deleted = 0`
4. 如果前端传了 `fileTypes`，则额外 `fileType in (...)`
5. 按 `gmt_modified desc` 排序

查询命中后，服务层会把 ES 文档映射成 `FileSearchVO`，填充：

* `fileId`
* `parentId`
* `filename`
* `folderFlag`
* `fileType`
* `fileSizeDesc`
* `updateTime`

需要特别说明的是：

* 当前即使走 ES，返回高亮仍然不是直接依赖 ES 的高亮结果
* 当前服务层还是会在后面统一跑一遍 `applyHighlight(...)`

#### MySQL 回退

如果 ES 结果为空，当前代码会回退到 `doSearch(...)`。

这个回退查询不是走 `UserFileMapper.xml` 里的老 `searchFile` SQL，而是直接在服务层使用 MyBatis-Plus `QueryWrapper` 组装条件。

当前回退查询条件包括：

1. 只查当前登录用户
2. 只查 `deleted = 0`
3. 如果有 `fileTypes`，则按 `file_type in (...)` 过滤
4. 文件名对搜索词集合做多组 `like` OR 匹配
5. 按 `gmt_modified desc` 排序

因此，当前搜索即使 ES 没有结果，也不会直接失效。

#### 父目录名补齐

ES 或 MySQL 拿到初步结果之后，服务层还会执行 `fillParentFilename(...)`。

它的做法是：

1. 收集结果里的所有 `parentId`
2. 再用 `listByIds(parentIdList)` 回查这些父级目录记录
3. 把父目录名称写回每条 `FileSearchVO.parentFilename`

不过当前前端并没有把这个字段展示出来，所以它目前主要是后端结果里的补充信息。

#### 服务端高亮

当前高亮逻辑由 `buildHighlightFilename(...)` 完成，核心步骤是：

1. 对每个搜索词在文件名中做不区分大小写匹配
2. 收集所有命中区间
3. 对重叠命中区间做合并
4. 对普通文本做 HTML 转义
5. 对命中片段包裹 `<span class="search-highlight">...</span>`

也就是说，当前高亮能力是后端统一输出的，因此：

* ES 查询结果和 MySQL 回退结果的高亮样式是一致的
* 即使 ES 没返回高亮字段，前端也照样能显示黄色高亮效果

### ES 索引与 Canal 同步

#### ES 索引结构

当前 ES 文档实体是 `UserFileESEntity`，索引名为：

* `user_file_index`

当前主要索引字段包括：

* `id`
* `user_id`
* `parent_id`
* `real_file_id`
* `filename`
* `folder_flag`
* `file_size_desc`
* `file_type`
* `create_user`
* `gmt_create`
* `gmt_modified`
* `update_user`
* `deleted`
* `lock_version`

其中：

* `filename` 当前使用 `TEXT + IK_SMART` 分词
* 其它过滤字段主要按 `KEYWORD / INTEGER / DATE` 保存

#### Canal 增量同步

当前项目里已经有 `user_file -> ES` 的 Canal 同步实现。

代码位置包括：

* `networkdisk-business/networkdisk-files/src/main/java/com/disk/files/infrastructure/canal/config/CanalSyncProperties.java`
* `networkdisk-business/networkdisk-files/src/main/java/com/disk/files/infrastructure/canal/sync/CanalUserFileEsSyncRunner.java`

同步线程启动条件是：

1. `com.disk.canal.enable = true`
2. Spring 容器中存在 `UserFileESMapper`

当前 `networkdisk-files/src/main/resources/application.yml` 已经引入：

* `classpath:es.yml`
* `classpath:canal.yml`

当前 `canal.yml` 默认配置为：

* `enable: true`
* `host: 127.0.0.1`
* `port: 11111`
* `destination: example`
* `subscribe-filter: network_disk\\.user_file`

当前同步规则是：

1. `INSERT / UPDATE`：把 `user_file` 行数据 upsert 到 ES
2. `DELETE`：按 `id` 删除 ES 文档
3. 当前批次处理成功后 `ack`
4. 处理失败则 `rollback` 并等待下一轮重试

### 当前实现边界

为了保证文档和代码一致，当前搜索能力还需要明确这些边界：

1. 当前搜索只搜索文件名，不搜索文件内容。
2. 当前搜索不限制在当前目录，而是按“当前用户 + 当前文件类型”全局搜索。
3. 当前搜索结果既可能是文件，也可能是文件夹。
4. 当前前端不会展示 `parentFilename`，虽然服务端已经返回了这个字段。
5. 当前没有分页参数，搜索结果会直接按 `gmt_modified desc` 全量返回。
6. 当前没有搜索历史、热门关键字、最近搜索等独立数据表或接口。
7. 当前服务里仍然保留了 `UserFileMapper.xml` 里的老搜索 SQL，但搜索主链路实际不走那段 XML，而是走 ES 查询和服务层 `QueryWrapper` 回退。

## 数据模型

### `user_file_index`

作用：保存用户文件在 ES 中的索引文档，用于文件名搜索。

当前索引里的核心字段包括：

* `id`
* `user_id`
* `parent_id`
* `real_file_id`
* `filename`
* `folder_flag`
* `file_size_desc`
* `file_type`
* `gmt_create`
* `gmt_modified`
* `deleted`

这份索引的意义在于告诉系统：“当前用户有哪些文件，它们叫什么，属于什么类型，最近什么时候更新，能不能被搜索出来”。

### `user_file`

作用：保存用户自己的文件记录，也是搜索回退查询和 Canal 同步的源表。

当前搜索链路里实际会用到：

* `id`
* `user_id`
* `parent_id`
* `filename`
* `folder_flag`
* `file_size_desc`
* `file_type`
* `gmt_modified`
* `deleted`

也就是说：

* ES 查询用的是 `user_file` 的同步副本
* MySQL 回退则直接查 `user_file`
