# 03-文件上传功能

## 功能说明

1. 当前页面上传主入口是 `disk-by-cursor/src/components/UploadButton.vue`，`disk-by-cursor/src/views/Files.vue` 里实际接入的也是这个组件。
2. 当前前端默认所有文件都走分片上传链路，而不是“大文件才分片”。原因是 `getChunkUploadSwitch()` 固定返回 `true`。
3. 当前上传前会先在前端计算文件内容 MD5，并把它作为 `identifier`，先尝试秒传，未命中再进入分片上传。
4. 当前秒传命中的范围是“当前用户自己已经上传过的同内容文件”，不是全站跨用户共享物理文件。
5. 当前无论是秒传命中，还是分片合并成功，只要最终创建了普通文件的 `user_file` 记录，就会触发 `DocumentAiInitializer.scheduleInitialize(...)`，进入文档 AI 预热链路。
6. 当前后端虽然保留了 `/api/v1/files/file/upload` 单文件上传接口，但前端页面并不走这条链路；并且 `FileServiceImpl.storeMultipartFile(...)` 里没有真正调用存储引擎，因此文档不能把它写成当前已验证可用的主上传路径。
7. 当前代码里已经实现多文件上传、拖拽上传、上传任务面板、暂停/继续/取消/重试；但没有看到完整的“文件夹上传”实现。

## 功能需求

上传功能在业务上通常要同时满足几类目标：

1. 对已经上传过的相同内容文件，尽量走秒传，减少重复传输。
2. 对大文件和不稳定网络场景，支持分片上传和断点续传。
3. 在页面层面提供拖拽、多选、进度展示和任务控制，避免只靠浏览器原生上传框。
4. 上传完成后不仅要有物理文件，还要能落下用户目录视图，也就是 `user_file` 记录。
5. 上传链路结束后，还要允许后续业务继续接力，例如当前项目里的文档 AI 预热。

结合当前仓库代码，以上目标中已经落地的主要是：秒传、默认分片上传、断点续传、任务面板、上传完成后目录落库与 AI 预热；

## 功能实现

### 整体思路

当前上传链路可以概括为：

1. 用户在 `UploadButton.vue` 中选择文件或拖拽文件。
2. 前端把文件加入 `simple-uploader.js` 队列，并先计算文件 MD5。
3. 前端调用 `POST /api/v1/files/file/sec-upload` 做秒传校验。
4. 如果秒传命中，则后端直接复用已有 `file` 记录并新增 `user_file` 记录，前端刷新列表。
5. 如果秒传未命中，则前端走 `POST /api/v1/files/file/chunk-upload` 分片上传。
6. 所有分片齐全后，前端调用 `POST /api/v1/files/file/merge`，后端合并物理分片并保存 `file`、`user_file`。
7. 普通文件 `user_file` 创建完成后，会调度 `DocumentAiInitializer` 做 AI 预热。

当前相关关键位置包括：

* 前端上传组件：`disk-by-cursor/src/components/UploadButton.vue`
* 前端任务状态：`disk-by-cursor/src/stores/task.js`
* 前端上传接口：`disk-by-cursor/src/api/file.js`
* 前端公共上传参数：`disk-by-cursor/src/utils/common.js`
* 前端 MD5 工具：`disk-by-cursor/src/utils/md5.js`
* 后端控制器：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/controller/UserFileController.java`
* 后端文件服务：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/service/impl/UserFileServiceImpl.java`
* 后端分片服务：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/service/impl/FileChunkServiceImpl.java`
* 后端物理文件服务：`networkdisk-business/networkdisk-files/src/main/java/com/disk/files/domain/service/impl/FileServiceImpl.java`
* 默认存储引擎：`networkdisk-common/networkdisk-file/src/main/java/com/disk/file/local/LocalStorageEngine.java`

### 3.1.1 当前前端交互形态

当前页面上传不是一个简单的原生 `input[type=file]`，而是基于 `simple-uploader.js` 包装后的上传组件，页面层面已经具备这些行为：

* 支持点击上传。
* 支持拖拽文件到上传区域。
* 支持一次选择多个文件。
* 上传任务会进入“传输列表”面板。
* 支持暂停、继续、取消和失败后重试。

这里需要明确两个边界：

* 当前上传对话框标题是“文件上传”，实际能力也确实只覆盖文件，不包含目录层级上传。
* 当前任务面板状态是由 `task.js` 本地维护的，属于前端任务视图，不是后端单独保存了一份上传任务表。

### 秒传实现

#### 秒传入口

当前秒传接口为：

* `POST /api/v1/files/file/sec-upload`

请求体包括：

* `parentId`
* `filename`
* `identifier`

前端在 `UploadButton.vue` 里会先计算 MD5，然后调用该接口。只要命中，当前文件就不会继续上传物理内容。

#### 当前秒传的真实判定范围

`UserFileServiceImpl.secUpload(...)` 内部会调用：

* `fileService.getFileList(...)`

而 `FileServiceImpl.getFileList(...)` 的查询条件是：

* `create_user = 当前用户`
* `identifier = 当前文件 MD5`

因此当前秒传的真实行为是：

* 同一个用户上传过相同内容文件时，可以秒传。
* 不同用户之间不会因为内容相同而共享命中结果。

也就是说，当前更接近“按用户维度去重”，不是“全站物理文件去重”。

#### 前端 MD5 计算

当前前端 MD5 逻辑在 `disk-by-cursor/src/utils/md5.js`，实现方式是：

* 按 `2MB` 读取块逐段计算 MD5。
* 计算完成后把结果写入 `file.uniqueIdentifier`。

需要注意的是：

* `2MB` 是前端本地哈希计算时的读取粒度。
* 实际上传分片粒度不是 `2MB`，而是 `1MB`。

#### 秒传未命中不是异常

秒传未命中时，后端会返回业务码：

* `FILE_NOT_EXIT`

虽然这个错误码名称本身有拼写问题，但当前前端已经把它视为正常流程，收到后会继续走分片上传，不会直接判定上传失败。

#### 秒传命中后的后续动作

秒传命中后，系统会：

1. 复用已有 `file` 表记录。
2. 新增当前目录下的 `user_file` 记录。
3. 刷新前端文件列表。
4. 如果是普通文件，再通过 `saveUserFile(...)` 触发 `DocumentAiInitializer.scheduleInitialize(...)`。

所以当前项目里“秒传命中”只是跳过物理传输，不会跳过后续目录落库和 AI 初始化。

### 分片上传实现

#### 当前前端上传参数

当前上传参数集中在 `disk-by-cursor/src/utils/common.js` 和 `UploadButton.vue`：

* 分片上传开关：始终开启
* 单片大小：`1MB`
* 单文件前端大小限制：`3GB`
* 并发上传分片数：`3`
* `testChunks = true`

后端 `networkdisk-files` 模块 `application.yml` 里还配置了：

* `spring.servlet.multipart.max-file-size = 4096MB`
* `spring.servlet.multipart.max-request-size = 4096MB`

所以当前代码层面的真实约束是：

* 页面层面单文件限制 `3GB`
* 服务端 Multipart 上限 `4096MB`

#### 3.3.2 分片上传接口

当前分片上传接口为：

* `POST /api/v1/files/file/chunk-upload`

表单参数包括：

* `filename`
* `identifier`
* `totalChunks`
* `chunkNumber`
* `currentChunkSize`
* `totalSize`
* `file`

返回体里的关键字段是：

* `mergeFlag`

它来自 `MergeFlagEnum`：

* `0`：`NOT_READY`
* `1`：`READY`

这表示当前片上传完之后，服务端判断该文件是否已经具备合并条件。

#### 3.3.3 已上传分片查询接口

当前断点探测接口为：

* `GET /api/v1/files/file/chunk-upload`

查询参数只有：

* `identifier`

返回体字段为：

* `uploadedChunks`

前端 `simple-uploader` 会用这份编号列表判断哪些分片已经传过，并在本次上传里直接跳过这些分片。

#### 3.3.4 服务端分片落盘

`FileChunkServiceImpl.saveChunkFile(...)` 的真实执行顺序是：

1. 先清理同一唯一键下已经逻辑删除或已过期的旧分片记录。
2. 判断当前分片是否已经上传过。
3. 如果未上传，则调用存储引擎保存分片文件。
4. 保存 `file_chunk` 记录。
5. 再判断当前 `identifier` 下有效分片数量是否已经等于 `totalChunks`。

分片唯一性依赖的是：

* `identifier`
* `chunk_number`
* `create_user`

当前分片过期时间由 `DiskConfig.chunkFileExpirationDays` 控制，默认值是 `1` 天。

#### 3.3.5 当前默认存储方式

当前默认存储引擎是 `LocalStorageEngine`，并且被标注为 `@Primary`。

在本地存储实现下：

* 普通文件写入 `rootFilePath` 对应目录。
* 分片文件写入 `rootFileChunkPath` 对应目录。
* 分片真实路径由 `identifier + chunkNumber` 规则生成。
* 合并时按分片编号顺序追加写入最终文件，然后删除分片文件。

#### 3.3.6 分片上传并发保护

为避免同一用户同一文件标识在并发上传时发生冲突，`UserFileServiceImpl.chunkUpload(...)` 上加了：

* `@DistributeLock(scene = "FILE_CHUNK_UPLOAD", keyExpression = "#context.userId + '-' + #context.identifier")`

因此当前系统对“同一用户 + 同一 identifier”的分片写入做了串行保护。

### 3.4 分片合并实现

当前分片合并接口为：

* `POST /api/v1/files/file/merge`

请求体包括：

* `filename`
* `identifier`
* `totalSize`
* `parentId`

服务端合并流程为：

1. 查询当前用户、当前 `identifier` 下所有未过期分片记录。
2. 按 `chunkNumber` 升序排序。
3. 调用存储引擎合并分片文件。
4. 保存 `file` 表记录。
5. 保存 `user_file` 表记录。
6. 物理删除分片文件。
7. 物理删除 `file_chunk` 表记录。

这里要特别说明一点：

* 合并完成后不仅是“文件传完了”，还会因为 `saveUserFile(...)` 的执行，把这份文件纳入用户目录，并触发文档 AI 预热。

### 3.5 断点续传实现

当前项目的断点续传，不依赖浏览器自动续传，而是依赖：

* 文件内容 MD5
* 已上传分片查询
* 已传分片跳过
* 最终合并

实际流程是：

1. 前端对同一个文件再次上传时，会重新得到同一个 `identifier`。
2. 上传前先调用 `GET /file/chunk-upload?identifier=...`。
3. 服务端返回当前用户、当前 `identifier` 下仍然有效的分片编号。
4. 前端跳过这些分片，只补传缺失分片。
5. 所有分片齐全后再发起合并。

因此，当前断点续传的真实边界是：

* 只在“同一用户 + 同一文件内容 MD5 + 分片未过期”前提下成立。
* 超过分片过期时间后，旧分片会失效，需要重新补传。

### 3.6 当前实现边界

为了保证文档和代码一致，当前上传功能还需要补充下面这些边界：

#### 3.6.1 页面主链路不是单文件直传

虽然有 `/api/v1/files/file/upload` 接口，但当前前端默认始终走：

* 秒传校验
* 分片上传
* 分片合并

而不是直接把整文件一次发到 `/file/upload`。

#### 3.6.2 单文件上传接口不应写成当前成熟能力

`FileServiceImpl.storeMultipartFile(...)` 里当前只创建了 `StoreFileContext`，但没有真正调用 `storageEngine.store(...)`。

因此更准确的表述应当是：

* 当前后端保留了单文件上传接口定义。
* 但当前页面不走它，而且这条直传代码链路也不应被文档描述成已经作为主链路验证通过。

#### 3.6.3 当前未看到文件夹上传实现

当前前端没有 `webkitdirectory`、`relativePath` 之类的目录上传参数，后端上传接口也没有目录层级恢复字段，因此不能把“文件夹上传”写成现状能力。

#### 3.6.4 当前已实现上传任务控制

这部分已经落地，包括：

* 多文件上传
* 拖拽上传
* 暂停
* 继续
* 取消
* 失败后重试

## 4. 数据模型

### 4.1 `file`

作用：保存真实物理文件元数据。

核心字段包括：

* `id`
* `filename`
* `real_path`
* `file_size`
* `file_size_desc`
* `file_suffix`
* `file_preview_content_type`
* `identifier`
* `create_user`

和上传链路最相关的索引包括：

* `idx_file_create_user_identifier`
* `idx_file_identifier`

这也说明当前秒传和物理文件查询的重要条件之一就是 `identifier`。

### 4.2 `user_file`

作用：保存用户目录中的文件视图。

核心字段包括：

* `id`
* `user_id`
* `parent_id`
* `real_file_id`
* `filename`
* `folder_flag`
* `file_size_desc`
* `file_type`
* `deleted`

上传完成后，真正决定“用户在目录里看不看得到这个文件”的，不是 `file` 表，而是这里的 `user_file` 记录。

### 4.3 `file_chunk`

作用：保存分片上传阶段的临时分片记录。

核心字段包括：

* `identifier`
* `real_path`
* `chunk_number`
* `expiration_time`
* `create_user`

关键约束包括：

* 唯一索引 `uk_identifier_chunk_number_create_user`

这意味着当前系统会按“文件 MD5 + 分片编号 + 用户”保证同一分片记录唯一。
