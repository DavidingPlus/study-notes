# 06-分享链接功能

## 功能说明

1. 当前项目的分享能力由 `networkdisk-business/networkdisk-share` 模块提供，前端主要有 3 个入口：文件页单项分享、我的分享页管理、匿名分享访问页。
2. 当前分享的本质，是把一个或多个 `user_file` 记录挂到一条 `share` 记录下面，并通过 `share_file` 做关联，而不是直接把物理文件暴露给外部。
3. 当前分享支持两种类型：
   * `shareType = 0`：公开分享
   * `shareType = 1`：私密分享，需要提取码
4. 当前无论公开还是私密分享，后端创建分享时都会生成一个 4 位小写字母提取码；只是公开分享在访问时不会强制校验该提取码。
5. 当前分享链接默认由 `com.disk.share.access-url-prefix` 组装，仓库默认配置为 `http://localhost:5173/share`，因此默认分享地址形如 `http://localhost:5173/share?shareId=加密后的分享ID`。
6. 当前过期处理采用“双保险”：
   * 访问分享时实时校验是否过期
   * 创建分享后为非永久分享注册延迟删除任务，到期后自动逻辑删除 `share` 和 `share_file`
7. 当前匿名分享页只支持展示“这条分享直接挂载的文件项”，并支持单文件下载；如果分享项本身是文件夹，页面会展示出来，但当前不能继续下钻，也不能直接下载文件夹。

## 功能需求

分享功能的目标，是让登录用户可以把自己的网盘文件以链接形式发给别人，并根据业务需要控制是否要提取码、分享多久、过期后如何失效。

从业务角度看，这类能力通常需要满足以下几点：

1. 登录用户可以创建分享，并得到可复制的分享链接。
2. 分享可以区分公开访问和私密访问，私密访问必须先校验提取码。
3. 分享要支持有限期和永久有效两种模式。
4. 分享拥有者要能查看、复制、取消自己创建的分享。
5. 匿名访问者不需要登录，也可以根据链接查看分享基础信息并下载允许下载的文件。
6. 分享到期后不能继续访问，同时后台要有自动失效机制，避免无效分享长期残留。
7. 分享链路不能绕过原始文件记录，下载时仍然要回到 `user_file` 和 `file` 记录校验实际可读文件。

## 功能实现

### 整体思路

当前项目里的分享链路可以概括为：

1. 登录用户在 `disk-by-cursor/src/views/Files.vue` 或 `disk-by-cursor/src/views/Shares.vue` 发起创建分享。
2. 前端把分享名称、分享类型、有效期类型和加密后的 `shareFileIds` 提交到 `POST /api/v1/shares/share`。
3. 后端通过 `ShareConvertor` 把前端传来的加密文件 ID 解密成内部 `user_file.id`，组装为 `CreateShareContext`。
4. `ShareServiceImpl` 生成一条 `share` 主记录，并为每个被分享文件生成一条 `share_file` 关联记录。
5. 如果本次分享不是永久有效，则在事务提交后把“删除该分享”的消息放入延迟队列，等待过期时自动触发逻辑删除。
6. 登录用户可以通过 `/api/v1/shares/list` 查看自己的分享列表，通过 `/api/v1/shares/share` 查询单条详情，通过 `DELETE /api/v1/shares/share` 取消分享。
7. 匿名访问者打开分享链接后，前端路由会进入 `disk-by-cursor/src/views/ShareAccess.vue`，从 URL 里的 `shareId` 拉取基础信息。
8. 如果是私密分享，前端会先调用 `/api/v1/shares/share/code/check` 校验提取码；如果是公开分享，则直接进入文件列表加载。
9. 前端通过 `/api/v1/shares/share/files` 获取这条分享下直接挂载的文件列表。
10. 匿名访问者点击下载时，前端调用 `/api/v1/shares/share/file/download`，后端在校验分享可用、提取码、文件映射和物理文件都存在之后，直接把文件流写回响应。

当前这条链路涉及的关键位置包括：

* 前端接口封装：`disk-by-cursor/src/api/share.js`
* 前端文件页分享入口：`disk-by-cursor/src/views/Files.vue`
* 前端我的分享页：`disk-by-cursor/src/views/Shares.vue`
* 前端匿名访问页：`disk-by-cursor/src/views/ShareAccess.vue`
* 前端分享访问路由：`disk-by-cursor/src/router/index.js`
* 后端控制器：`networkdisk-business/networkdisk-share/src/main/java/com/disk/share/controller/UserShareController.java`
* 后端领域服务：`networkdisk-business/networkdisk-share/src/main/java/com/disk/share/domain/service/impl/ShareServiceImpl.java`
* 分享参数转换：`networkdisk-business/networkdisk-share/src/main/java/com/disk/share/domain/entity/convertor/ShareConvertor.java`
* 延迟删除执行器：`networkdisk-business/networkdisk-share/src/main/java/com/disk/share/job/delay/DeleteShareInfoDelayQueueExecutor.java`
* 延迟队列工厂：`networkdisk-common/networkdisk-delay-message/src/main/java/com/disk/delayqueue/executor/DelayQueueExecutorFactory.java`

### 3.1.1 当前前端交互形态

当前前端并不是只有一个分享页面，而是把“创建分享”“管理分享”“匿名访问分享”拆成了三个场景。

在当前页面里：

* `Files.vue` 的文件行操作区始终提供“分享”按钮。
* `Files.vue` 里的分享弹窗一次只分享当前点击的这一项，既可以分享文件，也可以分享文件夹。
* `Files.vue` 的分享类型用 `withCode / withoutCode` 表示，有效期用 `permanent / 1day / 7days / 30days` 表示，提交前会转成旧式中文字符串。
* `Shares.vue` 提供“我的分享”管理页，支持查看列表、复制链接、复制分享码、查看详情、取消分享。
* `Shares.vue` 的“创建分享”弹窗支持一次选择多个分享项，但当前候选列表来自根目录 `getFileList(parentId = rootFileId)`，并不是整棵目录树。
* `Shares.vue` 页面上有“续期”按钮，但当前只是前端提示“开发中”，后端没有对应续期接口。
* `ShareAccess.vue` 对应公开路由 `/share`，不要求登录。
* `ShareAccess.vue` 对私密分享会先展示提取码输入框；公开分享则直接拉文件列表。
* `ShareAccess.vue` 当前对 `folderFlag = 1` 的项会禁用下载，并提示暂不支持从分享页直接下载文件夹。

### 分享接口

当前后端控制器的统一前缀是：

* `/api/v1/shares`

其中，登录后使用的接口有：

* `GET /api/v1/shares/list`
* `GET /api/v1/shares/share`
* `POST /api/v1/shares/share`
* `DELETE /api/v1/shares/share`

其中，匿名可访问的接口有：

* `GET /api/v1/shares/share/simple`
* `POST /api/v1/shares/share/code/check`
* `GET /api/v1/shares/share/files`
* `GET /api/v1/shares/share/file/download`

当前外部可见的 `shareId` 和 `fileId` 都不是数据库里的裸 Long，而是经过加密序列化后的字符串：

* `UserShareInfoVO.id` 会被序列化为加密后的 `shareId`
* `ShareFileInfoVO.fileId` 会被序列化为加密后的 `user_file.id`
* 创建分享时前端传入的 `shareFileIds` 也是加密后的 `user_file.id`

#### 创建分享接口

当前创建分享接口为：

* `POST /api/v1/shares/share`

当前请求参数为：

* `shareName`：必填，分享名称
* `shareType`：必填，`0` 公开分享，`1` 私密分享
* `shareDayType`：必填，分享有效期类型
* `shareFileIds`：必填，加密后的 `user_file.id` 列表

当前 `shareDayType` 的后端兼容范围比较宽，源码支持以下形式：

* `-1`、`1`、`7`、`30`
* `permanent`、`1day`、`7days`、`30days`
* 旧式中文值，例如“永久有效”“1天”“7天”“30天”

这也是为什么当前 `Files.vue` 和 `Shares.vue` 虽然传值格式不同，但都能创建成功。

#### 分享详情与管理接口

当前管理侧常用接口为：

1. `GET /api/v1/shares/list`
   * 返回当前登录用户创建的分享列表
2. `GET /api/v1/shares/share?shareId=...`
   * 按分享 ID 查询一条分享详情
3. `DELETE /api/v1/shares/share`
   * 请求体只需要 `shareId`
   * 实际执行的是逻辑删除 `share` 和 `share_file`，不是物理删除文件

#### 匿名访问接口

当前匿名访问链路对应的接口为：

1. `GET /api/v1/shares/share/simple`
   * 返回分享基础信息
   * 控制器会主动把 `shareCode` 置空，避免把提取码直接暴露给匿名访问者
2. `POST /api/v1/shares/share/code/check`
   * 校验私密分享提取码
   * 通过则只返回 `true`，不下发单独的访问令牌
3. `GET /api/v1/shares/share/files`
   * 返回分享下直接挂载的文件列表
4. `GET /api/v1/shares/share/file/download`
   * 下载分享中的单个文件

### 创建分享时的真实处理

当前 `ShareServiceImpl.addUserShareInfo(...)` 在创建分享时的核心流程是：

1. 取前端传来的 `shareFileIds`
2. 生成新的 `shareId`
3. 通过 `ShareDayTypeEnum.getDayByType(...)` 把 `shareDayType` 解析成实际天数
4. 组装 `share` 主记录
5. 为每个分享项生成一条 `share_file` 映射记录
6. 保存 `share`
7. 批量保存 `share_file`
8. 如果不是永久分享，则注册延迟删除任务

当前组装出来的 `share` 主记录有这些关键字段：

* `shareName`
* `shareType`
* `shareDayType`
* `shareDay`
* `shareEndTime`
* `shareStatus`
* `shareCode`
* `shareUrl`
* `createUser`

其中：

* `shareEndTime` 的计算规则是：永久分享写 `null`，非永久分享写“当前时间 + N 天”
* `shareStatus` 创建时固定写成 `ShareStatusEnum.NORMAL`，也就是 `0`
* `shareCode` 当前固定由 `RandomStringUtils.randomAlphabetic(4).toLowerCase()` 生成
* `shareUrl` 当前由 `buildShareUrl(...)` 根据配置前缀和加密后的 `shareId` 拼出来

### 匿名访问时的校验与下载

匿名访问的核心不是“拿到分享链接就直接读文件”，而是每一步都要重新确认分享是否还可用。

#### 分享可用性校验

当前真正负责“分享是否还能访问”的方法是 `assertShareAvailable(...)`。它会：

1. 根据 `shareId` 查询 `share` 记录，要求 `deleted = 0`
2. 如果查不到，则抛出 `SHARE_NOT_FOUND`
3. 如果不是永久分享，且 `share_end_time` 已早于当前时间，则抛出 `SHARE_EXPIRED`

需要特别说明的是：

* `GET /share/simple` 当前只检查“分享记录是否存在且未逻辑删除”，不会调用 `assertShareAvailable(...)`
* 因此如果某条分享已经过期、但延迟删除任务还没把它逻辑删除，匿名页仍然可能先看到基础信息
* 真正决定“还能不能继续访问文件列表或下载”的，是后面的提取码校验、文件列表和下载接口

#### 提取码校验

当前提取码校验逻辑是：

1. 只有 `shareType = 1` 时才要求校验提取码
2. 公开分享直接跳过提取码判断
3. 私密分享会把前端传入的 `shareCode` 做 `trim`
4. 当前比较逻辑使用 `StringUtils.equalsIgnoreCase(...)`

也就是说，当前提取码大小写不敏感。

#### 文件列表

当前 `listShareFiles(...)` 的真实行为是：

1. 先校验分享是否可用
2. 如果是私密分享，再校验提取码
3. 查询这条分享下所有 `share_file` 映射，按 `gmt_create desc` 排序
4. 取出映射里的 `file_id`
5. 批量查询对应的 `user_file` 记录
6. 过滤掉已经逻辑删除的 `user_file`
7. 转成 `ShareFileInfoVO` 返回给前端

当前返回给匿名页的文件项主要包括：

* `fileId`
* `filename`
* `folderFlag`
* `fileType`
* `fileSizeDesc`
* `updateTime`

需要特别说明的是：

* 当前接口没有 `parentId` 参数
* 当前实现返回的是“分享时直接挂载的项”，不是某个分享目录的下一级列表
* 因此前端虽然可以显示被分享的文件夹，但当前没有继续浏览文件夹内部内容的后端接口

#### 单文件下载

当前 `downloadShareFile(...)` 的处理流程是：

1. 校验分享是否可用
2. 私密分享时校验提取码
3. 校验 `share_file` 中确实存在 `shareId + fileId` 这条映射
4. 根据 `fileId` 查询 `user_file`
5. 校验 `user_file` 没有被逻辑删除
6. 如果当前项是文件夹，则直接抛 `INVALID_ARGS`
7. 根据 `user_file.real_file_id` 查询物理文件表 `file`
8. 校验 `file` 没有被逻辑删除，且 `real_path` 在磁盘上真实存在
9. 设置下载响应头
10. 直接从物理路径打开输入流，把文件内容写到 HTTP 响应输出流

因此当前分享下载走的是“数据库记录校验 + 本地物理文件流式输出”模式，而不是走对象存储签名 URL。

### 过期处理与延迟删除

当前分享的过期处理不是定时扫库，而是基于延迟队列。

#### 创建时登记延迟任务

`scheduleShareExpireDeleteJob(...)` 当前的处理规则是：

1. 如果分享为空，直接跳过
2. 如果是永久分享，直接跳过
3. 如果 `shareEndTime` 为空，直接跳过
4. 否则计算 `shareEndTime - 当前时间` 得到延迟毫秒数
5. 组装 `DeleteShareInfoMessage`，只携带 `shareId`
6. 在事务提交成功后，把消息投递到 `deleteShareInfoDelayQueue`

这里之所以放在 `afterCommit()` 中执行，是为了避免数据库事务还没提交成功，就提前把延迟删除任务放进队列。

#### 到期后执行逻辑删除

当前到期执行器是 `DeleteShareInfoDelayQueueExecutor`。它会：

1. 从 `deleteShareInfoDelayQueue` 里阻塞式消费到期消息
2. 拿到 `shareId`
3. 组装 `DeleteShareContext`
4. 调用 `shareService.deleteUserShare(...)`

而 `deleteUserShare(...)` 当前会：

1. 把 `share.deleted` 更新为已删除
2. 把该分享下所有 `share_file.deleted` 更新为已删除
3. 尝试把还没执行的延迟任务从队列里移除

因此当前所谓的“分享过期删除”，本质上是“逻辑删除分享记录及其映射关系”，并不会删除用户原始文件。

#### 队列启动方式

当前延迟队列消费者不是手动启动的，而是依赖 `DelayQueueExecutorFactory` 在 Spring 容器启动完成后自动扫描所有 `DelayQueueExecutor` 实现并启动对应线程。

当前分享模块使用的队列名称是：

* `deleteShareInfoDelayQueue`

底层 `DelayQueueHolder` 的默认实现是 `RedisDelayQueueHolder`，即基于 Redisson 的 `RBlockingDeque + RDelayedQueue`。

### 分享链接与提取码生成

当前分享链接的组装逻辑是：

1. 先把内部 Long 型 `shareId` 加密
2. 再做 URL 编码
3. 然后根据 `shareAccessUrlPrefix` 拼接

当前支持三种前缀写法：

1. 如果前缀里显式包含 `{shareId}`，则直接替换占位符
2. 如果前缀本身已经带查询串，则自动追加 `shareId=...`
3. 如果前缀只是普通路径，则自动补成 `?shareId=...`

因此默认配置：

* `com.disk.share.access-url-prefix = http://localhost:5173/share`

最终会得到类似：

* `http://localhost:5173/share?shareId=xxxxx`

### 当前实现边界

为了保证文档和代码一致，当前分享能力还需要明确这些边界：

1. 当前没有“保存到我的网盘”接口，也没有分享页内的二级目录浏览能力。
2. 当前匿名访问不会下发独立的分享访问会话或 token；私密分享只是每次请求都重新带 `shareCode`。
3. 当前 `share/simple` 不做过期校验，只返回基础信息；真正的访问限制发生在后续校验和文件操作上。
4. 当前后端虽然定义了 `ShareStatusEnum.FILE_DELETED = 1`，但创建分享时只会写入 `0`，源码里没有自动把状态维护成“即将过期”或“已过期”。
5. 当前 `Shares.vue` 页面上“续期”只是占位交互，后端没有对应实现。
6. 当前 `Shares.vue` 的创建分享弹窗只加载根目录第一层文件作为候选项，不是全量文件树。
7. 当前分享模块在创建分享时主要负责写入 `share` / `share_file` 记录和登记延迟任务，后续真正的文件有效性依赖列表和下载时对 `user_file`、`file`、物理路径的再次校验。

## 数据模型

### `share`

作用：保存一条分享链接本身的元数据。

当前表里记录的核心信息包括：

* `id`
* `share_name`
* `share_type`
* `share_day_type`
* `share_day`
* `share_end_time`
* `share_url`
* `share_code`
* `share_status`
* `create_user`
* `gmt_create`
* `gmt_modified`
* `deleted`

这张表的意义在于告诉系统：“谁创建了一条分享、分享给谁看、多久过期、访问地址是什么、是否还有效”。

需要特别说明的是：

* 对外返回时，`id` 会被序列化为加密后的字符串
* 当前 `share_status` 字段虽然存在，但源码里主要还是依赖 `share_end_time` 和 `deleted` 判断是否可访问

### `share_file`

作用：保存“某条分享包含哪些用户文件”的映射关系。

当前表里记录的核心信息包括：

* `id`
* `share_id`
* `file_id`
* `create_user`
* `gmt_create`
* `gmt_modified`
* `deleted`

这张表的意义在于告诉系统：“这条分享具体挂了哪些 `user_file` 记录”。

### `user_file` 与 `file`

分享模块本身并不重复保存文件完整元信息，而是通过关联回原始文件表继续工作。

当前分享链路里实际会用到：

* `user_file.id`
* `user_file.real_file_id`
* `user_file.filename`
* `user_file.folder_flag`
* `user_file.file_size_desc`
* `user_file.file_type`
* `file.real_path`
* `file.file_size`

也就是说：

* 文件列表展示主要来自 `user_file`
* 实际下载时会再追到 `file.real_path`

### 当前没有单独的分享访问会话表

需要特别说明的是，当前项目并没有专门保存：

* 匿名访问者会话
* 提取码校验票据
* 分享访问日志
* 分享下载日志
* 分享保存到我的网盘记录

因此当前分享能力更接近“可控链接访问 + 文件流下载”，还不是“完整的分享协作产品”。
