# 01-基础功能-注册/登录（权限控制）

![1777474319536-03405f58-15eb-49f1-a53b-f65ec9a9d839.jpeg](https://cdn.davidingplus.cn/images/2026/09/11/1777474319536-03405f58-15eb-49f1-a53b-f65ec9a9d839-314909.jpeg)

* 用户注册时，前端 Register.vue 先收集 email、nickName、password，并在本地校验邮箱格式、密码长度和两次密码一致性。校验通过后，请求 POST /api/v1/auth/register。认证服务 networkdisk-auth 接收后，先通过 Dubbo 调用用户服务创建用户，写入 user表；随后再调用文件服务创建用户根目录，在 user\_file 表中生成默认的“全部文件”目录。注册成功后，前端提示用户跳转到登录页。
* 用户登录时，前端 Login.vue 提交 email 和 password 到 POST /api/v1/auth/login。认证服务会按邮箱查询用户，生成 JWT，并把JWT 写入 Redis，key 为 USER\_LOGIN\_{userId}，然后把 JWT 返回给前端。前端将 token 保存到 Pinia 和 Cookie 中，后续请求都会通过 Authorization 请求头携带该 token。
* 登录成功后，前端立即调用 GET /api/v1/users/get-user-info 获取当前用户信息。请求进入后端时，UserInfoLoginAspect 会先解析 Authorization 中的 JWT，取出用户 ID，再去 Redis 比对 token 是否一致。校验通过后，把用户 ID 写入 UserIdUtil。用户服务随后根据该用户 ID 查询 user 表和用户根目录记录，返回 nickname、头像、rootFileId、rootFilename 等信息。前端拿到rootFileId 后，就可以进入用户的网盘根目录并加载文件列表。

## 1. 功能说明

1. 当前前端注册入口是 `disk-by-cursor/src/views/Register.vue`，登录入口是 `disk-by-cursor/src/views/Login.vue`，状态管理统一走 `disk-by-cursor/src/stores/user.js`。
2. 当前注册页面实际提交的字段只有 `email`、`nickName`、`password`；`confirmPassword` 只做前端本地校验，不会提交给后端。当前登录页面实际提交的字段只有 `email`、`password`；
3. 当前登录成功后，前端会把 token 写入 Pinia 和 Cookie，并立刻调用 `GET /api/v1/users/get-user-info` 获取当前用户信息与根目录 ID。
4. 当前业务接口的登录态校验，主要依赖 `JWT + Redis + UserInfoLoginAspect`。

## 2. 功能需求

登录注册这类基础能力，需要做到：

1. 注册时创建用户，并为新用户准备网盘根目录。
2. 登录后返回可用于后续业务请求的身份凭证。
3. 每次业务请求进入服务端时，都能稳定识别当前登录用户。
4. 退出登录时，前端本地状态和服务端缓存状态都能被清理。

## 3. 功能实现

### 3.1 注册实现

#### 3.1.1 前端注册流程

注册页面位于：

* `disk-by-cursor/src/views/Register.vue`

在前端页面注册流程是：

1. 用户填写 `email`、`nickName`、`password`、`confirmPassword`。
2. 页面本地校验邮箱格式、昵称长度、密码长度以及两次密码一致性。
3. 校验通过后，调用 `userStore.registerAction(...)`。
4. `registerAction(...)` 实际调用 `POST /api/v1/auth/register`。
5. 注册成功后，页面提示“注册成功，请登录”，并跳转到 `/login`。

#### 3.1.2 后端注册流程

当前后端注册入口位于：

* `networkdisk-auth/src/main/java/com/disk/auth/controller/AuthController.java`

接口为：

* `POST /api/v1/auth/register`

控制器接收的参数对象是：

* `RegisterParamVO`

其中字段包括：

* `email`
* `password`
* `nickName`
* `checkCode`
* `emailCode`

需要注意，当前接口参数类里有验证码相关字段，但当前注册流程并没有真正做图形验证码或邮箱验证码校验，可以作为扩展方向。

#### 3.1.3 用户服务落库逻辑

`AuthServiceImpl.register(...)` 的真实执行顺序是：

1. 组装 `UserRegisterRequest`。
2. 通过 Dubbo 调用 `UserFacadeService.register(...)` 创建用户。
3. 用户创建成功后，再调用 `UserFileFacadeService.createUserRootFile(...)` 创建根目录。
4. 最终返回新用户 ID，控制器再把它加密后返回给前端。

用户真正落库发生在：

* `networkdisk-business/networkdisk-user/src/main/java/com/disk/user/domain/service/UserService.java`

当前注册时会写入这些关键信息：

* `id`：通过 `IdUtil.get()` 生成
* `email`
* `nickName`
* `passwordHash`：通过 `PasswordUtil.encryptPassword(...)` 保存，当前实现是 MD5
* `useSpace = 0`
* `totalSpace = USER_INIT_SPACE`
* `lastLoginTime = new Date()`
* `profilePhotoUrl`：默认写入一个固定头像 URL
* `deleted = 0`

其中 `USER_INIT_SPACE` 当前值为：

* `1024 * 1024 * 1024L`

也就是默认初始化 `1GB` 总空间。

#### 3.1.4 根目录初始化

注册成功后，认证服务会继续调用文件服务创建用户根目录。

当前根目录初始化行为是：

* 目录名称来自 `BaseConstant.USER_ROOT_FILE`
* 当前常量值是 `全部文件`
* `parentId = 0`
* `folder_flag = 1`

因此当前项目里，注册不只是“插入一条用户记录”，还会同步建立 `user_file` 里的根目录记录。

### 3.2 登录实现

#### 3.2.1 前端登录流程

当前登录页面位于：

* `disk-by-cursor/src/views/Login.vue`

页面行为是：

1. 用户填写 `email`、`password`。
2. 页面本地做必填和密码长度校验。
3. 调用 `userStore.loginAction(...)`。
4. `loginAction(...)` 调用 `POST /api/v1/auth/login`。
5. 登录成功后，先把 token 写入 Cookie 和 Pinia，再调用 `getUserInfoAction()` 拉取当前用户信息。
6. 前端随后调用 `fileStore.initRoot()`，把当前用户根目录加载进文件页。

当前 Cookie 的保存逻辑位于 `userStore.setToken(...)`，保存方式是：

* key：`token`
* 有效期：`7` 天

#### 3.2.2 后端登录流程

当前后端登录入口是：

* `POST /api/v1/auth/login`

请求对象是：

* `LoginParamVO`

包含字段：

* `email`
* `password`
* `checkCode`
* `rememberMe`

但当前服务实现 `AuthServiceImpl.login(...)` 的真实逻辑是：

1. 通过 `userFacadeService.query(...)` 按邮箱查询用户。
2. 如果用户不存在，则抛出 `USER_NOT_EXIST`。
3. 调用 `StpUtil.login(userId)`。
4. 通过 `JWTUtil.generateToken(...)` 生成 JWT。
5. 把 JWT 写入 Redis，key 为 `USER_LOGIN_{userId}`。
6. 把 JWT 原样返回给前端。

这里要特别说明几个和代码一致的事实：

* 当前登录逻辑没有比对数据库里的 `passwordHash`。
* `password` 字段虽然是必填参数，但当前服务层没有真正使用它。
* `checkCode` 当前没有校验。
* `rememberMe` 当前也没有参与 token 过期策略。

所以文档不能写成“当前登录已完成邮箱 + 密码 + 验证码联合校验”，因为这和代码现状不一致。

#### 3.2.3 当前 token 的真实形态

当前返回给前端的是 JWT，不是 Sa-Token 直接暴露出的会话凭证。

生成 token 时使用的是：

* claim key：`LOGIN_USER_ID`
* 过期时间：`AuthConstant.ONE_DAY_TIME_MILLS`

也就是：

* JWT 过期时间是 `1` 天

而 Redis 写入当前是：

* `stringRedisTemplate.opsForValue().set(BaseConstant.USER_LOGIN_PREFIX + userInfo.getUserId(), accessToken);`

没有显式 TTL。

因此当前登录态存在一个实际边界：

* JWT 自身带 1 天过期时间。
* 前端 Cookie 配置了 7 天。
* Redis 里的 token 当前没有单独设置过期时间。

文档需要把这个差异写清楚，而不能简单写成“统一 7 天登录态”。

### 3.3 登录后鉴权实现

#### 3.3.1 前端如何携带 token

当前 axios 实例统一通过：

* `disk-by-cursor/src/utils/attachInterceptors.js`

在请求拦截器里追加：

* `Authorization: token`

因此后续文件、用户、分享等业务请求，都是靠这个请求头把登录态带到后端。

#### 3.3.2 后端如何识别当前用户

当前业务接口的登录校验主要发生在：

* `networkdisk-common/networkdisk-web/src/main/java/com/disk/web/aspect/UserInfoLoginAspect.java`

这个切面会拦截：

* `execution(* com.disk.*.controller..*(..))`

并对没有标记 `@LoginIgnore` 的接口执行校验。真实校验步骤是：

1. 从请求头 `Authorization` 或请求参数 `authorization` 中读取 token。
2. 用 `JWTUtil.analyzeToken(...)` 解析 `LOGIN_USER_ID`。
3. 去 Redis 读取 `USER_LOGIN_{userId}`。
4. 对比请求 token 和 Redis token 是否一致。
5. 校验通过后，把 `userId` 写入 `UserIdUtil` 的 ThreadLocal。

后续业务代码就是通过：

* `UserIdUtil.get()`

拿到当前登录用户 ID。

#### 3.3.3 获取当前用户信息

当前前端登录成功后会调用：

* `GET /api/v1/users/get-user-info`

后端会返回：

* `userId`
* `nickname`
* `rootFileId`
* `rootFilename`
* `profilePhotoUrl`

其中：

* `userId`
* `rootFileId`

都会经过 `IdEncryptSerializer` 加密后再返回给前端。

这也是当前文件页能够直接进入用户根目录的原因。

### 3.4 退出登录实现

#### 3.4.1 后端登出接口

当前后端提供了：

* `POST /api/v1/auth/logout`

但当前 `AuthServiceImpl.logout()` 的代码实现是：

1. 调用 `IdUtil.get()` 生成一个新的 Long 值。
2. 按这个新值去删除 Redis 中的 `USER_LOGIN_{userId}`。
3. 再调用 `StpUtil.logout(userId)`。

因此更准确的说法应该是：

* 当前后端“提供了登出接口”。
* 但它并不是按登录上下文中的当前用户 ID 做清理，不能写成“已经正确完成当前用户服务端登录态清理”。

#### 3.4.2 当前前端退出登录行为

虽然 `api/auth.js` 已经封装了 `/logout` 接口，但当前前端用户下拉菜单中的退出逻辑是：

* 直接执行 `userStore.logout()`
* 清空本地 Cookie 和 Pinia 状态
* 路由跳转到 `/login`

并没有真正发起：

* `POST /api/v1/auth/logout`

因此当前 UI 侧“退出登录”的真实效果是：

* 本地状态被清理
* 服务端 Redis 登录态不会在这一刻被删除

这点必须按代码现状描述，不能写成“前后端登录态都已经同步清理”。

### 3.5 当前实现边界

为了保证文档和代码一致，这里把当前登录注册链路的边界单独列出来：

#### 3.5.1 当前没有真正使用验证码

虽然有：

* `GET /api/v1/auth/send-captcha`
* `checkCode`
* `emailCode`

这些接口或字段，但当前前端注册、登录页面都没有把它们接入完整流程，控制器里也保留着 `TODO` 校验。

#### 3.5.2 当前 rememberMe 没有生效

`LoginParamVO` 和 `LoginContext` 里有 `rememberMe`，但当前服务层没有使用它调整 token 时长或 Cookie 策略。

#### 3.5.3 当前登录没有校验密码

当前登录代码只按邮箱查用户并发 token，这一点必须按事实记录。

#### 3.5.4 当前后端 logout 代码也没有按当前用户清理

`AuthServiceImpl.logout()` 当前使用的是 `IdUtil.get()`，而不是像其它业务接口那样通过登录上下文拿当前用户 ID。

因此即使页面未来接上 `/api/v1/auth/logout`，也不能直接把现状描述成“后端 logout 已按当前用户正确生效”。

#### 3.5.5 当前鉴权是混合方案

当前登录时虽然调用了 `StpUtil.login(...)`，但业务请求真正依赖的是：

* JWT
* Redis
* `UserInfoLoginAspect`
* `UserIdUtil`

因此不能把当前方案简单写成“纯 Sa-Token 方案”。

## 4. 数据模型

### 4.1 `user`

作用：保存用户主数据。

当前与登录注册关系最强的字段包括：

* `id`
* `nick_name`
* `email`
* `password_hash`
* `use_space`
* `total_space`
* `last_login_time`
* `profile_photo_url`
* `deleted`

### 4.2 `user_file`

作用：保存用户目录视图。

在登录注册链路里，最关键的不是普通文件，而是注册后会额外创建一条根目录记录，关键字段包括：

* `id`
* `user_id`
* `parent_id = 0`
* `real_file_id = NULL`
* `filename = 全部文件`
* `folder_flag = 1`

后续 `get-user-info` 返回给前端的 `rootFileId`，本质上就是这条根目录 `user_file` 记录的加密 ID。

### 4.3 Redis 登录态

当前项目没有单独的“登录会话表”，登录态主要落在 Redis 中，key 规则是：

* `USER_LOGIN_{userId}`

value 存的是当前签发给前端的 JWT。

因此，当前登录链路的持久化形态可以理解为：

* 用户基础信息在 `user`
* 根目录初始化在 `user_file`
* 登录态一致性校验在 Redis
