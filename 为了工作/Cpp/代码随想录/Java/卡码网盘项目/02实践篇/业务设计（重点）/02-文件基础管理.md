# 02-文件基础管理

## 1. 功能说明

1. 当前文件基础能力主要由后端 `networkdisk-business/networkdisk-files` 模块和前端 `disk-by-cursor/src/views/Files.vue` 共同完成。
2. 当前目录视图的核心数据表是 `user_file`，它表示“某个用户在自己网盘目录里看到的文件/文件夹记录”；真实物理文件元数据则在 `file` 表。
3. 当前文件夹本质上也是 `user_file` 记录，只是 `folder_flag = 1`、`real_file_id = NULL`。
4. 当前前端文件页已经接入：文件列表、目录切换、面包屑、新建文件夹、搜索、预览、下载、重命名、删除、批量删除、批量下载、分享入口和 AI 入口。
5. 当前所有返回给前端的文件/目录 ID 都不是明文 Long，而是通过 `IdEncryptSerializer` 序列化后的加密字符串；控制器收到后再做解密。

## 2. 功能需求

文件基础能力一般要解决的是“用户如何在自己的目录视图里管理文件”。这通常包含：

1. 列表查询和目录导航。
2. 新建文件夹。
3. 文件预览和下载。
4. 文件重命名和删除。
5. 文件搜索。
6. 目录树选择、转移和复制。
7. 同名冲突处理和权限校验。

## 3. 功能实现

### 3.1 文件列表与目录导航

#### 3.1.1 当前前端入口

当前文件页位于：

* `disk-by-cursor/src/views/Files.vue`

文件页的目录状态统一由：

* `disk-by-cursor/src/stores/file.js`

维护。核心状态包括：

* `parentId`
* `currentFolderId`
* `fileTypes`
* `files`
* `breadcrumbs`

当前页面打开后，会先通过用户信息里的 `rootFileId` 进入根目录，再根据当前侧边栏类型筛选加载文件列表。

#### 3.1.2 文件列表接口

当前文件列表接口为：

* `GET /api/v1/files/folders-files`

请求参数包括：

* `parentId`
* `fileTypes`

后端处理流程是：

1. 控制器把前端传来的加密 `parentId` 解密为 Long。
2. 如果 `fileTypes != -1`，则按逗号分割成文件类型列表。
3. 用当前登录用户 `userId`、`parentId`、`deleted = 0`、`fileTypes` 组装查询条件。
4. 从 `user_file` 表查询当前目录下的有效记录。
5. 返回 `UserFileVO` 列表给前端。

当前 `UserFileVO` 里最关键的字段包括：

* `id`
* `parentId`
* `filename`
* `fileSizeDesc`
* `folderFlag`
* `fileType`
* `updateTime`

其中 `id` 和 `parentId` 返回给前端时都是加密字符串。

#### 3.1.3 目录切换与点击行为

当前页面中：

* 点击文件夹名称，会调用 `openFolder(...)` 进入下一级目录。
* 点击普通文件时，如果文件类型支持内联预览，则直接预览；否则直接下载。
* 如果文件类型属于当前 AI 支持范围，则点击文件名会优先打开 `AiFileDrawer` 的 `insight` 模式，显示智能的摘要与标签。

因此当前“点击文件名”的行为会按文件夹、AI 文件、普通文件分别处理。

### 3.2 面包屑实现

当前面包屑接口为：

* `GET /api/v1/files/file/breadcrumbs`

请求参数：

* `fileId`

后端实现流程：

1. 先查询当前用户所有有效文件夹记录。
2. 把它们转成 `id -> BreadcrumbVO` 的映射。
3. 从当前文件夹开始，按 `parentId` 一层层向上回溯。
4. 最终在内存中拼出面包屑列表。

前端 `fileStore.loadFiles(...)` 在拿到文件列表后，会额外请求一次面包屑接口，并显示在页面顶部。

### 3.3 新建文件夹

#### 3.3.1 前端页面行为

当前文件页已经接入“新建文件夹”按钮。

前端弹窗会对输入做这些本地校验：

* 名称不能为空
* 长度不能超过 `255`
* 不能包含 `< > : " / \ | ? *`

需要注意的是：

* 这些非法字符校验目前主要发生在前端。
* 后端 `CreateFolderParamVO` 只校验了 `parentId`、`folderName` 非空，没有重复做同样的字符过滤。

#### 3.3.2 后端创建流程

当前创建文件夹接口为：

* `POST /api/v1/files/folder`

请求体包括：

* `parentId`
* `folderName`

后端 `UserFileServiceImpl.createFolder(...)` 会：

1. 组装一条新的 `UserFileDO`。
2. 设置 `folder_flag = 1`。
3. 设置 `real_file_id = NULL`。
4. 设置 `fileType = NULL`。
5. 调用 `handleDuplicateFilename(...)` 处理同目录重名。
6. 保存到 `user_file` 表。

当前创建文件夹不是“重名直接报错”，而是会自动改名。

### 3.4 同名冲突规则

当前项目里，同名冲突的真实规则需要单独说明，因为不同操作并不完全一致。

#### 3.4.1 自动改名的场景

当前这些场景会走：

* `handleDuplicateFilename(...)`

包括：

* 创建文件夹
* 上传完成后创建普通文件记录
* 秒传命中后创建普通文件记录
* 文件转移
* 文件复制

自动改名规则是：

* 保留原扩展名
* 文件名主体后追加全角括号编号，例如 `文档（1）.pdf`

#### 3.4.2 重命名场景

当前“重命名”接口不会自动加编号，而是会做显式校验：

* 新旧名称不能相同
* 同目录下不能已有同名记录

如果冲突，会直接返回业务错误，而不是自动改名。

### 3.5 文件重命名

当前重命名接口为：

* `PUT /api/v1/files/file`

请求体：

* `fileId`
* `newFilename`

后端 `checkUpdateFilenameCondition(...)` 的真实校验包括：

1. 文件记录必须存在。
2. 当前记录的 `userId` 必须等于当前登录用户。
3. 新旧名称不能相同。
4. 同目录下不能有同名记录。

校验通过后，服务端只更新：

* `user_file.filename`

也就是说，当前重命名修改的是用户目录视图里的文件名，不会去改 `file` 表里的物理文件名。

### 3.6 删除实现

#### 3.6.1 当前页面已接入单删和批量删

当前 `Files.vue` 已经接入：

* 单个文件删除
* 批量删除

调用的都是：

* `DELETE /api/v1/files/file`

请求体中的参数是：

* `fileIds: List<String>`

#### 3.6.2 后端删除逻辑

`UserFileServiceImpl.deleteFile(...)` 的真实流程是：

1. 按传入 ID 查询 `user_file` 记录。
2. 检查这些记录的 `user_id` 是否都属于同一个用户。
3. 检查该用户是否等于当前登录用户。
4. 执行逻辑删除，把 `deleted` 更新为已删除。

这里有两个容易写错的点：

* 当前删除的是 `user_file` 视图记录，不是直接删除 `file` 物理文件。
* 当前 `doDeleteFile(...)` 只对传入的记录本身做逻辑删除，没有在这个方法里递归处理文件夹的全部子孙节点。

### 3.7 预览与下载

#### 3.7.1 当前页面已接入

当前文件页已经接入：

* 文件预览
* 文件下载
* 批量下载（仅对普通文件生效）

对应接口分别为：

* `GET /api/v1/files/file/preview`
* `GET /api/v1/files/file/download`

#### 3.7.2 后端校验逻辑

无论预览还是下载，后端都会先：

1. 读取 `user_file` 记录。
2. 校验该记录必须存在。
3. 校验该记录必须属于当前登录用户。
4. 校验不能对文件夹执行下载/预览。

随后再通过 `real_file_id` 找到 `file` 表中的真实物理文件记录，并委托存储引擎把文件内容写回响应流。

当前下载与预览的差异主要是：

* 下载会设置 `Content-Disposition`，触发浏览器保存。
* 预览会优先使用 `file_preview_content_type` 作为响应类型。

### 3.8 文件夹树、转移与复制

#### 3.8.1 文件夹树

当前后端提供：

* `GET /api/v1/files/file/folder/tree`

返回的每个节点包括：

* `id`
* `parentId`
* `name`
* `children`

真实实现是：

1. 查询当前用户所有未删除文件夹记录。
2. 在内存中按 `parentId` 分组。
3. 把 `parentId = 0` 的文件夹作为顶层节点返回。

#### 3.8.2 文件转移

当前后端提供：

* `POST /api/v1/files/file/transfer`

请求体：

* `fileIds: List<String>`
* `targetParentId`

服务层会做这些事：

1. 检查目标节点必须是文件夹。
2. 检查目标目录不能是待转移文件夹本身或其子文件夹。
3. 把选中记录的 `parent_id` 改到目标目录。
4. 如有重名，自动改名。

#### 3.8.3 文件复制

当前后端提供：

* `POST /api/v1/files/file/copy`

请求体：

* `fileIds`：多个 ID 通过 `__,__` 拼接成一个字符串
* `targetParentId`

服务层真实行为是：

1. 检查目标节点必须是文件夹。
2. 检查目标目录不能是被复制文件夹本身或其子文件夹。
3. 递归复制 `user_file` 树。
4. 为每条新记录生成新的 `id`。
5. 保留原来的 `real_file_id`，也就是不会复制一份新的物理文件内容。
6. 如有重名，自动改名。

## 4. 数据模型

### 4.1 `user_file`

作用：保存用户目录视图，是当前文件基础能力里最核心的表。

核心字段包括：

* `id`
* `user_id`
* `parent_id`
* `real_file_id`
* `filename`
* `folder_flag`
* `file_size_desc`
* `file_type`
* `deleted`

可以把它理解为：

* 用户在界面上看到的每一个文件、文件夹，本质上都是一条 `user_file` 记录。

### 4.2 `file`

作用：保存真实物理文件元数据。

核心字段包括：

* `id`
* `filename`
* `real_path`
* `file_size`
* `file_size_desc`
* `file_suffix`
* `file_preview_content_type`
* `identifier`
* `create_user`

`user_file.real_file_id` 指向的就是这里的 `file.id`。

因此当前项目的数据关系更接近：

* `file` 代表真实物理文件
* `user_file` 代表用户目录里的文件视图
