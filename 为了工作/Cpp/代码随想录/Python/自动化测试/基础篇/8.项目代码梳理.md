# 启动 run.py
你执行 python run.py 或 uv run run.py，脚本读取 conf/setting.py 中的 REPORT_TYPE。假设它是 'allure'。脚本调用 pytest.main() 并传入参数，指定测试目录为 ./testcase，以及 Allure 报告相关的参数。pytest.main() 是 pytest 测试框架提供的一个函数，它的主要作用是允许你在 Python 脚本内部以编程方式启动和运行 pytest 测试，就像你在命令行中直接输入 pytest 命令一样。

在框架代码中，是这么写的：

```bash
pytest.main(
    ['-s', '-v', '--alluredir=./report/temp', './testcase', '--clean-alluredir',
     '--junitxml=./report/results.xml'])
```

这行代码的作用等同于在你的项目根目录下打开终端并执行以下命令：

```bash
pytest -s -v --alluredir=./report/temp ./testcase --clean-alluredir --junitxml=./report/results.xml
```



pytest.main()就是 pytest 的入口，我们下面可以简单看一下 pytest 的源码。

先看 main 函数的签名和返回值

**args** 这个参数指定了要传递给 pytest 的命令行参数。它可以是一个字符串列表 (list[str])，每个字符串代表一个命令行参数（例如 ['-s', '-v', './testcase']）。也可以是一个路径对象 (os.PathLike[str])，尽管这不太常见，通常参数是字符串列表。如果为 None（默认值），pytest.main 会尝试从 sys.argv 读取命令行参数，就像你直接在终端运行 pytest 命令一样。在 run.py 中，就是显式地传递了一个列表给 args，例如 ['-s', '-v', '--alluredir=./report/temp', './testcase', '--clean-alluredir', '--junitxml=./report/results.xml']

**plugins** 这个参数允许你在 pytest 初始化时，以编程方式自动注册一些插件。它可以是一个包含插件模块名称（字符串）或插件对象本身的序列（例如列表或元组）。如果为 None（默认值），则不自动注册额外的插件（但 pytest 仍会发现并加载通过入口点或其他方式安装的插件）。在你的 run.py 中没有使用这个参数，意味着它依赖 pytest 自动发现已安装的插件（如 pytest-allure-adaptor 或 pytest-tmreport）。

**返回值 **函数返回一个整数 (int) 或一个 ExitCode 枚举值。这个返回值代表了测试执行的退出状态码。通常：0 (或 ExitCode.OK) 表示所有测试通过。非零值表示测试执行过程中出现了问题，例如测试失败、用法错误、内部错误等（对应 ExitCode 枚举中的不同值，如 ExitCode.TESTS_FAILED, ExitCode.USAGE_ERROR, ExitCode.INTERNAL_ERROR 等）。

```python
def main(
    args: list[str] | os.PathLike[str] | None = None,
    plugins: Sequence[str | _PluggyPlugin] | None = None,
) -> int | ExitCode:
```



继续往下，准备配置是 pytest.main 做的第一件重要的事情，它调用内部函数 _prepareconfig （python 中下划线开头的约定为内部使用的函数，不对外暴露。但这只是一种约定，没有语法上的检查）来处理传入的 args 和 plugins。_prepareconfig 会解析命令行参数，查找并加载配置文件（如 pytest.ini, pyproject.toml），发现并导入 conftest.py 文件，最终创建一个 config 对象。这个 config 对象包含了整个测试会话的所有配置信息。源码中特别处理了 ConftestImportFailure 异常，说明加载 conftest.py 是配置阶段的关键一步，如果失败会直接报错并退出。Pytest 对名为 conftest.py 的文件有特殊处理。它会自动发现每个测试目录及其父目录下的 conftest.py 文件。这些文件不需要被直接导入，但它们里面的 Fixtures和钩子函数会被 Pytest 自动识别并应用到该目录及子目录下的测试中。

```python
@final
class PytestPluginManager(PluginManager):

    def _loadconftestmodules(
        self,
        path: pathlib.Path,
        importmode: str | ImportMode,
        rootpath: pathlib.Path,
        *,
        consider_namespace_packages: bool,
    ) -> None:
        if self._noconftest:
            return

        directory = self._get_directory(path)

        # Optimization: avoid repeated searches in the same directory.
        # Assumes always called with same importmode and rootpath.
        if directory in self._dirpath2confmods:
            return

        clist = []
        for parent in reversed((directory, *directory.parents)):
            if self._is_in_confcutdir(parent):
                conftestpath = parent / "conftest.py"
                if conftestpath.is_file():
                    mod = self._importconftest(
                        conftestpath,
                        importmode,
                        rootpath,
                        consider_namespace_packages=consider_namespace_packages,
                    )
                    clist.append(mod)
        self._dirpath2confmods[directory] = clist
```

再往下就是最核心的一步，执行核心命令行逻辑 config.hook.pytest_cmdline_main。它通过 pytest 的钩子（hook）系统调用 pytest_cmdline_main 这个钩子函数。这个钩子是 pytest 内部执行测试流程的起点。它会利用之前创建的 config 对象，触发后续的测试收集（找到所有测试项）、执行（运行测试函数、管理 fixture）和报告（生成结果）等所有阶段。所有你在 args 中指定的选项（如 -s, -v, --alluredir, ./testcase）都会在 config 对象中体现，并被 pytest_cmdline_main 及其调用的后续流程使用。

pytest_cmdline_main 钩子执行完毕后会返回一个结果（通常是整数形式的退出码）将这个结果包装成 ExitCode 枚举类型（或保持为整数）并返回。这个退出码表示了测试运行的最终状态，0 通常表示所有测试通过 (ExitCode.OK)。非 0 值表示有测试失败、执行错误或其他问题（如 ExitCode.TESTS_FAILED, ExitCode.INTERRUPTED, ExitCode.USAGE_ERROR 等）。



最后在 finally 块中确保调用 _ensure_unconfigure()，用于执行必要的清理工作，比如注销插件、关闭资源等。

```python
        else:
            try:
                ret: ExitCode | int = config.hook.pytest_cmdline_main(config=config)
                try:
                    return ExitCode(ret)
                except ValueError:
                    return ret
            finally:

    except UsageError as e:

        for msg in e.args:
            tw.line(f"ERROR: {msg}\n", red=True)
        return ExitCode.USAGE_ERROR
```

总之，pytest.main 就是整个 pytest 的入口，流程就是：

+ 解析你传入的参数 (args)。
+ 加载配置 (conftest.py, pytest.ini 等)。
+ 调用 pytest 内部的核心钩子 (pytest_cmdline_main) 来启动并执行完整的测试收集、运行和报告流程。
+ 返回一个退出码，表明测试结果。

# test_debug_api.py
## 测试用例参数化
以这个具体的 case 为例，其他的 case 都一样：

```python
@allure.story(next(c_id) + "新增用户")
@pytest.mark.run(order=1)
@pytest.mark.parametrize('base_info,testcase', get_testcase_yaml("./testcase/Single interface/addUser.yaml"))
def test_add_user(self, base_info, testcase):
    allure.dynamic.title(testcase['case_name'])
    RequestBase().specification_yaml(base_info, testcase)
```

这里有几个关键点：

1. **@pytest.mark.parametrize(argnames, argvalues) 装饰器**

这是 pytest 的核心功能之一，用于实现参数化测试。它告诉 pytest 要使用不同的参数多次运行同一个测试函数。argnames: 是一个字符串 'base_info,testcase'。这定义了测试函数 test_add_user 中将接收参数化数据的两个参数名：base_info 和 testcase。argvalues: 是一个可迭代对象（通常是列表或元组），它的值由get_testcase_yaml("./testcase/Single interface/addUser.yaml") 函数调用返回。

2. **get_testcase_yaml(yaml_path) 函数:**

这个函数（定义在 common/readyaml.py 中）负责读取并解析指定的 YAML 文件（在这里是 addUser.yaml）。

它读取 YAML 文件的内容，这个 YAML 文件通常包含两部分：baseInfo: 描述这个 API 的基本信息（如 URL、请求方法、通用请求头）。通常在一个 YAML 文件中只有一个 baseInfo。testCase: 一个列表，包含了针对这个 API 的多个具体测试场景。列表中的每个元素都是一个字典，描述了一个独立的测试用例（包括用例名称case_name、请求数据 data、验证规则 validation 等）。get_testcase_yaml 函数处理这个 YAML 结构，并返回一个列表。这个列表的 每个元素 都是一个 元组，格式为 (baseInfo_dict, testCase_item_dict)。其中：baseInfo_dict 是从 YAML 文件中解析出来的 baseInfo 部分（通常对于一个文件返回的所有元组，这部分是相同的）。testCase_item_dict 是从 YAML 文件 testCase 列表中的 某一个测试场景字典。



3. **参数化执行流程:**

pytest 在执行 test_add_user 之前，先调用 get_testcase_yaml("./testcase/Single interface/addUser.yaml")。

假设 addUser.yaml 的 testCase 列表里有 3 个测试场景。那么 get_testcase_yaml 会返回一个包含 3 个元组的列表，例如：

```python
[
    (common_base_info, test_case_1_details),
    (common_base_info, test_case_2_details),
    (common_base_info, test_case_3_details)
]
```

@pytest.mark.parametrize 接收到这个列表后，会 依次 遍历列表中的每个元组：

第一次执行: 它取出第一个元组 (common_base_info, test_case_1_details)。将 common_base_info 赋值给 test_add_user 的 base_info 参数，将 test_case_1_details 赋值给 testcase 参数。然后执行 test_add_user 函数体内的代码。

第二次执行: 它取出第二个元组 (common_base_info, test_case_2_details)。再次将 common_base_info 赋值给 base_info，将 test_case_2_details 赋值给 testcase。然后再次执行 test_add_user 函数体。

第三次执行: 以此类推。

因此，虽然 test_add_user 函数只定义了一次，但它会根据 addUser.yaml 文件中 testCase 列表的数量，被独立执行多次，每次执行都使用不同的 testcase 数据。

4. **函数体内:**

allure.dynamic.title(testcase['case_name']): 在每次参数化执行时，从当前传入的 testcase 字典中获取 case_name，并将其设置为 Allure 报告中这次具体执行的标题，方便区分不同的测试场景。RequestBase().specification_yaml(base_info, testcase): 将当前参数化执行对应的 base_info 和 testcase 传递给核心请求处理逻辑。

这种参数化方式实现了 数据与逻辑的分离。测试执行的逻辑（发送请求、处理响应、断言）封装在 RequestBase 和 test_add_user 函数中，而具体的测试数据（API 信息、请求内容、预期结果）则定义在 YAML 文件中。这使得添加或修改测试场景变得非常容易，只需要编辑 YAML 文件，而无需改动 Python 代码。@pytest.mark.parametrize 结合 get_testcase_yaml 优雅地将 YAML 中的每个测试场景映射为一次独立的 pytest 测试执行。

    - 动态值处理: 调用 self.replace_load(value) 方法递归地处理请求头、请求体、Cookie、验证规则等部分。
        * 此方法查找并解析 ${...} 格式的占位符，例如 ${get_extract_data(token)} 或 ${random_phone()}。通过 Python 的反射机制 (getattr)，动态调用 common/debugtalk.py 中 DebugTalk 类对应名称的方法 (get_extract_data, random_phone 等)，并将括号内的参数传入。DebugTalk 类的方法负责执行具体逻辑，比如从 extract.yaml 文件读取之前保存的数据 (依赖注入的 ReadYamlData 实例)，或者生成随机数据。用 DebugTalk 方法返回的实际值替换掉原始数据中的 ${...} 占位符，实现数据的动态生成和关联。

```python
# base/apiutil.py
from common.debugtalk import DebugTalk
import json
# ...

    def replace_load(self, data):
        """yaml数据替换解析"""
        str_data = data
        if not isinstance(data, str):
            str_data = json.dumps(data, ensure_ascii=False)

        for i in range(str_data.count('${')): # 查找 ${...}
            if '${' in str_data and '}' in str_data:
                start_index = str_data.index('$')
                end_index = str_data.index('}', start_index)
                ref_all_params = str_data[start_index:end_index + 1]
                # 解析函数名和参数
                func_name = ref_all_params[2:ref_all_params.index("(")]
                func_params = ref_all_params[ref_all_params.index("(") + 1:ref_all_params.index(")")]
                # 使用 getattr 动态调用 DebugTalk 类的方法
                extract_data = getattr(DebugTalk(), func_name)(*func_params.split(',') if func_params else "")
                # 替换原始字符串
                str_data = str_data.replace(ref_all_params, str(extract_data))

        # 还原数据类型
        if data and isinstance(data, dict):
            data = json.loads(str_data)
        else:
            data = str_data
        return data
```

+ 数据提取:
    - 检查 testcase 中是否定义了 extract (提取单个值) 或 extract_list (提取列表值)。
    - 如果定义了，调用 self.extract_data 或 self.extract_data_list 方法。
    - 这些方法使用 JSONPath 表达式 (如 $.data.token) 或正则表达式从 响应体 (res.text) 中提取需要的数据。
    - 调用 self.read.write_yaml_data(...) (即 ReadYamlData 实例的方法) 将提取到的键值对（例如 {'token': 'extracted_token_value'}）写入项目根目录下的 extract.yaml 文件中。这样，后续的测试用例就可以通过 ${get_extract_data(token)} 来引用这个提取到的值。

+ 执行断言:
    - 调用 self.asserts.assert_result(...) (即 Assertions 实例的方法)。
    - 将 YAML 中定义的 validation 规则列表 (经过 replace_load 处理可能包含动态值) 、实际响应体 (通常是 JSON 字典) 和响应状态码传入。
    - assert_result 方法遍历 validation 规则，执行各种比较，例如：检查状态码是否等于 200 ({'eq': ['status_code', 200]})、检查响应体中是否包含特定字符串 ({'contains': {'msg': '成功'}})、检查某个字段的值是否等于预期值等。如果任何一条断言失败，该方法会抛出 AssertionError 异常。Pytest 会捕获这个异常，并将当前这个参数化测试实例标记为 失败。如果没有异常抛出，则测试实例标记为 成功。

```python
# base/apiutil.py within specification_yaml method, inside try block after extraction
self.asserts.assert_result(validation, res_json, status_code) # 调用断言方法

# common/assertions.py (简化示例)
from common.recordlog import logs
import jsonpath
# ...

class Assertions:
    def assert_result(self, validation, res_json, status_code):
        # logs.info(\"预期结果：%s\" % validation)
        # logs.info(\"实际结果：%s\" % res_json)
        # logs.info(\"状态码：%s\" % status_code)
        flag = True  # 断言结果标识

        if validation:
            for assert_dict in validation: # 遍历 validation 列表中的每个断言规则字典
                for assert_type, assert_value in assert_dict.items(): # ('eq', ['status_code', 200]) or ('contains', {'msg': '成功'})
                    if assert_type == 'eq': # 等于断言
                        if assert_value[0] == 'status_code': # 针对状态码
                            assert status_code == assert_value[1], f\"状态码断言失败！预期：{assert_value[1]}，实际：{status_code}\"
                            logs.info(f\"状态码断言成功！预期：{assert_value[1]}，实际：{status_code}\")
                        else: # 针对响应体字段
                            actual_value = jsonpath.jsonpath(res_json, f\"$..{assert_value[0]}\")
                            if actual_value:
                                assert actual_value[0] == assert_value[1], f\"{assert_value[0]}断言失败！预期：{assert_value[1]}，实际：{actual_value[0]}\"
                                logs.info(f\"{assert_value[0]}断言成功！预期：{assert_value[1]}，实际：{actual_value[0]}\")
                            else:
                                flag = False
                                logs.error(f\"断言失败！未在响应体中找到字段：{assert_value[0]}\")
                    elif assert_type == 'contains': # 包含断言
                        if isinstance(assert_value, dict): # 检查响应体中特定字段是否包含某值
                            for key, value in assert_value.items():
                                 actual_value = jsonpath.jsonpath(res_json, f\"$..{key}\")
                                 if actual_value:
                                     assert str(value) in str(actual_value[0]), f\"{key}字段包含断言失败！预期包含：{value}，实际值：{actual_value[0]}\"
                                     logs.info(f\"{key}字段包含断言成功！预期包含：{value}，实际值：{actual_value[0]}\")
                                 else:
                                      flag = False
                                      logs.error(f\"包含断言失败！未在响应体中找到字段：{key}\")
                        else: # 直接检查响应体文本是否包含某字符串
                            assert str(assert_value) in str(res_json), f\"响应体包含断言失败！预期包含：{assert_value}，实际响应：{str(res_json)[:500]}...\" # 截断过长响应
                            logs.info(f\"响应体包含断言成功！预期包含：{assert_value}\")
                    # ... (可以扩展其他断言类型，如 ne, gt, lt, etc.) ...
        # return flag # 可以选择返回断言结果
```
