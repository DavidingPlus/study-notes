# 项目简介：从零搭一个本地 AI Agent 系统

这套教程要带你做的，不是一个"调用一次大模型 API 的命令行脚本"。

我们要从空仓库开始，一步一步搭出一个本地运行的 AI Agent 系统：它有常驻的 Core daemon，有 CLI 和 TUI 两种前端，有类型化的 IPC 协议，有可回放的事件流，有工具调用、任务规划、会话记忆、权限审批、上下文压缩、子 Agent 和 MCP 外部工具接入。

最终它会长成这样：

```latex
用户
  │
  ├─ kama CLI        一次性命令、chat 会话、trace 查看
  │
  └─ kama-tui        终端 UI、实时事件流、权限审批、上下文水位
        │
        ▼
  kama-core daemon   AgentRunner / AgentLoop / EventBus / SessionManager
        │
        ├─ LLM Provider
        ├─ ToolRegistry
        ├─ Session Store
        ├─ Permission Manager
        ├─ Subagents
        └─ MCP Servers
```

这不是一个追求"功能堆满"的项目。它的重点是把现代 agent 工具背后的工程结构拆开：为什么要有 daemon，为什么事件要类型化，为什么工具调用不能直接执行，为什么会话历史要完整回放，为什么还需要 notes，为什么上下文压缩不能直接覆盖原始历史，为什么子 Agent 要隔离上下文。

每一章都会围绕一个真实执行路径展开。我们不先堆概念，而是从用户敲下某条命令开始，顺着代码一路追到最终结果。读者看到的是系统怎么长出来，而不是一份模块清单。

## 这个项目解决什么问题

很多 agent demo 都从这里开始：

```python
response = client.messages.create(...)
print(response.text)
```

这能证明模型会回答问题，但离一个可用的 agent 工具还很远。

一个真正能长期使用的本地 agent，至少要回答这些问题：

* 用户发来的命令在哪里执行？CLI 进程里，还是一个常驻 daemon 里？
* agent 做了什么，能不能事后回放？
* 工具调用失败了，是让程序崩掉，还是把错误作为结果交还给 LLM？
* 危险工具调用谁来审批？
* 多轮对话之间怎么记住上下文？
* 上下文越来越长怎么办？
* 复杂任务能不能拆给不同角色的子 agent？
* 外部工具生态怎么接进来，而不是每个工具都写死在项目里？

KamaClaude 就是围绕这些问题组织的。

它从一个最小的双进程 ping/pong 开始，逐步把这些能力加上去。每个阶段都能运行、能验证、能留下文件证据，而不是等到最后才得到一个庞大的黑盒。

## 为什么第一步就是双进程

很多项目会先写一个单进程脚本，等功能多了再拆成 daemon + client。KamaClaude 反过来：S0 就先让 `kama` CLI 和 `kama-core` daemon 通过 TCP NDJSON 说上话。

这个选择会让 S0 看起来比普通脚手架重一点，但它换来几个长期收益：

* 所有跨进程数据从第一天开始就必须可序列化。
* 所有命令从第一天开始就有请求、响应和错误格式。
* 后续 TUI、事件订阅、权限审批都能复用同一条 IPC 通道。
* Core daemon 从一开始就是唯一执行体，CLI 和 TUI 只是客户端。

这条边界一旦立住，后面阶段的新增能力就不是推倒重来，而是在同一条执行链上逐步加订阅者、工具、状态和策略。

## 阶段怎么安排

这套教程按阶段推进，每一阶段只引入一个核心变量。

| 阶段 | 主题 | 这一阶段真正解决的问题 |
| --- | --- | --- |
| S0 | 骨架与协议契约 | CLI 和 daemon 通过真实 IPC 完成一次 ping/pong |
| S1 | Agent 最小闭环 | 一次 `kama run` 从 goal 到 LLM、工具、事件文件完整跑通 |
| S2 | 事件流外化 | AgentRunner 搬进 daemon，CLI/TUI 通过 IPC 订阅同一份事件流 |
| S3 | 自主规划与 TUI | agent 能用任务工具拆解复杂目标，TUI 展示完整执行过程 |
| S4 | 会话与记忆 | 多个 run 进入同一个 session，thread 和 notes 让下一轮接住上一轮 |
| S5 | 工具安全 | 工具调用前有参数校验、权限审批、失败分类和重试 |
| S6 | 上下文治理 | 长会话下有 context 水位、tool\_result 截断和 compact |
| S7 | 扩展边界 | Skills、Subagents、MCP 让 agent 可组织、可派生、可接外部工具 |

每一章都不是"今天写哪些文件"。它会先给出这一阶段之前系统哪里不够用，再顺着一个用户动作展开实现路径。

例如 S1 的主线是：

```latex
kama run --goal ...
  → cmd_run
  → AgentRunner
  → EventBus
  → AgentLoop
  → AnthropicProvider / ToolRegistry
  → EventWriter / StdoutPrinter
```

S4 的主线变成：

```latex
kama chat
  → session.create
  → session.send_message
  → SessionManager
  → AgentRunner 读取 thread + notes
  → run 结束写回 session
  → 第二轮复用上下文
```

读完每一章，你应该能讲清楚这一阶段为什么存在、改了哪条执行路径。

## 代码之外，重点看什么

这个项目的价值不只在代码能跑，还在它把 agent 工程里容易被忽略的边界都显式化了。

**协议边界**

CLI、TUI 和 Core 之间不是函数调用，而是 JSON-RPC + NDJSON。每个命令、响应、事件都有类型模型。这样事件订阅、回放、权限审批、compact 通知都能走同一套通道。

**事件边界**

AgentLoop 不直接打印，也不直接写日志。它只发布事件。谁关心终端输出，谁订阅；谁关心 events.jsonl，谁订阅；谁关心 TUI 展示，谁订阅。这让核心循环保持干净。

**工具边界**

工具调用不是"LLM 说什么就执行什么"。参数要校验，权限要判断，错误要分类，结果要回到对话历史。agent 能从失败中恢复，是因为失败也被建模成一种 tool result。

**记忆边界**

thread 记录完整消息流，notes 记录 agent 主动保存的事实，context.md 记录用户和项目级背景。它们都叫"上下文"，但职责不同。混在一起会让后续 compact 和恢复变得不可控。

**扩展边界**

Skills 不是硬编码命令，Subagents 不是另一个调度系统，MCP 工具也不是特殊分支。它们最终都回到同一套 `AgentRunner / ToolRegistry / EventBus` 链路里。

## 学完之后你应该得到什么

完成这套教程后，你会有一个可以演示的本地 agent 项目：

* 可以启动 `kama-core`，用 `kama run` 或 `kama chat` 触发任务。
* 可以打开 TUI 看实时 token、工具调用、权限审批和上下文水位。
* 可以在 `~/.kama/sessions/` 里看到 session 的 thread、notes、runs 和 events。
* 可以解释一次工具调用从 LLM 请求到权限审批再到 tool result 的完整路径。
* 可以说明为什么完整回放比滑动窗口稳，为什么 compact 分自动和手动两种语义。
* 可以用 `/review`、`/orchestrate` 这类 skill 组织更复杂的 agent 工作流。
* 可以通过 MCP 把外部工具接入同一套工具注册和事件系统。

更重要的是，你会拿到一条可复用的工程思路：不要把 agent 当成一个 prompt；把它当成一个有协议、有状态、有事件、有权限、有上下文治理的本地系统。
