# 面试题

> 按主题分组，每题附参考答案要点。面试官通常从"介绍一下项目"开始，然后深挖某个模块。建议优先熟悉「项目整体」和「异步与并发」两节，其余按岗位方向选读。

***

## 一、项目整体

**Q：用一两句话描述这个项目解决了什么问题？**

本地 AI Agent 运行时：用户通过终端 TUI 向持久守护进程发送目标，守护进程驱动 LLM + 工具循环完成任务，并将所有过程事件实时推送给前端渲染。解决的核心问题是：让 Claude 不只是聊天，而是能执行文件读写、代码运行、子任务编排等真实操作。

***

**Q：为什么选择守护进程 + 客户端双进程架构，而不是单进程？**

要点：

* TUI 崩溃或用户关闭终端不中断 Agent 执行
* 未来可以同时连接多个客户端（CLI + TUI + Web）而无需修改核心逻辑
* 守护进程可以跨 session 维护状态（任务队列、权限策略），不依赖某个前端的生命周期
* 代价是增加了 IPC 复杂度，通过 JSON-RPC 2.0 协议和类型化消息模型来控制这个复杂度

***

## 二、异步与并发

**Q：守护进程是单线程还是多线程？如何处理并发？**

单线程，基于 `asyncio` 事件循环。并发模型：

* 每个 TCP 连接对应一个 `asyncio` 协程，通过 `asyncio.start_server` 管理
* 命令处理、事件发布、Agent 循环全部是协程，通过 `await` 让出控制权
* 没有 `threading`，避免了锁竞争；CPU 密集型任务（目前没有）如果存在，会用 `run_in_executor`
* `asyncio.Task` 用于并发运行多个 session 的 Agent，`asyncio.Future` 用于子 Agent 结果等待

***

**Q：LLM 流式输出是如何从守护进程传到 TUI 的？中间经过几层？**

路径：

```plain
Anthropic SDK (stream) → AnthropicProvider.chat()
  → EventBus.publish(LlmTokenEvent)
    → SocketServer 遍历订阅了 "llm.token" 的客户端连接
      → 序列化为 JSON-RPC Notification
        → asyncio.StreamWriter.write() 写入 TCP
          → TUI SocketClient 接收 → on_event 回调
            → KamaTuiApp._handle_event_inner()
              → LLMStreamBlock.append_token()
```

共 5–6 层，全异步，不阻塞。TUI 收到 token 后直接更新 widget 文本，Textual 框架在下一帧刷新屏幕。

***

**Q：流式重试是怎么实现的？重试时如何避免消息重复？**

要点：

* 捕获 `httpx.RemoteProtocolError` / `httpx.ReadTimeout` 等网络异常
* 重试前丢弃本次 partial stream 收到的所有 token（不写入 message history）
* message history 在重试间保持不变（上一步完成的工具结果仍在），所以 LLM 看到的上下文是一致的
* 重试用指数退避（1s/2s/4s），最多 3 次；第 4 次失败则向上抛出，由 AgentLoop 报告 run.finished(status=failed)
* 关键：`LlmTokenEvent` 只在成功完成一个完整 response 后才有对应的 `llm.usage` 事件，TUI 侧不需要额外去重

***

**Q：EventBus 的 publish 和 subscribe 是如何实现的？**

要点：

* 订阅者注册时传入 topic pattern（支持 glob，如 `tool.*`）和异步回调
* `publish(event)` 时遍历所有订阅者，匹配 topic 后 `asyncio.ensure_future` 或直接 `await` 回调
* 本项目中事件总线是内存内的（守护进程内部），序列化到 TCP 是 SocketServer 的职责（它订阅全局 bus，再推送给 TCP 客户端）
* 子 Agent 使用独立 EventBus，通过 bridge 函数（subscribe 回调）将事件重发到父 Bus，实现事件透传

## 三、LLM 与 Agent 设计

**Q：AgentLoop 的终止条件是什么？如何防止死循环？**

要点：

* 正常终止：LLM response 中没有 `tool_use` 块，说明 LLM 认为任务已完成
* 强制终止：达到最大步数上限（可配置，默认 30 步），发布 `run.finished(status=failed, reason="max_steps")`
* 工具执行失败：`is_error=true` 的 ToolResult 返回给 LLM，LLM 自行决定是否继续；连续失败超限时终止
* 不存在真正的死循环风险，因为每步都需要 LLM 明确请求工具调用

***

**Q：Prompt Caching 是怎么用的？有什么注意事项？**

要点：

* 在系统 prompt 和工具 schema 的末尾加 `cache_control: {"type": "ephemeral"}`，Anthropic 会缓存这部分内容
* 多步对话中，系统 prompt 和工具 schema 每步都重发，但命中缓存后 input token 计费大幅降低（约 90% 折扣）
* 注意：缓存有 5 分钟 TTL，长时间暂停后缓存失效；工具列表变化（如 MCP 工具增减）会使缓存失效
* `llm.usage` 事件中的 `cache_read_input_tokens` 字段反映缓存命中情况，TUI 实时显示

***

**Q：上下文压缩是如何触发和执行的？压缩后如何保证 Agent 不丢失关键信息？**

要点：

* 触发：每步执行后检查 `context_pct = used_tokens / context_window`，超过阈值（默认 80%）则触发
* 执行：将完整 message history 发给 Claude，要求生成结构化摘要（任务目标、已完成步骤、关键发现、待续工作）
* 替换：用摘要消息替换历史，保留最新 1–2 轮消息（避免摘要刚生成就丢失最新上下文）
* 风险：LLM 摘要可能丢失某些细节，这是有损压缩的固有局限；项目通过保留最新轮次来降低影响

***

**Q：多 Agent 编排中，父 Agent 是如何等待子 Agent 结果的？**

要点：

* `SpawnAgentTool.execute()` 创建 `asyncio.Future`，启动子 AgentLoop（`asyncio.create_task`），然后 `await future`
* 子 AgentLoop 完成后，`SpawnAgentTool` 的完成回调 resolve 这个 future，父 Agent 的 `await` 返回
* 整个过程在同一个 event loop 内，不需要线程或进程间通信
* Background 模式：不 await future，直接返回 run\_id，父 Agent 可通过 `check_background_task` 工具轮询

***

## 四、工具系统与权限

**Q：ToolRegistry 是如何实现的？新增一个工具需要做什么？**

要点：

* ToolRegistry 维护 `dict[str, ToolHandler]`，每个 handler 包含：async 执行函数 + JSON schema + 权限等级
* 注册时传入函数引用和 schema，registry 在调用时根据 tool\_name 路由
* 新增工具：实现一个 async 函数，定义其 JSON schema，调用 `registry.register(name, fn, schema)`
* MCP 工具在客户端发现后动态注册，名称加 `{server}__` 前缀，卸载时批量移除

***

**Q：权限系统的 always\_allow / always\_deny 是如何持久化的？**

要点：

* 策略存储在 `~/.kama/permissions.json`（TOML/JSON，格式可配置）
* `PermissionManager` 启动时加载，运行期决策写入内存并异步刷盘
* 持久化格式：`{"tool_name": "always_allow", ...}`，不存储 session 级临时决策（allow\_once/deny\_once）
* 潜在问题：多进程同时写同一文件时可能竞争；当前实现假设单守护进程，未加文件锁

***

## 五、TUI 与前端

**Q：TUI 是如何做到「不阻塞」的？Agent 运行期间用户还能操作 UI 吗？**

要点：

* `KamaTuiApp` 通过 `run_worker()` 在 Textual 的 worker 线程中执行 IPC 发送，不阻塞 Textual 的主事件循环
* Agent 运行期间输入框被 `disabled = True`，但权限审批控件仍可响应键盘（焦点主动转移）
* socket 事件接收是独立的 worker（`_socket_loop`），收到事件后通过 Textual 的线程安全 API 更新 UI
* TUI 和守护进程通过 TCP 解耦，TUI 侧的 UI 卡顿不影响 Agent 执行

***

**Q：Slash 补全弹窗是如何实现的？为什么不用 Textual 内置的补全？**

要点：

* 自实现 `SlashCompleteWidget(Static)`，`can_focus=False`（不抢输入框焦点）
* 监听 `ChatTextArea.SlashChanged` 消息：文本以 `/` 开头且无空格时触发，`query=None` 时收起
* `ChatTextArea._on_key` 拦截 ↑↓/Tab/Escape，路由到弹窗的 `move_up/move_down/select_current`
* 不用内置补全的原因：需要自定义渲染格式（显示 description）、自定义触发条件（`/` 前缀）、与 Skill 系统集成

## 六、工程实践

**Q：项目是如何保证类型安全的？**

要点：

* mypy strict 模式：`disallow_untyped_defs`、`no_implicit_optional`、`warn_return_any` 等全部开启
* Pydantic v2 模型用于所有 IPC 消息，字段类型在运行时和编译期双重保证
* discriminated union 确保事件分发时不需要 `isinstance` 判断，类型收窄由 mypy 自动处理
* 唯一例外：Anthropic SDK 的 streaming response 类型较复杂，用 `Any` 注解并在边界处做运行时检查

***

**Q：集成测试是怎么做的？如何在不依赖真实 API 的情况下测试？**

要点：

* 集成测试通过 pytest fixture 启动真实守护进程子进程（`subprocess.Popen`），用随机端口避免冲突
* 单元测试通过依赖注入：`AnthropicProvider` 接受外部传入的 `client` 参数，测试时注入 mock client
* mock client 实现 `messages.stream()` 的 async context manager 协议，返回预设的 token 序列
* Agent 循环测试用 `FakeLLM`（可脚本化的 stub），验证工具调用序列、步数限制、错误处理等逻辑

***

**Q：如果让你重新设计这个项目，你会改变哪些设计决策？**

这道题没有标准答案，面试官想看你的反思能力。可以提的真实局限：

* **PermissionManager 文件锁**：当前无锁写磁盘，多实例场景可能竞争；可以改用 SQLite（自带并发安全）
* **EventBus 背压**：高频事件时订阅者处理速度跟不上发布速度，当前无 backpressure 机制；可以加 `asyncio.Queue` 缓冲
* **子 Agent 资源隔离**：子 Agent 共享父进程资源（内存、文件系统），无沙箱；生产场景应考虑进程隔离或容器
* **Skills 的 tool\_whitelist 是字符串列表**：没有 schema 校验，运行时才发现工具名拼错；可以在 loader 时做验证
* **TUI 与协议耦合**：TUI 直接解析 `event.get("type")` 字符串，而不是用 Pydantic 反序列化；可以复用 events.py 类型
