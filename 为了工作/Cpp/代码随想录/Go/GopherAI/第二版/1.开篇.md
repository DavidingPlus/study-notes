# 第一版与第二版差异说明

**注意: 不要上来就阅读第二版的文章,因为第一版讲过的,第二版不会重点讲解**

***

在第二版中，我们进一步增强了平台的功能和易用性，新增了以下关键模块：

**RAG（检索增强生成）服务**

* 允许用户通过网站直接上传RAG文件，构建个性化知识库。
* 提供高效的知识检索和生成能力，增强AI应用的智能化水平。
* 实现了文件上传、向量化存储、检索和问答功能，支持用户通过上传文件构建个性化知识库。

**文件上传服务**

* 每个用户都可以上传属于自己的文件，这些文件主要用于为 RAG 提供数据基础，从而实现用户级别的隔离式 RAG 机制，确保不同用户之间的知识库相互独立、互不影响。

**MCP（****模型上下文协议****）服务：**

* 当前实现了天气查询服务，支持通过MCP协议获取指定城市的天气信息。
* 提供了便捷的客户端和服务器实现，支持扩展其他多模态工具。

**语音识别服务**

* 集成语音合成功能，支持tts服务。
* 进一步丰富用户与AI应用的交互方式。

# Go 版本与 C++ 版本能力实现差异说明

尽管 Go 版本与原有 C++ 版本在功能层面均已覆盖 **RAG 与 MCP 等核心能力**，但在具体实现路径、架构设计及平台自主性方面，两者存在显著差异。

## 1. RAG 能力实现差异

在 **C++ 版本** 中，RAG 能力主要依赖 **第三方云服务的托管方案**：

* 通过阿里云平台预先构建并维护知识库
* 在推理阶段，使用 `curl` 等方式调用阿里云指定模型接口
* 由云侧完成 **向量化、检索与基于知识库的生成（RAG）逻辑**
* 本地服务主要承担请求转发与结果消费的角色

该方案能够较快实现功能，但对 **外部平台依赖较强**，在定制化、可控性和扩展性方面存在一定限制。

在 **Go 版本** 中，RAG 能力采用 **完全自研与本地化实现方案**：

* 使用 **Redis 作为向量数据库**，统一管理文档向量与元数据
* 在平台内部完成：
  * 文件解析与内容切分
  * 向量化处理
  * 向量入库与索引维护
* 在推理阶段，通过 **Top-K 相似度检索**，从向量库中筛选与当前问题最相关的文档片段
* 最终将检索结果作为上下文输入至大模型，完成生成任务

该实现方式使 RAG 能力 **完全掌控在平台自身**，避免对外部云厂商 RAG 服务的强依赖，显著提升了 **系统可控性、可定制性与长期演进能力**。

## 2. MCP 能力实现差异

在 **C++ 版本** 中，由于整体生态相对受限：

* 缺乏成熟、通用的 MCP（模型能力编排 / 多能力协作）框架
* MCP 相关能力多以 **业务代码内嵌或定制化逻辑** 的方式实现
* 随着模型和能力增多，维护成本与复杂度逐步上升

在 **Go 版本** 中，得益于更完善的语言生态与工程化支持：

* 采用 **独立 MCP Server 架构**
  * MCP 服务作为独立进程运行
  * 通过标准化协议与主服务进行通信
* MCP Server 专注于：
  * 模型能力管理
  * 多能力编排与调度
  * 请求上下文与状态管理
* 主服务仅负责业务入口与结果整合，职责边界清晰

该架构与 **主流 Java 企业级项目的 MCP 实践模式保持一致**，在 **可扩展性、可维护性和服务解耦** 方面具有明显优势，也为后续多模型、多工作流场景提供了良好的架构基础。
