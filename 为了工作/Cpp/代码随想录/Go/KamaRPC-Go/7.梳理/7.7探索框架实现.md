# InvokeAsync函数(客户端调用)

可以看到, 用到的函数,都是前几章节所涉及的.

这里就不重新讲解这些组件了, 讲解一些新的知识点

```go
func (c *Client) InvokeAsync(ctx context.Context, service string, method string, args interface{}) (*transport.Future, error) {

	if !c.limiter.Allow() {
		return nil, errors.New("rate limit exceeded")
	}

	addr, err := c.getAddr(service)
	if err != nil {
		return nil, err
	}
	br := c.getBreaker(service, addr)

	if !br.Allow() {
		return nil, errors.New("circuit breaker open")
	}

	pool := c.getPool(addr)

	ctx, cancel := context.WithTimeout(ctx, c.timeout)
	defer cancel()

	conn, err := pool.Acquire(ctx)
	if err != nil {
		return nil, err
	}

	body, err := c.codec.Marshal(args)
	if err != nil {
		return nil, err
	}

	req := &protocol.Message{
		Header: &protocol.Header{
			ServiceName: service,
			MethodName:  method,
			Compression: codec.CompressionGzip,
		},
		Body: body,
	}
	future, err := conn.SendAsync(req)
	if err != nil {
		br.RecordFailure()
		return nil, err
	}

	future.OnComplete(func(err error) {
		if err != nil {
			br.RecordFailure()
		} else {
			br.RecordSuccess()
		}
	})

	return future, nil
}
```

# 什么是Future?

在连接与连接池中,我们并没有对Future进行详细的解析,而我认为这个更适合在讲InvokeAsync函数的时候再讲

所以放到本章来讲

当发出一个 RPC 请求的时候

服务端需要执行函数、计算结果、再返回, 这是需要时间的. 所以客户端不能立刻拿到结果. 于是SendAsync() 先给一个 Future . 等服务器响应回来时,Future 再被填充结果

我们可以阻塞等/带超时等/注册回调/检查是否完成 . **客户端层面可以自己控制它的行为,这就叫做future, 这与其他RPC框架部分不同,他们设计的是callback. 你可以自己注册一个回调函数,当到了一定的时机,框架层面会自己帮你调用这个函数**

**当然两者可以混合思想进行使用**

两者设计思路不一样. 下面是他们的区别(我们用代码来解释):

**Future 风格**

```go
future := client.SendAsync(req)

result, err := future.Wait()
if err != nil {
    return err
}
process(result)
```

逻辑是线性的。

**Callback 风格**

```go
client.SendAsync(req, func(result []byte, err error) {
    if err != nil {
        return
    }
    process(result)
})
```

逻辑被拆开。

## Future代码解析:

那么Future是怎么封装的呢?

### Future结构体定义:

```go
type Future struct {
    //整个 Future 的核心,表示这个异步任务是否完成
	done  chan struct{} 
    //保存服务器返回的原始字节结果
	res   []byte
    //用于表示这个 RPC 是否出错
	err   error
	mu    sync.Mutex
	codec codec.Codec
    //回调函数,
	onComplete func(error)
}

```

### Future中的NewFuture函数:

```go
func NewFuture() *Future {
    //默认编码器为json,其中codec封装很简单
    //这边就不讲解了,不过要注意一点:目前代码中只能用json
    //编解码格式,proto版本需要是proto工具生成的idl代码才能编解码
	c, _ := codec.New(codec.JSON)
	return &Future{
        //创建一个未关闭的 channel,表示任务还没有完成
		done:  make(chan struct{}),
		codec: c,
	}
}

```

### Future中的Done函数:

这个函数,**会被连接与连接池章节中所涉及的readLoop调用.**

**表示RPC 响应回来了,会将结果放入到Future类中,并执行相应的回调函数**

```go
func (f *Future) Done(res []byte, err error) {
	f.mu.Lock()
	f.res = res
	f.err = err
	f.mu.Unlock()

	if f.onComplete != nil {
		f.onComplete(err)
	}
    //关闭 done channel(重点)
    //一旦关闭：
	close(f.done)
}
```

### Future中的Wait函数:

如果没完成 → 阻塞 如果已完成 → 立即返回

这就是最基础的“同步等待”。

```go
func (f *Future) Wait() ([]byte, error) {
	<-f.done
	f.mu.Lock()
	defer f.mu.Unlock()
	return f.res, f.err
}
```

```go
func (f *Future) GetResult(reply interface{}) error {
	//等待完成
    <-f.done
	f.mu.Lock()
	defer f.mu.Unlock()
    //检查错误
	if f.err != nil {
		return f.err
	}
    //反序列化
	return f.codec.Unmarshal(f.res, reply)
}
```

# 设计模式之选项模式与建造者模式

大家在看代码的时候,肯定有看到这么一种写法:

调用方是这么写的:

```go
	c, err := client.NewClient(
		reg,
		client.WithClientCodec(codec.JSON),
	)
```

内部实现是这样的

```go
func NewClient(reg *registry.Registry, opts ...ClientOption) (*Client, error) {
	c := &Client{
		reg:     reg,
		lb:      &loadbalance.RoundRobin{},
		limiter: limiter.NewTokenBucket(10000),
		timeout: 5 * time.Second,
	}
	for _, opt := range opts {
		if err := opt(c); err != nil {
			return nil, err
		}
	}
	return c, nil
}
```

```go
type ClientOption func(*Client) error

func WithClientCodec(t codec.Type) ClientOption {
	return func(c *Client) error {
		cc, err := codec.New(t)
		if err != nil {
			return err
		}
		c.codec = cc
		return nil
	}
}

func WithClientTimeout(d time.Duration) ClientOption {
	return func(c *Client) error {
		c.timeout = d
		return nil
	}
}

func WithClientLoadBalancer(lb loadbalance.LoadBalancer) ClientOption {
	return func(c *Client) error {
		c.lb = lb
		return nil
	}
}

```

## 为什么要这么写?

为什么不直接在 NewClient里面传一堆参数？这些WithXXX是干嘛的？为什么要这么绕？

我们先假设我们不用选项模式，而是直接这样设计

```go
func NewClient(
    reg *registry.Registry,
    codec codec.Type,
    timeout time.Duration,
    lb loadbalance.LoadBalancer,
) (*Client, error)

```

调用方会变成

```go
c, err := NewClient(reg, codec.JSON, 5*time.Second, &RoundRobin{})
```

那么这样会出现一些问题:

1. 参数会越来越多,那么构造函数的参数会越来越多
2. 可读性极差:NewClient(reg, codec.JSON, 5\*time.Second, nil, nil, true, 3) 这个true并不方便地知道是什么含义
3. 如果用户只想改 一个参数,其他都用默认值,那么不方便处理.因为其他参数也依旧需要传递值

**而go中的选项设计模式就是解决这个问题的**

一般来说,在代码中会先初始化一个结构体,用默认参数去设置

例如先

```go
	c := &Client{
		reg:     reg,
		lb:      &loadbalance.RoundRobin{},
		limiter: limiter.NewTokenBucket(10000),
		timeout: 5 * time.Second,
	}
```

再来对这个对象进行操作,用外部传进来的函数,对这个对象进行“覆盖操作”

```go
	for _, opt := range opts {
		if err := opt(c); err != nil {
			return nil, err
		}
	}
```

由于我是C++出身, Go作为我的第二语言. 所以在第一次接触这种设计模式的时候.会去思考c++为什么不会这么写?而go会这么写?(这块大家可以多思考一下,多了解一下)

我归结了几个原因:

C++我们可以这么写:

```go
Client();
Client(Codec c);
Client(Codec c, int timeout);
Client(Codec c, int timeout, LoadBalancer lb);

```

C++ 支持：

* 构造函数重载
* 默认参数
* 可选参数

所以它天然适合, 通过重载解决不同配置场景

而Go中, 没有函数重载机制,不允许

```go
func NewClient()
func NewClient(codec codec.Type)
```

但是如何优雅的支持可选参数?

于是就出现了**Functional Options Pattern（函数式选项模式）**

**优点 1：可读性极高(像是自然语言)**

```go
NewClient(
    reg,
    WithClientCodec(codec.JSON),
    WithClientTimeout(10*time.Second),
)

```

**优点 2：可扩展性极强**

以后新增加新的如下选项,不用更改NewClient函数的签名,这点在大型工程中非常重要

```go
WithRetry(3)
WithBreaker(...)
WithPoolSize(100)

```

对比C++中的Builder 模式(**23种设计模式中的建造者模式**)

感兴趣的可以了解一下什么是建造者模式,下面是找的一篇文章([设计模式——Builder模式](https://blog.csdn.net/yxh_1_/article/details/116049542))

我们可能会这么写.而Go 直接把 Builder 模式函数化了

```cpp
ClientBuilder builder;
builder.SetTimeout(10);
builder.SetCodec(JSON);
Client c = builder.Build();

```

对比

| 对比项 | C++ | Go |
| --- | --- | --- |
| 构造函数重载 | 支持 | 不支持 |
| 默认参数 |  支持 | 不支持 |
| 可选参数 |  原生支持 | 需要模式 |
| 解决方案 | 重载 | 选项模式 |

# Start函数(服务端调用)\[网络模式知识点]

在使用本 RPC 框架时：

* 客户端通过 InvokeAsync发送请求
* 服务端通过 Start方法启动 TCP 监听

在 Start 方法内部：

1. 创建 listen 对象监听指定端口
2. 循环调用 Accept 接收客户端连接
3. 为每一个 TCP 连接启动一个 goroutine 执行 `Handle` 方法

因此，从逻辑层来看：

本框架采用 **One Connection One Goroutine** 模型

即每个连接由一个独立协程负责读写与业务处理。

## 底层实现机制分析

虽然代码层面使用的是阻塞式 Accept() 和 go Handle(conn)，\
但在 Linux 系统下，Go 的 **net** 包底层并非真正的阻塞 I/O。

Go runtime 内部实现了：

* netpoll 机制
* 基于 epoll 的 I/O 多路复用
* 统一的事件循环（Reactor）
* M:N 调度模型

因此从操作系统角度来看，本 RPC 框架的真实网络模型为：

单 Reactor（epoll）+ M:N 调度模型

其中：

* 单 Reactor 负责统一监听所有 fd 的 I/O 事件
* goroutine 由 runtime 调度到多个 OS 线程上执行

## 与经典 Reactor 模型的关系

经典网络模型包括：

* 单 Reactor 单线程
* 单 Reactor 多线程
* 多 Reactor 多线程

本框架并未显式实现 Reactor 模型，\
而是依赖 Go runtime 封装好的 netpoll 机制完成事件驱动调度。

因此可以认为：

本 RPC 框架是一种 Go 风格的 Reactor 封装模型。

**上述涉及到操作系统八股相关知识,感兴趣的可以多了解这块知识点**

```cpp
func (s *Server) Start() error {
	ln, err := net.Listen("tcp", s.addr)
	if err != nil {
		return err
	}
	s.listener = ln

	for {
		conn, err := ln.Accept()
		if err != nil {
			select {
			case <-s.closing:
				return nil
			default:
				continue
			}
		}

		tcpConn := transport.NewTCPConnection(conn)

		s.conns[tcpConn] = struct{}{}

		go func() {
			s.Handle(tcpConn)
			delete(s.conns, tcpConn)
		}()
	}

}
```

# 服务端反射调用方法

在讲解Start函数的时候,我们知道针对每一个连接,都会开启一个协程去执行Handle函数,我们一起探索其内部实现:

可以发现包含了读取请求,限流检查的操作, 但是最核心是Process这个方法,我们继续往内层看

```go
func (s *Server) Handle(conn *transport.TCPConnection) {
	defer conn.Close()
	for {
		// 读取请求
		msg, err := conn.Read()
		if err != nil {
			// 连接被关闭或出错，退出
			return
		}
		// 限流检查
		if !s.limiter.Allow() {
			resp := &protocol.Message{
				Header: &protocol.Header{
					RequestID:   msg.Header.RequestID,
					Error:       "rate limit exceeded",
					Compression: codec.CompressionGzip,
				},
			}
			conn.Write(resp)
			continue
		}
		// 处理请求
		s.handler.Process(conn, msg, s.services[msg.Header.ServiceName])
	}
}
```

Process方法首先将读到消息里面的serviceName和MethodName传入给了invoke方法

其次将invoke方法返回的结果进行了包装,并写入给对端.所以不难发现,

其实invoke函数就是在调用本地服务的方法. 根据字符串方法名，动态调用本地方法

```go
func (h *Handler) Process(conn *transport.TCPConnection, msg *protocol.Message, server interface{}) {
	result, err := h.invoke(
		context.Background(),
		server,
		msg.Header.ServiceName,
		msg.Header.MethodName,
		msg.Body,
	)
	if err != nil {
		h.writeError(conn, msg.Header.RequestID, err.Error())
		return
	}

	var body []byte
	if result != nil {
		var marshalErr error
		body, marshalErr = h.codec.Marshal(result)
		if marshalErr != nil {
			log.Println("marshal error:", marshalErr)
			h.writeError(conn, msg.Header.RequestID, marshalErr.Error())
			return
		}
	}

	resp := &protocol.Message{
		Header: &protocol.Header{
			RequestID:   msg.Header.RequestID,
			Compression: codec.CompressionGzip,
		},
		Body: body,
	}

	conn.Write(resp)
}
```

在了解invoke函数前,我们先来了解一下什么是反射?

## 什么是反射?

我们平时写代码是这样的 , 编译器在编译阶段就知道：arith方法是什么类型,Add方法是否存在,参数类型是什么

这叫做静态调用(编译器确定了)

```go
arith.Add(req, reply)
```

而在RPC框架中,客户端发送的信息是像如下这种字符串,我们并不知道是哪个结构体,方法参数是什么类型,返回值是什么类型,而反射就可以做到知道这些信息

```go
{
  "service": "Arith",
  "method": "Add"
}
```

所以, 反射就是：在运行时，动态地查看类型信息，并且调用方法。

更简单地说:反射可以用字符串调用方法

因为RPC框架中,我们必须支持任意服务、支持任意方法、支持任意参数结构.

**所以需要动态解析+动态调用,而Go中 能做到这一点的只有反射**(当然也可以使用idl工具如proto工具生成代码的方式)

说完这些,我们再来看看invoke的函数定义:

```go
func (h *Handler) invoke(
    ctx context.Context,
    service interface{},  //注册的服务实例
    serviceName, methodName string,  //服务名与方法名
    body []byte, 
) (interface{}, error)

```

再来看看完整实现:

```go
func (h *Handler) invoke(ctx context.Context, service interface{}, serviceName, methodName string, body []byte) (interface{}, error) {
    //第一步：把 service 变成反射对象
    //reflect.Value 是反射世界里的对象
    //动态调用方法，必须先拿到service例的反射对象
	serviceValue := reflect.ValueOf(service)
    //根据字符串找方法,例如"Add"字符串,他会找到该实例的Add方法
	method := serviceValue.MethodByName(methodName)
    //判断方法是否存在
	if !method.IsValid() {
		return nil, fmt.Errorf("method not found: %s.%s", serviceName, methodName)
	}
    //查看方法的签名,这边主要是查看参数个数与返回参数个数
	methodType := method.Type()
	numIn := methodType.NumIn()
	numOut := methodType.NumOut()
    //准备参数列表,因为反射调用必须传入[]reflect.Value
    //而不能直接传递普通的参数
	args := make([]reflect.Value, 0, numIn)
	// net/rpc 风格
	// func(req *Req, reply *Resp) error
    //如果符合这种rpc参数风格,那么就会开始调用方法
	if numIn == 2 &&
		methodType.In(0).Kind() == reflect.Ptr &&
		methodType.In(1).Kind() == reflect.Ptr &&
		numOut == 1 &&
		methodType.Out(0).Implements(reflect.TypeOf((*error)(nil)).Elem()) {

		// 构造 req
		reqType := methodType.In(0)
		req := reflect.New(reqType.Elem())

		if len(body) > 0 {
			if err := h.codec.Unmarshal(body, req.Interface()); err != nil {
				return nil, err
			}
		}

		// 构造 reply
		replyType := methodType.In(1)
		reply := reflect.New(replyType.Elem())

		args = append(args, req)
		args = append(args, reply)
        //真正开始调用方法例如Add方法
		results := method.Call(args)

		// 我们rpc风格的返回值是error
        // 所以这边会将其转化成error类型并返回回去
		if errVal := results[0].Interface(); errVal != nil {
			return nil, errVal.(error)
		}
        // resp是指针,Elem返回的是他所对应的值
		return reply.Elem().Interface(), nil
	}
	return nil, nil
}
```

总结整段invoke函数的代码, 分别包含下面几个步骤, 这就是RPC 框架的核心执行流程

* 根据字符串找到方法
* 检查方法签名是否合法
* 动态创建 req
* 反序列化请求数据
* 动态创建 reply
* 通过反射调用方法
* 返回 reply
