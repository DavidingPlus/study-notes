# 7.6 连接与连接池(重点)

# 连接与连接池
## 什么是连接?
在讲解连接池之前,我们先讲解什么是连接,在我们这套RPC框架中,内部维护的是TCP连接. 好比电话线, 客户端和服务端只有建立连接,建立好这条电话线,才能通信

建立连接不是一瞬间就完成的,而是完成三次握手之后才建立来的

每一个 TCP 连接都会占用：

+ 文件描述符（FD）
+ 内存缓冲区
+ 内核 socket 资源

如果每个请求都新建立连接,那么如果1秒需要发送1000次请求,就需要在1s建立1000条连接,在操作系统中,一个进程中所能创建的文件描述符也是有限制的,且创建大量连接会导致CPU 飙升、FD 被耗尽、服务崩溃

## 什么是连接池?为什么需要连接池?什么是连接复用?
提前创建好一些 TCP 连接，放在这个池子里，大家重复使用

这个池子就是连接池

就像：

+ 不要每次打电话都重新拉电话线
+ 而是装好 10 条固定电话线
+ 需要打电话时直接用

为什么 RPC 需要连接池？

+ 建立 TCP 连接非常昂贵
+ 三次握手耗时
+ 创建太多连接会耗尽资源

所以我们通过连接池,复用了连接

**这叫做RPC端的连接复用**

## 什么是请求复用?
一般来说,连接复用的做法就是,一个进程中的多个线程/协程在从连接池中获取连接后,这个连接就会从连接池弹出,直到这个线程/协程用完了这个连接,归还到连接池后,其他线程/协程才能继续使用相同的连接. 

这样做的坏处是,做不到针对同一个连接的复用. 不利于高并发场景. 因为针对同一个连接,不同线程/协程是串行执行的.效率很低, **针对HTTP1.0,请求端和服务端都是只能串行,不支持真正的复用,而Http1.1,服务端依旧存在串行现象**(这块是底层八股,大家可以去多阅读一下)

而请求复用.是针对同一个连接,可以被多个线程/协程都同时拥有.当然,在同一个封装的连接中,对一些必要的场景,会进行加锁操作

这就是请求复用

**那么大家可以思考一下 :那么针对不同线程/协程都是同一个连接,服务端这边是无感知的,不清楚这个请求来自于哪个线程/协程. 那么怎么辨识呢?**

答: 利用requestID/streamID

像HTTP2.0支持真正的多路复用：

+ 一个 TCP 连接
+ 多个 Stream
+ 每个 Stream 有 ID
+ 数据拆成 Frame
+ Frame 里带 streamId

也就是对TCP 之上再封装了一层

**只要对TCP层面进行一些封装,每次发送的时候带一些"标识符",就可以知道是哪个线程/协程的了:**

**具体示例如下:**

```go
请求1 ──────┐
请求2 ──────┼── 同一条TCP连接
请求3 ──────┘

响应2 先回来
响应1 后回来
响应3 再回来

```

很多人容易把这二者搞混.这里列举一个表格

| 技术 | 作用 |
| --- | --- |
| 连接池 | 多条连接复用 |
| 请求复用 | 一条连接并发多个请求 |


在代码中,我们不仅仅支持连接复用,也支持请求复用

****

## 连接池代码封装讲解(连接复用与请求复用解析)
### 连接池结构体定义:
```go
type ConnectionPool struct {
	addr string  //远端地址
	maxActive int //最大连接数
	conns []*TCPClient //当前连接列表
	mu    sync.Mutex //锁,用于并发安全
	closed bool //连接池是否处于关闭状态
	next   int //轮询索引
}
```

### 创建连接池: 
注意：一开始并不会创建连接 . 连接是“按需创建” . 这是懒加载设计(防止在初始化的时候创建过多连接,导致启动过慢)

```go
func NewConnectionPool(addr string, maxIdle, maxActive int) *ConnectionPool {
	return &ConnectionPool{
		addr:      addr,
		maxActive: maxActive,
		conns:     make([]*TCPClient, 0, maxActive),
	}
}

```

### 核心方法:Acquire函数
用于从池子里拿一个可用连接

如果当前连接数量达到了最大连接,那么会轮询查找已有连接(**注意,此时连接可能被其它使用者也拿到了,但是这边依旧会将这个连接给出去,这叫做请求复用,在Http1.1中,也有对Http1.0的相应优化)**

还需要注意的是,这边如果连接已经死了,那么会进行删除操作,如果连接池中的所有连接都死了,那么会新开辟一个和对端的连接

为什么需要这样做?

我在自测代码的时候,模拟了这么一个场景.

先启动两个服务端,分别是localhost的9090端口和9091端口,此时客户端的demo是可以正常运行输出的, 但是当我将服务端杀死再启动, 此时连接会断开, 而客户端依旧拥有这个无效的连接(未清除)所以,此时拿到了当前连接,再去发送其实会出现发送失败的现象.固然这边会进行一次连接是否失效的判断.

```go
func (p *ConnectionPool) Acquire(ctx context.Context) (*TCPClient, error) {
	//加锁
    p.mu.Lock()
	defer p.mu.Unlock()
    //连接池关闭则不返回连接,返回报错信息
	if p.closed {
		return nil, ErrPoolClosed
	}

	// 如果当前连接数量 < 最大值,那么就新建立连接
	if len(p.conns) < p.maxActive {
        //新建立连接
		conn, err := newTCPClient(p.addr)
		if err != nil {
			return nil, err
		}
		p.conns = append(p.conns, conn)
		return conn, nil
	}

	// 轮询
	for i := 0; i < len(p.conns); i++ {
		idx := (p.next + i) % len(p.conns)
		conn := p.conns[idx]

		if atomic.LoadInt32(&conn.closed) == 0 {
			p.next = (idx + 1) % len(p.conns)
			return conn, nil
		}

		// 删除死亡连接
		p.conns = append(p.conns[:idx], p.conns[idx+1:]...)
		if len(p.conns) == 0 {
			break
		}
	}

	// 如果全死了，重新建
	conn, err := newTCPClient(p.addr)
	if err != nil {
		return nil, err
	}

	p.conns = append(p.conns, conn)
	return conn, nil
}
```

### Close函数
将连接池上的所有连接都关闭,并标记closed字段为true.

```go
func (p *ConnectionPool) Close() {
	p.mu.Lock()
	defer p.mu.Unlock()

	if p.closed {
		return
	}
	p.closed = true

	for _, conn := range p.conns {
		conn.Close()
	}
}
```

## 连接代码封装讲解:
关于连接,有这么两个结构体

一个是TCPConnection. 核心职责只有 3 个(不懂下面的知识点我们接下来会讲)：

1. 解决粘包/半包
2. 提供完整 Message 读写
3. 屏蔽底层 net.Conn 细节

一个是TCPClient. TCPClient 是带请求复用能力的逻辑客户端, 它解决的是

+ 多协程并发发送
+ requestID 分配
+ Future 管理
+ 异步响应分发
+ 连接失败广播

### 什么是半包?
很多刚学网络编程的人都会有一个误区, 即发送一条消息，对方就能一次 Read 读到一整条消息。

但其实TCP 不是“消息协议”，它是面向字节流的协议, 可以粗略理解为是一个字符一个字符发送出去的

那么什么是半包?

假设客户端发送完整消息A,但由于网络原因，服务端可能第一次只读到消息A的一半 ,这就是半包问题

### 什么是粘包?
假设客户端连续发送两条消息, [消息A][消息B] ,但服务端可能一次 Read 就读到了,那么两条消息就粘在一起了,你并不知道消息的边界在哪里. 不知道哪里是A的终点,哪里是B的起点. 这就是粘包

因为 TCP 只保证数据可靠和数据有序, 但并不保证每次 Read 是一条完整消息

我们设计了一套规范

### 自定义规范:
#### Message的结构
可以理解为一条完整的 RPC 消息 = 头部(Header) + 消息体(Body)

```go
type Message struct {
	Header *Header
	Body   []byte
}

```

而Header里面有什么?

#### Header的结构
Header字段每个都有注释,就不一一说了

但是有一点需要提及, 针对压缩,其实压缩的是body的数据

在HTTP2.0前,只会对body数据进行压缩(通过Content-Encoding: gzip指定压缩方式)

但是在HTTP2.0,他会对header也进行压缩.(HPACK)防止一些冗余数据的堆积. 这点不过多提及,属于是计算机网络八股层面的知识了,大家有兴趣可以了解一下

在本项目协议中,由于设计的不会过于复杂,所以并没有对header进行压缩

```go
type Header struct {
	RequestID   uint64 //用于多路复用
	ServiceName string //用于服务名
	MethodName  string //用于方法名
	Error       string //错误信息 
	CodecType   CodecType //编解码类型
	Compression codec.CompressionType //Body压缩方式
}
```

框架层面会封装头和体, 其实还会在包装一层.最终网络发送的结构为

```go
┌────────┬────────────┬────────────┬────────────┬────────────┐
│ Magic  │ headerLen  │ bodyLen    │ Header数据  │ Body数据    │
│ 2字节   │ 4字节       │ 4字节       │ 变长        │ 变长        │
└────────┴────────────┴────────────┴────────────┴────────────┘

```

这样,在发送信息的时候,对端就可以知道头的大小是多少, 体的大小是多少

知道完整的消息大小是多少了

#### Encode函数
它的目标是把 Message 结构体转成可以通过 TCP 发送的字节数组

```go
func Encode(msg *Message) ([]byte, error) {
    //校验 Header
    //没有 Header 就不知道请求信息,所以必须要要求不为空
	if msg.Header == nil {
		return nil, fmt.Errorf("header is nil")
	}

	bodyBytes := msg.Body
    //压缩 Body
	if msg.Header.Compression != codec.CompressionNone {
		var err error
		bodyBytes, err = codec.Compress(bodyBytes, msg.Header.Compression)
		if err != nil {
			return nil, err
		}
	}

	headerCodec, err := codec.New(codec.JSON)
	if err != nil {
		return nil, err
	}
    //序列化 Header
	headerBytes, err := headerCodec.Marshal(msg.Header)
	if err != nil {
		return nil, err
	}
    //计算长度
	headerLen := uint32(len(headerBytes))
	bodyLen := uint32(len(bodyBytes))

	total := 2 + 4 + 4 + headerLen + bodyLen
	buf := make([]byte, total)
    //写入固定头
	binary.BigEndian.PutUint16(buf[0:2], Magic)

	binary.BigEndian.PutUint32(buf[2:6], headerLen)

	binary.BigEndian.PutUint32(buf[6:10], bodyLen)

	copy(buf[10:], headerBytes)

	copy(buf[10+headerLen:], bodyBytes)

	return buf, nil
}
```

#### Decode函数解析:
本质作用就是把收到的字节数组还原成 Message

```go
// DecodeHeaderLen 从字节切片解析 headerLen
func DecodeHeaderLen(data []byte) uint32 {
	return binary.BigEndian.Uint32(data)
}

// DecodeBodyLen 从字节切片解析 bodyLen
func DecodeBodyLen(data []byte) uint32 {
	return binary.BigEndian.Uint32(data)
}

// DecodeBytes 从字节数组解码完整的 Message（用于粘包处理）
func Decode(data []byte) (*Message, error) {
    //最小长度检查,如果连头都没有，根本没法解析
    //所以强制要求一定要>=10
	if len(data) < 10 {
		return nil, fmt.Errorf("data too short")
	}

	// 检查 Magic
	if binary.BigEndian.Uint16(data[0:2]) != Magic {
		return nil, fmt.Errorf("invalid magic number")
	}
    //读取长度字段
	headerLen := binary.BigEndian.Uint32(data[2:6])
	bodyLen := binary.BigEndian.Uint32(data[6:10])

	totalLen := 10 + int(headerLen) + int(bodyLen)
    //完整性检查(这边会一次性读取完整一个包结构)
    //所以必须要达到完整的包,才会对其进行处理
	if len(data) < totalLen {
		return nil, fmt.Errorf("incomplete packet")
	}

	headerBytes := data[10 : 10+headerLen]

	headerCodec, err := codec.New(codec.JSON)
	if err != nil {
		return nil, err
	}

	var header Header
	if err := headerCodec.Unmarshal(headerBytes, &header); err != nil {
		return nil, err
	}

	// 读取 body
	bodyBytes := data[10+headerLen : 10+headerLen+bodyLen]

	if header.Compression != codec.CompressionNone {
		bodyBytes, err = codec.Decompress(bodyBytes, header.Compression)
		if err != nil {
			return nil, err
		}
	}
    //构造 Message并返回
	return &Message{
		Header: &header,
		Body:   bodyBytes,
	}, nil
}

```



### TCPConnection代码封装解析:
这段代码的作用就是在 TCP 之上，构建一个有边界的消息协议

#### 结构体定义:
TCPConnection中reader *bufio.Reader. 是用于提升效率的.

不用net.Conn原生自带的read函数,是因为它的读取效率并不高

而bufio.Reader是带缓冲的读取器,可以减少系统调用,提高读取效率

```go
type TCPConnection struct {
	conn   net.Conn    //操作系统 TCP
	reader *bufio.Reader //提高读取效率
	buffer *PacketBuffer //解决粘包半包
}

```

其中PacketBuffer定义如下:

```go
type PacketBuffer struct {

}

```

#### PacketBuffer中的Read方法
```go
func (pb *PacketBuffer) Read() []byte {
	pb.lock.Lock()
	defer pb.lock.Unlock()

	// 最小包头长度校验
	if len(pb.buf) < 10 {
		return nil
	}

	headerLen := int(protocol.DecodeHeaderLen(pb.buf[2:6]))
	bodyLen := int(protocol.DecodeBodyLen(pb.buf[6:10]))
	totalLen := 10 + headerLen + bodyLen

	if len(pb.buf) < totalLen {
		return nil
	}

	packet := make([]byte, totalLen)
	copy(packet, pb.buf[:totalLen])

	// 移动窗口
	pb.buf = pb.buf[totalLen:]
	return packet
}
```

#### PacketBuffer的Write方法:
每次从 socket 读到数据后,把字节 append 进缓存

```go
func (pb *PacketBuffer) Write(data []byte) {
	pb.lock.Lock()
	pb.buf = append(pb.buf, data...)
	pb.lock.Unlock()
}
```

#### TCPConnection中的Read函数
不断读取数据，直到拼出一个完整协议包

```go
func (tc *TCPConnection) Read() (*protocol.Message, error) {
	for {
		// 尝试从缓冲区取完整包
        //看看 buffer 里有没有完整的一条数据
		if packet := tc.buffer.Read(); packet != nil {
			return protocol.Decode(packet)
		}
        //从网络读取数据
		tmp := make([]byte, BufferSize)
		n, err := tc.reader.Read(tmp)
		if err != nil {
			if err == io.EOF {
				return nil, err
			}
			return nil, err
		}
        //把新收到的数据拼接进缓存
		if n > 0 {
			tc.buffer.Write(tmp[:n])
		}
	}
}
```

#### TCPConnection中的Write函数
```go
func (tc *TCPConnection) Write(msg *protocol.Message) error {
	//将消息编码
    data, err := protocol.Encode(msg)
	if err != nil {
		return err
	}
    //加锁,因为请求复用和tcp自身是流式的原因
    //这边写的时候必须完整写入一条消息
    //否则会出现ABAB这种现象,而不是预期的AABB这种
	tc.writeMu.Lock()
	defer tc.writeMu.Unlock()

	total := 0
    //循环写入
	for total < len(data) {
		n, err := tc.conn.Write(data[total:])
		if err != nil {
			return err
		}
		total += n
	}
	return nil
}
```

### TCPClient代码封装解析
TCPClient 解决的是 **请求-响应匹配问题**

这一层才是真正的：**支持并发请求的 RPC 客户端**

**它解决了一个关键问题**

我同时发 100 个请求

服务端乱序返回

我怎么知道哪个响应对应哪个请求?当然是用 RequestID 做匹配!

#### 结构体定义
```go
type TCPClient struct {
	conn *TCPConnection //底层网络通信封装(刚刚讲过)
	addr string //就是服务器地址(如127.0.0.1:8080)

	writeMu sync.Mutex 
	seq     uint64 //requestID

	pending sync.Map // map[uint64]*Future

	closed int32 //
}
```

那么这里的Future是什么呢?我们会在**探索框架实现**这一个章节中讲

#### TCPClient中的newTCPClient函数
```go
func newTCPClient(addr string) (*TCPClient, error) {
    //建立 TCP 连接
    rawConn, err := net.DialTimeout("tcp", addr, 5*time.Second)
    if err != nil {
        return nil, err
    }

    c := &TCPClient{
        conn: NewTCPConnection(rawConn),
        addr: addr,
    }
    //启动一个协程,专门负责监听服务器响应
    go c.readLoop()
    return c, nil
}
```

#### TCPClient中的readLoop函数
```go
func (c *TCPClient) readLoop() {
	for {
        //读取服务器响应
		msg, err := c.conn.Read()
		if err != nil {
			c.fail(err)
			return
		}
        //获取 RequestID
		seq := msg.Header.RequestID
        //找到对应 Future
		val, ok := c.pending.LoadAndDelete(seq)
		if !ok {
			continue
		}

		future := val.(*Future)

		if msg.Header.Error != "" {
			future.Done(nil, errors.New(msg.Header.Error))
		} else {
			future.Done(msg.Body, nil)
		}
	}
}
```

#### TCPClient中的SendAsync与fail函数
它做的事情是：发送一个请求，并返回一个 Future

```go
func (c *TCPClient) SendAsync(msg *protocol.Message) (*Future, error) {
	//检查连接是否关闭
    if atomic.LoadInt32(&c.closed) == 1 {
		return nil, errors.New("connection closed")
	}
    //生成 RequestID
	seq := c.nextSeq()
	msg.Header.RequestID = seq
    //创建 Future
	future := NewFuture()
	c.pending.Store(seq, future)
    //发送请求
	c.writeMu.Lock()
	err := c.conn.Write(msg)
	c.writeMu.Unlock()
    //如果写失败：一般来说是连接断开了
    //所以我这边会利用一个回调函数fail,将其连接断开
	if err != nil {
		c.pending.Delete(seq)
		c.fail(err) // 关键：write 失败也要彻底杀死连接(解决之前连接bug)
		return nil, err
	}

	return future, nil
}
func (c *TCPClient) fail(err error) {
	if !atomic.CompareAndSwapInt32(&c.closed, 0, 1) {
		return
	}

	// 关闭底层连接
	_ = c.conn.Close()

	// 失败所有 pending
	c.pending.Range(func(key, value interface{}) bool {
		future := value.(*Future)
		future.Done(nil, err)
		c.pending.Delete(key)
		return true
	})
}
```
