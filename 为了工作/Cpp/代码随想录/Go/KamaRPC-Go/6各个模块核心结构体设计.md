# 1）protocol 模块：协议元信息与消息体

## `protocol.Header`（`internal/protocol/header.go`）

```plain
type Header struct {
    RequestID   uint64
    ServiceName string
    MethodName  string
    Error       string
    CodecType   CodecType
    Compression codec.CompressionType
}
```

* **RequestID**：多路复用的核心键
  * 同一条 TCP 连接上并发多个请求，响应会乱序返回，必须靠 RequestID 把响应匹配回对应 Future。
* **ServiceName / MethodName**：服务路由信息
  * 服务端用它做“动态分发”：找到服务对象 + 方法名，然后反射调用。
* **Error**：把服务端错误放进协议层返回
  * 不依赖业务结构体，也避免“错误必须序列化在 Body 里”的耦合。
* **CodecType**：告诉对端 Body 用什么序列化（JSON/Protobuf…）
  * Header 属于控制面，Body 属于数据面，CodecType 让数据面可插拔。
* **Compression**：Body 是否压缩、用哪种压缩（gzip）
  * 压缩是传输层优化点，放在 Header 能让对端按需解压。

## `protocol.Message`（`internal/protocol/message.go`）

```plain
type Message struct {
    Header *Header
    Body   []byte
}
```

* **Header 指针**：Header 是元信息，频繁创建/传递，用指针更轻量，也便于扩展字段。
* **Body \[]byte**：序列化后的“纯二进制 payload”
  * RPC 框架内部只关心字节流，业务结构体只在 codec 层才出现。

# 2）transport 模块：TCP 长连接、拆包、多路复用、连接池

## `transport.PacketBuffer`（`internal/transport/tcp_connection.go`）

```plain
type PacketBuffer struct {
    buf  []byte
    lock sync.Mutex
}
```

* **buf**：承载“从 socket 读到的碎片数据”
  * TCP 是流式，可能一次 read 读到半包或多个包粘在一起，必须用 buffer 暂存并拼包。
* **lock**：保证并发安全
  * Read/Write buffer 的时候需要互斥（尤其在扩展到多 goroutine 读写时更稳）。

为什么需要 PacketBuffer？\
因为 **“解包逻辑必须基于累计字节判断边界”**：不到一个完整包就继续读，够了才切出来。

***

## `transport.TCPConnection`（`internal/transport/tcp_connection.go`）

```plain
type TCPConnection struct {
    conn    net.Conn
    reader  *bufio.Reader
    buffer  *PacketBuffer
    writeMu sync.Mutex
}
```

* **conn**：底层 TCP socket
* **reader bufio.Reader**：减少 syscall 次数，读性能更稳定
  * 读包时通常是多次小读，bufio 能显著降低系统调用开销。
* **buffer PacketBuffer**：解决粘包/半包
  * Read() 逻辑 = 先尝试从 buffer 拼包，不够再从 conn 继续读补齐。
* **writeMu**：写互斥，避免并发 Write 导致字节交叉写入
  * 多个 goroutine 同时写一个 net.Conn，会出现“包内容交错”风险；互斥是最直接安全的做法。

***

## `transport.TCPClient`（`internal/transport/tcp_client.go`）

```plain
type TCPClient struct {
    conn    *TCPConnection
    addr    string
    writeMu sync.Mutex
    seq     uint64
    pending sync.Map
    closed  int32
}
```

* **conn**：这条 client 端持有的 TCPConnection（长连接）
* **addr**：连接的服务端地址，用于日志/错误定位/重连策略等
* **seq**：全局递增 requestId 生成器
  * 每次发送请求都需要唯一 RequestID，用 seq++ 是最简单且高效的方案。
* **pending sync.Map**：`requestId -> Future` 的映射表（多路复用关键）
  * 发送时 `Store(id,future)`；readLoop 收到响应后 `LoadAndDelete(id)` 完成 future。
* **closed int32**：连接关闭标记（原子变量）
  * 用于防止重复关闭、读写在关闭后的异常路径（比互斥更轻量）。
* **writeMu**（注意：这里也有写锁）：与 TCPConnection 的 writeMu 类似用途
  * 项目里“双重写锁”属于偏保守设计：一层在 client 发包级别串行化，一层在 connection 级别兜底保证 conn.Write 安全。

为什么 TCPClient 要自己维护 pending？\
因为多路复用的本质就是：**同一连接上并发请求，必须有一个“响应归属表”**。

***

## `transport.Future`（`internal/transport/future.go`）

```plain
type Future struct {
    done  chan struct{}
    res   []byte
    err   error
    mu    sync.Mutex
    codec codec.Codec

    onComplete func(error)
}
```

* **done chan struct{}**：一次性完成通知
  * 非常典型：`close(done)` 广播唤醒所有等待者，开销小、写法清晰。
* **res / err**：承载结果与错误
  * res 是响应 body 的 bytes，err 是网络错误/超时/服务端 error 等。
* **mu**：保护 res/err 的并发读写
  * readLoop 写入结果 + 业务 goroutine 读取结果并反序列化，需要锁保证一致性。
* **codec**：用于 `GetResult(out)` 时把 res 反序列化到业务结构体
  * 把“结果 bytes → 业务对象”的责任放到 Future 上，调用侧体验更好。
* **onComplete**：完成回调（框架内部用来更新熔断统计等）
  * 设计点：Future 完成是一个天然的 hook 点，适合挂熔断成功/失败计数。

为什么不用 channel 直接传 `Reply`？\
因为框架是通用 RPC：Reply 类型不固定，用 `[]byte + codec` 才能做到解耦与可插拔。

***

## `transport.ConnectionPool`（`internal/transport/tcp_connection_pool.go`）

```plain
type ConnectionPool struct {
    addr      string
    maxActive int
    conns     []*TCPClient
    mu        sync.Mutex
    closed    bool
    next      int
}
```

* **addr**：这个池子对应哪个目标节点（一个 addr 一组连接）
* **maxActive**：上限控制（防止无限建连把服务端/本机打爆）
* \*\_conns \[]\_*TCPClient*：池内连接集合
* **next**：简单轮询取连接（连接复用）
  * 连接池内部也做一个“负载均衡”：请求分散到不同连接，降低单连接队头阻塞。
* **mu / closed**：并发控制 + 关闭状态
  * 避免 acquire 时与 close 并发冲突。

为什么需要连接池？\
因为单连接虽然支持多路复用，但在高并发/大包场景仍可能队头阻塞；连接池能提升吞吐与稳定性。

# 3）client 模块：治理总控（发现 + LB + 熔断限流 + 超时）

## `client.Client`（`internal/client/client.go`）

```plain
type Client struct {
    reg     *registry.Registry
    lb      loadbalance.LoadBalancer
    limiter *limiter.TokenBucket
    timeout time.Duration
    codec   codec.Codec
    breaker sync.Map
    pools   sync.Map
}
```

* **reg**：服务发现来源（etcd registry）
* **lb**：负载均衡策略（RR/Random/WeightedRR…）
* **limiter**：客户端限流（保护自己：避免请求洪峰把本机 goroutine/连接打满）
* **timeout**：默认超时（配合 context 控制调用上限）
* **codec**：默认序列化协议（JSON/Protobuf）
* **breaker sync.Map**：熔断器集合（通常按 `service+addr` 维度存）
  * 让每个下游实例有独立熔断状态，避免“一台挂了拖死全部”。
* **pools sync.Map**：连接池集合（按 addr 维度）
  * key=addr，value=\*ConnectionPool，做到“实例隔离 + 连接复用”。

为什么 Client 要同时持有 registry / lb / breaker / pools？\
因为它是**一次调用的“控制中心”**：先发现，再选址，再检查熔断，再拿连接，再发包。

# 4）server 模块：服务注册表 + 反射分发 + 监听与连接管理

## `server.Server`（`internal/server/server.go`）

```plain
type Server struct {
    addr     string
    services map[string]interface{}
    limiter  *limiter.TokenBucket
    listener net.Listener
    handler  *Handler
    codec    codec.Codec

    conns   map[*transport.TCPConnection]struct{}
    closing chan struct{}
}
```

* **addr**：监听地址
* **services map\[string]interface{}**：服务注册表（serviceName -> 实例）
  * Register("Arith",\&Arith{}) 存进去，真正调用时再用反射找方法。
* **limiter**：服务端限流（保护服务端：避免被突发流量打穿）
* **listener**：net.Listener（Accept 新连接）
* **handler**：请求处理器（解码、反射调用、编码响应）
* **codec**：服务端默认 codec（一般与 client 协商/一致）
* **conns map\[\*TCPConnection]struct{}**：已建立连接集合
  * 用于管理与优雅关闭：关闭时遍历 conns 逐个 Close。
* **closing chan struct{}**：关闭广播信号
  * 典型 stop channel：通知 accept/handle 循环退出。

为什么 services 用 `map[string]interface{}`？\
因为框架不知道业务服务的具体类型，用 interface{} 才能容纳任意 struct；分发靠反射完成。

***

## `server.Handler`（`internal/server/handler.go`）

```plain
type Handler struct {
    codec codec.Codec
}
```

* **codec**：用于“请求 Body 反序列化 + 响应 Body 序列化”
  * 让 handler 只聚焦“如何执行方法”，而序列化策略可插拔。

Handler 为什么要独立出来？\
这是一个典型的分层：Server 负责网络 accept/连接管理；Handler 负责业务调用与响应组装。

# 5）registry 模块：etcd 注册发现 + watch + 本地缓存

## `registry.Instance`（`internal/registry/registry.go`）

```plain
type Instance struct {
    Addr string
}
```

* 很轻量：只存地址
  * 这是一个“演示版最小实例信息”，生产级通常还会加：weight、version、tags、meta、健康状态等。

## `registry.Registry`

```plain
type Registry struct {
    client  *clientv3.Client
    prefix  string

    mu       sync.RWMutex
    services map[string]map[string]Instance

    ctx    context.Context
    cancel context.CancelFunc
}
```

* **client**：etcd 客户端
* **prefix**：服务 key 前缀（例如 `/kamaRPC/services/`）
* **services**：本地缓存：`serviceName -> (addr -> Instance)`
  * Discover 先读缓存；没有再 Get 全量，并启动 watch 增量维护。
* **mu RWMutex**：读多写少场景，用 RWMutex 提升并发性能
  * Discover 会高频读缓存，watch 偶尔写更新，非常适合读写锁。
* **ctx/cancel**：registry 生命周期控制
  * 用来关闭 watch / keepalive 等后台 goroutine。

为什么要本地缓存？\
如果每次调用都去 etcd Get，会把注册中心打爆；缓存 + watch 才是常见生产形态。

# 6）loadbalance 模块：尤其是 WeightedRR 的关键字段

## `loadbalance.WeightedRR`（`internal/loadbalance/weighted_rr.go`）

```plain
type WeightedRR struct {
    mu            sync.Mutex
    weights       []int
    currentWeight []int
    totalWeight   int
}
```

* **weights**：静态权重列表（对应实例）
* **currentWeight**：平滑加权轮询的“动态权重”数组
  * 每次选择时累加并挑最大，再减 totalWeight，达到“平滑”效果。
* **totalWeight**：权重总和（减少重复计算）
* **mu**：因为 currentWeight 会变，Select 必须加锁保护并发安全

为什么需要 currentWeight？\
平滑 WRR 的精髓就是：**不用一次性把权重展开成 N 个节点**，而是用动态权重实现均匀分布与平滑性。

# 7）breaker 模块：熔断器状态机的关键字段

## `breaker.CircuitBreaker`（`internal/breaker/breaker.go`）

```plain
type CircuitBreaker struct {
    mu sync.Mutex

    state State

    failureCount int
    successCount int

    windowSize       int
    failureThreshold float64

    openTimeout      time.Duration
    lastStateChange  time.Time

    halfOpenProbe bool
}
```

* **state**：Closed/Open/HalfOpen
* **failureCount / successCount**：窗口统计
  * 判断失败率是否超过阈值，是否进入 Open；HalfOpen 探测是否恢复。
* **windowSize**：统计窗口大小（样本数）
* **failureThreshold**：失败率阈值（例如 0.5）
* **openTimeout**：Open 状态保持时间（到期后进入 HalfOpen 探测）
* **lastStateChange**：记录状态切换时间（用来判断 openTimeout）
* **halfOpenProbe**：HalfOpen 下“是否已经放行过探测请求”
  * HalfOpen 一般只允许少量探测，避免瞬时放量再次打挂下游。

为什么必须记录 lastStateChange？\
因为 Open 状态不是永久，超时后要自动进入 HalfOpen；时间是状态机推进条件。

# 8）limiter 模块：令牌桶关键字段

## `limiter.TokenBucket`（`internal/limiter/token_bucket.go`）

```plain
type TokenBucket struct {
    tokens int
    rate   int
    mu     sync.Mutex
}
```

* **tokens**：当前可用令牌数（是否放行的依据）
* **rate**：补充速率（每秒/每周期补 tokens）
* **mu**：并发 Allow 时保护 tokens

为什么用令牌桶？\
它允许一定“突发流量”（桶里有积累的 token），比漏桶更适合 RPC 这种短时突发请求模型。
